Section 1: Spring Framework Quick Reference & Java Annotations

Q1. What is Dependency Injection, and how does Spring implement it? Which injection style is best?

DI supplies an object's dependencies from outside rather than having it construct or look them up itself, decoupling classes from concrete implementations and making unit tests easier (dependencies can be mocked). Spring's IoC container implements DI: you declare beans (via @Component, @Service, @Repository, or Java/XML configuration) and Spring wires them together. (See Part 1, Section 9 for the IoC principle itself.)

  • Constructor injection (recommended) — makes dependencies explicit, enables immutability (final fields), fully initializes the object on construction, and fails fast if a bean is missing.
  • Setter injection — suits optional dependencies and reconfiguration after construction, but risks partially initialized objects if the setter is never called.
  • Field injection — concise, but hides dependencies and is harder to test and mock.

Rule of thumb: constructor injection for mandatory dependencies, setter injection for optional ones. Compared with the Factory pattern, DI yields cleaner code: the class is a plain POJO that declares what it needs, with no knowledge of how dependencies are built or of any factory API, so it is easier to test in isolation.

@Service
public class OrderProcessingService {
    private final PaymentGateway paymentGateway; // dependency
 
    // constructor injection -- Spring supplies a PaymentGateway bean automatically
    @Autowired
    public OrderProcessingService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}

Q2. What are Spring bean scopes, and how do they interact with thread safety?

  • singleton (default) — one shared instance per container. Spring does nothing special to make it thread-safe; it is an ordinary singleton, so concurrent access is the developer's responsibility.
  • prototype — a new instance every time the bean is requested.
  • request — one instance per HTTP request; thread-safe by construction since no two requests share an instance.
  • session — one instance per HTTP session; requests from multiple browser tabs in the same session CAN run concurrently against it, so mutable state needs care.

Any bean with no mutable instance state is a safe singleton candidate, which is why DAO, Service, and Controller beans are usually singletons: each thread passes what it needs as method arguments. A bad singleton candidate is a bean that carries per-use mutable state, such as a Person bean with mutable name/age fields, which concurrent callers would silently corrupt.

Q3. What is the difference between @Component, @Service, @Repository, and @Controller?

All are specializations of @Component, registered as Spring beans by component scanning and functionally similar; the distinction is semantic (and useful for AOP targeting). @Service marks business-logic classes; @Repository marks data-access classes and additionally enables automatic translation of persistence-technology exceptions into Spring's DataAccessException hierarchy; @Controller marks web-layer classes handling HTTP requests.

Q4. What is an annotation, and what are the standard built-in and meta-annotations?

An annotation is metadata attached to code elements (classes, methods, fields, parameters) without directly affecting the semantics of the annotated code; it is consumed by the compiler, build tools, or runtime reflection. By themselves annotations execute nothing — something (the compiler, an annotation processor, or a framework such as Spring or Hibernate) must read and act on them.

  • @Override — the compiler errors if the method doesn't actually override, catching signature typos.
  • @Deprecated — marks an element as discouraged; usage triggers a compiler warning.
  • @SuppressWarnings — suppresses specific warning categories (e.g. "unchecked").
  • @FunctionalInterface — asserts exactly one abstract method; the compiler errors otherwise.

Meta-annotations control custom annotations: @Target (which elements it may annotate), @Retention (SOURCE: discarded at compile time, useful for tools like Lombok; CLASS: kept in the .class file but invisible at runtime, the default; RUNTIME: available via reflection, required for framework-style annotations), @Documented (include in Javadoc), and @Inherited (class-level annotation inherited by subclasses).

Problem statement: Define a custom runtime annotation and read it via reflection to audit an operation.

import java.lang.annotation.*;
import java.lang.reflect.Method;
 
@Retention(RetentionPolicy.RUNTIME) // needed to read it via reflection
@Target(ElementType.METHOD)
@interface AuditableOperation {
    String description();
}
 
class OrderService {
    @AuditableOperation(description = "Processes customer order")
    public void placeOrder() {
        System.out.println("Order placed");
    }
}
 
public class AnnotationProcessorDemo {
    public static void main(String[] arguments) throws Exception {
        Method targetMethod = OrderService.class.getMethod("placeOrder");
        if (targetMethod.isAnnotationPresent(AuditableOperation.class)) {
            AuditableOperation annotationData = targetMethod.getAnnotation(AuditableOperation.class);
            System.out.println("Audit: " + annotationData.description());
        }
    }
}

Q5. What is reflection, and what are its use cases and drawbacks?

Reflection (java.lang.reflect) allows runtime inspection and manipulation of classes, methods, fields, and constructors, even private ones. Use cases: frameworks (Spring and Hibernate annotation processing), serialization libraries, and testing tools. Drawbacks: performance overhead, broken encapsulation, bypassed compile-time type safety, and blocking by module-system restrictions (Java 9+).

Section 2: Spring & Spring Boot

Already covered in Section 1 and not repeated here: DI/IoC and the three injection styles, bean scopes and their thread-safety implications, and @Component/@Service/@Repository/@Controller. Below are the Spring Boot topics beyond those.

Q1. What is Spring Boot, and how does it differ from the traditional Spring Framework?

Spring Boot is an opinionated extension of Spring that minimizes boilerplate configuration. Traditional Spring needs extensive XML or Java configuration for beans, data sources, and infrastructure; Spring Boot adds auto-configuration driven by the classpath and sensible defaults, an embedded server (Tomcat or Jetty) so the app runs as a standalone JAR, starters (spring-boot-starter-web, spring-boot-starter-data-jpa) that bundle related dependencies, and production-ready features via Actuator. It is the default choice for microservices and cloud-native apps.

Q2. How does Spring Boot auto-configuration work? How would you write a custom starter?

@SpringBootApplication includes @EnableAutoConfiguration, which makes Spring load @Configuration classes listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports (Spring Boot 3+; earlier versions used spring.factories). Those classes carry conditional annotations (@ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty), so defaults apply only when the relevant dependency is present and the developer hasn't defined their own bean. For example, adding spring-boot-starter-web auto-configures an embedded Tomcat and the DispatcherServlet.

Problem statement: Build an internal starter that gives every microservice a RestTemplate with standard timeouts, correlation-ID propagation, and audit logging.

@AutoConfiguration
@ConditionalOnClass(RestTemplate.class)
@EnableConfigurationProperties(CompanyHttpClientProperties.class)
public class CompanyHttpClientAutoConfiguration {
 
    @Bean
    @ConditionalOnMissingBean // back off if a service defines its own RestTemplate
    public RestTemplate restTemplate(CompanyHttpClientProperties clientProperties) {
        return new RestTemplateBuilder()
                .setConnectTimeout(Duration.ofMillis(clientProperties.getConnectTimeoutMs()))
                .setReadTimeout(Duration.ofMillis(clientProperties.getReadTimeoutMs()))
                .interceptors(new CorrelationIdInterceptor(), new AuditLoggingInterceptor())
                .build();
    }
}
 
# META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports
com.company.starter.http.CompanyHttpClientAutoConfiguration

Note: Tech-lead takeaway: internal starters for cross-cutting concerns (security defaults, observability, standard exception handling) are among the highest-leverage things a lead can build, turning “remember to configure X” tribal knowledge into defaults that are simply there across 30 services.

Q3. What are Spring Boot profiles, @RestController vs. @Controller, and @RequestMapping vs. @GetMapping?

  • Profiles (@Profile("dev"), application-{profile}.properties/yml, activated via spring.profiles.active) provide environment-specific beans and configuration (datasource URLs, log levels, feature toggles) without code changes.
  • @Controller returns view names resolved to templates (Thymeleaf, JSP). @RestController combines @Controller and @ResponseBody, serializing return values straight to the response body as JSON/XML, the standard for REST APIs.
  • @RequestMapping is the general-purpose mapping annotation and needs an explicit method attribute; @GetMapping, @PostMapping and so on are shortcuts preconfigured for one HTTP method, improving readability.

Q4. What is Spring Boot Actuator?

Actuator adds production-ready monitoring and management with minimal configuration, exposing endpoints such as /actuator/health, /actuator/metrics, /actuator/info, and /actuator/env, consumable by Prometheus, Grafana, or Datadog. It supports custom health indicators (database, message queue status) and provides the liveness/readiness probes Kubernetes needs. Because some endpoints expose sensitive data, restrict access with Spring Security.

Q5. How does global exception handling work with @ControllerAdvice?

A class annotated with @ControllerAdvice acts as a global interceptor for exceptions thrown by any controller; its @ExceptionHandler methods map specific exception types to a structured ResponseEntity with the right HTTP status, avoiding scattered try/catch blocks. Pair it with custom business exceptions (ResourceNotFoundException to 404, InvalidRequestException to 400) and a standard error DTO (timestamp, message, error code) for consistent client-side handling.

Problem statement: Return a consistent JSON error body and a 404 status whenever any controller throws ResourceNotFoundException.

@RestControllerAdvice
public class GlobalExceptionHandler {
 
    @ExceptionHandler(ResourceNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleResourceNotFound(ResourceNotFoundException exception) {
        ErrorResponse errorResponse = new ErrorResponse(
                Instant.now(), "RESOURCE_NOT_FOUND", exception.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(errorResponse);
    }
}
 
public record ErrorResponse(Instant timestamp, String errorCode, String message) { }

Q6. How does @Transactional work internally, and when does it silently fail?

@Transactional relies on AOP proxies (JDK dynamic proxies for interface-based beans, CGLIB proxies for class-based beans). Spring injects a proxy, not the real instance; the proxy intercepts the external call, begins the transaction, delegates to the real method, then commits or rolls back.

Silent-failure scenarios:

  • Self-invocation — a method calling another @Transactional method in the same class via this.someMethod() bypasses the proxy, so no transactional advice applies.
  • Non-public methods — proxies intercept only public method calls, so a private @Transactional method is ignored.
  • Checked exceptions — by default Spring rolls back only on unchecked exceptions (RuntimeException and Error); a thrown checked exception commits unless you configure rollbackFor.

Propagation controls nesting: REQUIRED (join or create, the default), REQUIRES_NEW (suspend and start an independent transaction), NESTED (savepoint), MANDATORY (must already exist). Isolation levels are covered in Part 4, Section 3.

@Service
public class OrderProcessingService {
 
    @Transactional(rollbackFor = Exception.class) // also roll back on checked exceptions
    public void placeOrder(OrderRequest orderRequest) throws Exception { /* ... */ }
 
    public void processBatch(List<OrderRequest> orderRequests) throws Exception {
        for (OrderRequest orderRequest : orderRequests) {
            // BUG: self-invocation bypasses the proxy, so NO transaction is started here.
            // Fix: move placeOrder into a separate bean, or inject and call through the proxy.
            this.placeOrder(orderRequest);
        }
    }
}

Q7. Explain the Spring bean lifecycle and how circular dependencies are resolved (and when they cannot be).

The container reads bean definitions, instantiates the object (typically via constructor), populates properties via dependency injection, then runs BeanPostProcessor callbacks around initialization callbacks such as @PostConstruct or afterPropertiesSet().

For a circular dependency (A needs B, B needs A) among singleton beans using setter or field injection, Spring resolves it with a three-level cache: it creates a raw instance of A, exposes an early reference (a factory that can produce a proxy if needed) in the earlySingletonObjects cache before A is fully initialized, lets B inject that early reference, and finishes both. This does not work with constructor injection, because neither bean can be created until the other exists, producing a BeanCurrentlyInCreationException at startup.

Preferred fixes: refactor the cycle out via an intermediary service or restructured responsibilities, fall back to setter injection, or place @Lazy on one of the dependencies to defer instantiation.

Q8. How would you secure a Spring Boot REST API with JWT, handle refresh, and what are the client-side storage pitfalls?

Register a custom OncePerRequestFilter in the Spring Security filter chain that extracts the JWT from the Authorization header, validates its signature and expiry (secret key, or public key for RS256), and on success populates the SecurityContext with an Authentication object so @PreAuthorize and method security work downstream.

Access tokens are short-lived to limit exposure; a longer-lived refresh token, ideally in an httpOnly, Secure cookie, is exchanged for a new access token at a dedicated /refresh endpoint without re-entering credentials.

  • localStorage/sessionStorage are readable by JavaScript, so an XSS attack can steal the token.
  • httpOnly cookies mitigate XSS but introduce CSRF risk, requiring CSRF tokens or SameSite cookie attributes.
  • JWTs are stateless and can't be revoked before expiry; for logout or a compromised account, keep a blacklist (often in Redis with a TTL matching the token's expiry), which reintroduces a little of the statefulness JWTs were meant to avoid.

JWT structure and XSS/CSRF basics are in Part 6, Section 5.

Q9. What are Spring components, and how have you used Spring in your applications?

  • Stereotype annotations register beans via component scanning: @Component (generic), @Service (business logic), @Repository (data access, exception translation), @Controller/@RestController (web layer). @Configuration + @Bean define beans explicitly.
  • Typical usage: constructor injection of services into controllers, Spring Data JPA repositories, @Transactional on service methods, Spring Security for authentication, Actuator for health and metrics, @Scheduled jobs, and profile-based configuration in application.yml.

Q10. How does Spring MVC work, and what is a view resolver?

  • Request flow: client → DispatcherServlet (front controller) → HandlerMapping finds the controller method → HandlerAdapter invokes it → controller returns a model plus a logical view name → ViewResolver turns the name into a concrete view (Thymeleaf/JSP/FreeMarker) → view renders the response.
  • ViewResolver maps a logical name such as "orders/list" to a template (for example prefix /templates/ + name + suffix .html), keeping controllers independent of the view technology.
  • With @RestController / @ResponseBody the view step is skipped; an HttpMessageConverter writes JSON directly.

Problem statement: Return an order-details page from a controller by logical view name.

@Controller
public class OrderPageController {

    private final OrderService orderService;

    public OrderPageController(OrderService orderService) {   // constructor injection
        this.orderService = orderService;
    }

    @GetMapping("/orders/{orderId}")
    public String showOrderDetails(@PathVariable Long orderId, Model viewModel) {
        viewModel.addAttribute("order", orderService.findOrder(orderId));  // data for the view
        return "orders/details";   // logical name resolved by the ViewResolver
    }
}

Q11. How do you handle exceptions thrown from a Spring Boot interceptor?

A HandlerInterceptor runs inside DispatcherServlet, so exceptions it throws are resolved by the same @ControllerAdvice / @ExceptionHandler used for controllers.

  • preHandle() runs before the controller; return false to stop the request or throw an exception for the advice to handle.
  • postHandle() runs after the controller, only if no exception occurred.
  • afterCompletion() runs whenever preHandle returned true, even on exceptions; its Exception parameter holds the failure. Use it for cleanup/logging, not to change the response.
  • Servlet Filters run outside DispatcherServlet, so @ControllerAdvice does not see their exceptions; delegate to a HandlerExceptionResolver or handle them in the filter.

Problem statement: Reject requests without an API key header and return a clean 401 JSON error through a global handler.

// 1. Custom exception thrown by the interceptor
public class MissingApiKeyException extends RuntimeException {
    public MissingApiKeyException(String errorMessage) { super(errorMessage); }
}

// 2. Interceptor: validates the header before the controller runs
@Component
public class ApiKeyInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String apiKeyHeader = request.getHeader("X-API-KEY");
        if (apiKeyHeader == null || apiKeyHeader.isBlank()) {
            throw new MissingApiKeyException("API key is required");  // routed to @RestControllerAdvice
        }
        return true;                                                   // continue to the controller
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception exception) {
        // always runs after the request finishes; logging/cleanup only
        if (exception != null) { System.out.println("Request failed: " + exception.getMessage()); }
    }
}

// 3. Global handler converts the exception into an HTTP response
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(MissingApiKeyException.class)
    public ResponseEntity<Map<String, String>> handleMissingKey(MissingApiKeyException exception) {
        return ResponseEntity.status(HttpStatus.UNAUTHORIZED)         // 401
                .body(Map.of("error", exception.getMessage()));
    }
}

// 4. Register the interceptor
@Configuration
public class WebConfiguration implements WebMvcConfigurer {
    @Autowired private ApiKeyInterceptor apiKeyInterceptor;

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(apiKeyInterceptor).addPathPatterns("/orders/**");
    }
}

Q12. How do you configure multiple data sources in Spring Boot?

Boot auto-configures exactly one DataSource from spring.datasource.*. For two databases, disable reliance on that: define your own properties prefix, and for each database declare a DataSource, an EntityManagerFactory and a TransactionManager, then bind each Spring Data repository package to its own set. Mark one set @Primary so auto-configured pieces (Actuator health, Flyway, plain JdbcTemplate) have a default.

Problem statement: An application reads orders from an "orders" database and stock levels from an "inventory" database. Configure both with separate connection pools, entities, repositories and transaction managers.

# application.yml: one block per database (custom prefix, not spring.datasource)
app:
  datasource:
    orders:
      url: jdbc:postgresql://orders-host:5432/orders
      username: orders_user
      password: ${ORDERS_DB_PASSWORD}
      hikari.maximum-pool-size: 10
    inventory:
      url: jdbc:mysql://inventory-host:3306/inventory
      username: inventory_user
      password: ${INVENTORY_DB_PASSWORD}
      hikari.maximum-pool-size: 5
@Configuration
@EnableJpaRepositories(
        basePackages = "com.example.orders.repository",        // repositories that use THIS database
        entityManagerFactoryRef = "ordersEntityManagerFactory",
        transactionManagerRef = "ordersTransactionManager")
public class OrdersDataSourceConfiguration {

    @Primary
    @Bean
    @ConfigurationProperties("app.datasource.orders")          // binds url, username, password
    public DataSourceProperties ordersDataSourceProperties() {
        return new DataSourceProperties();
    }

    @Primary
    @Bean
    @ConfigurationProperties("app.datasource.orders.hikari")   // binds pool settings
    public HikariDataSource ordersDataSource(
            @Qualifier("ordersDataSourceProperties") DataSourceProperties dataSourceProperties) {
        return dataSourceProperties.initializeDataSourceBuilder().type(HikariDataSource.class).build();
    }

    @Primary
    @Bean
    public LocalContainerEntityManagerFactoryBean ordersEntityManagerFactory(
            EntityManagerFactoryBuilder entityManagerBuilder,
            @Qualifier("ordersDataSource") DataSource ordersDataSource) {
        return entityManagerBuilder
                .dataSource(ordersDataSource)
                .packages("com.example.orders.entity")         // entities that belong to THIS database
                .persistenceUnit("orders")
                .build();
    }

    @Primary
    @Bean
    public PlatformTransactionManager ordersTransactionManager(
            @Qualifier("ordersEntityManagerFactory") EntityManagerFactory ordersEntityManagerFactory) {
        return new JpaTransactionManager(ordersEntityManagerFactory);
    }
}

// InventoryDataSourceConfiguration: identical shape, but WITHOUT @Primary, using the
// "app.datasource.inventory" prefix, the "com.example.inventory.*" packages and "inventory*" bean names.

@Service
public class StockReservationService {
    // Pick the transaction manager explicitly; the default (@Primary) one would be used otherwise
    @Transactional(transactionManager = "inventoryTransactionManager")
    public void reserveStock(Long productIdentifier, int requestedQuantity) { /* ... */ }
}
  • Plain JDBC: skip JPA and declare a JdbcTemplate per DataSource with @Qualifier.
  • Runtime routing (read replicas, multi-tenant): one logical DataSource extending AbstractRoutingDataSource that picks the target from a thread-bound key in determineCurrentLookupKey().
  • Pitfall: @Transactional covers one transaction manager only, so a write to both databases is not atomic. Use JTA/XA (Atomikos, Narayana), or preferably the saga/outbox patterns (Section 5, Q5).
  • Also configure per database: Flyway/Liquibase migrations, pool names, and health indicators.

Section 3: Testing, Code Quality & Production Readiness

Q1. What is the difference between @Mock and @InjectMocks in Mockito?

@Mock creates a fake implementation of a dependency with stubbed behavior, isolating the class under test from real collaborators. @InjectMocks creates a real instance of the class under test and injects the @Mock fields into it (via constructor, setter, or field), enabling isolated unit tests with no Spring context.

Problem statement: Unit test that an order is confirmed when the inventory repository reports stock, and verify the repository was consulted exactly once.

@ExtendWith(MockitoExtension.class)
class OrderServiceTest {
 
    @Mock
    private InventoryRepository inventoryRepository;   // fake collaborator
 
    @InjectMocks
    private OrderService orderService;                 // real class under test, mocks injected
 
    @Test
    void shouldConfirmOrderWhenStockAvailable() {
        when(inventoryRepository.hasStock("SKU123")).thenReturn(true);
 
        boolean orderConfirmed = orderService.placeOrder("SKU123");
 
        assertTrue(orderConfirmed);
        verify(inventoryRepository, times(1)).hasStock("SKU123");
    }
}

Q2. What is the difference between @BeforeEach and @BeforeAll in JUnit 5? What is TDD?

@BeforeEach runs before every test method, ideal for resetting state and mocks for isolation. @BeforeAll runs once before all tests in the class (it must be static unless you use @TestInstance(PER_CLASS)), suited to expensive one-time setup such as starting an embedded database; @AfterEach/@AfterAll handle teardown.

Test-driven development is the red-green-refactor cycle: write a failing test that defines the desired behavior (red), write the minimal code to pass it (green), then improve the code without changing behavior (refactor). It yields high coverage by construction, drives simpler designs, and provides a refactoring safety net.

Q3. What is your strategy for testing a complex service, and how do you design for observability?

Follow the test pyramid: many fast unit tests with mocked dependencies; fewer integration tests using Testcontainers for realistic database and broker behavior; contract tests (Pact) verifying producer/consumer compatibility; and a small number of end-to-end tests for critical journeys. Test behavior, not implementation details, so tests survive refactoring.

Observability rests on three pillars: structured JSON logs with correlation/trace IDs via MDC; metrics (latency percentiles, error rates, throughput via Micrometer to Prometheus/Grafana, following the RED or USE methodology); and distributed tracing (OpenTelemetry). Define SLOs (p99 latency, an error budget) and alert on user-impacting symptoms rather than raw resource metrics.

Q4. What code-review red flags do you look for as a senior engineer?

  • Mutable shared state accessed without synchronization in concurrent code paths.
  • Catching broad exceptions and swallowing them silently.
  • Business logic embedded in controllers instead of a service layer.
  • N+1 query patterns or unbounded collection loading from the database.
  • Missing timeout, retry, or circuit-breaker configuration on external calls.
  • Tests that assert implementation details instead of observable behavior.

Section 4: Web Services — REST

Q2. What HTTP methods do RESTful services support, and what do safe and idempotent mean?

  • GET — retrieve a representation; safe (no side effects) and idempotent.
  • POST — typically create a resource or trigger a non-idempotent action; calling it twice is expected to create two resources.
  • PUT — replace a resource entirely with the supplied representation (or create it at that client-specified URL); idempotent.
  • PATCH — partial update of only the fields supplied; not necessarily idempotent, though many implementations are designed to be.
  • DELETE — remove a resource; conventionally idempotent (deleting an already-deleted resource shouldn't be treated as a failure).
  • HEAD — like GET but returns headers only, with no body; cheap for checking size or last-modified metadata.
  • OPTIONS — asks which methods a resource supports; browsers use it for the CORS preflight check before a cross-origin request.

Note: PUT vs. PATCH is a common follow-up: PUT requires the complete updated representation, and any omitted field is typically reset or cleared; PATCH sends only the fields that should change and leaves everything else untouched.

Q4. Why can't you send arbitrary data in a web service header?

  • Purpose — headers carry metadata (auth tokens, content type, caching directives, correlation/trace IDs), not business payload; mixing them blurs “how to process this message” and “what it contains.”
  • Size limits — servers, proxies, and load balancers typically cap total header size (commonly 4KB–16KB), so large data risks silent, mysterious request failures; bodies are built for large payloads.
  • Encoding — header values are restricted to a limited (essentially ASCII) character set, making them a poor fit for structured or binary data without awkward Base64 overhead.
  • Caching, logging, and security — headers are far more likely to be logged, cached, or inspected by intermediaries (proxies, API gateways, monitoring), so placing sensitive business data there is a genuine security risk.

Convention in both SOAP and REST: headers for metadata, body for business data.

Q6. How do you test web services?

  • Manual, exploratory testing — Postman (mainly REST/JSON) or SoapUI (built for SOAP, also supports REST) for interactive requests and saved collections.
  • Automated unit tests — test controller/service logic with dependencies mocked; Spring's MockMvc simulates an HTTP request without a running server.
  • Automated integration tests — exercise the real endpoint end to end (routing, serialization, business logic, persistence), typically with a real or embedded test database.
  • Contract testing — tools like Pact let a consumer define the request/response contract it expects and verify the provider satisfies it, catching breaking API changes early.
  • Load/performance testing — JMeter or Gatling simulate many concurrent users to verify response time and error rate under realistic or peak load.

Problem statement: Test a REST endpoint's JSON response without starting a real server.

@WebMvcTest(EmployeeController.class)
public class EmployeeControllerTest {
 
    @Autowired
    private MockMvc mockMvc;
 
    @MockBean
    private EmployeeService employeeService; // dependency mocked out
 
    @Test
    public void shouldReturnEmployeeDetailsAsJson() throws Exception {
        when(employeeService.findById(42L)).thenReturn(new Employee(42L, "Alice"));
 
        mockMvc.perform(get("/api/employees/42"))
               .andExpect(status().isOk())
               .andExpect(jsonPath("$.employeeName").value("Alice"));
    }
}

Q8. How do you send and receive XML in a REST service?

  • Add an XML converter (jackson-dataformat-xml in Spring Boot) and declare media types with consumes / produces; the Accept and Content-Type headers select the format (content negotiation).
  • A single endpoint can serve both JSON and XML.

Problem statement: Accept a customer as XML and respond with XML.

@RestController
@RequestMapping("/customers")
public class CustomerController {

    @PostMapping(
        consumes = MediaType.APPLICATION_XML_VALUE,    // request body is XML
        produces = MediaType.APPLICATION_XML_VALUE)    // response body is XML
    public CustomerDto createCustomer(@RequestBody CustomerDto customerRequest) {
        customerRequest.setCustomerId(UUID.randomUUID().toString());
        return customerRequest;   // converter serializes it back to XML
    }
}

Q9. How do you return the correct HTTP status codes from a Spring REST controller?

Beyond the table in Q7: 405 Method Not Allowed (wrong verb), 415 Unsupported Media Type (bad Content-Type), 422 Unprocessable Entity (valid syntax, failed validation), 409 Conflict (duplicate or version clash). 502/504 usually indicate an upstream or gateway problem, not your own code. Use ResponseEntity or @ResponseStatus to set them explicitly.

Problem statement: Return 201 on create, 200/404 on lookup, and 204 on delete.

@RestController
@RequestMapping("/orders")
public class OrderController {

    @PostMapping
    public ResponseEntity<Order> createOrder(@RequestBody Order newOrder) {
        Order savedOrder = orderService.save(newOrder);
        return ResponseEntity.status(HttpStatus.CREATED).body(savedOrder);        // 201
    }

    @GetMapping("/{orderId}")
    public ResponseEntity<Order> findOrder(@PathVariable long orderId) {
        return orderService.findById(orderId)
                .map(ResponseEntity::ok)                                          // 200
                .orElse(ResponseEntity.status(HttpStatus.NOT_FOUND).build());     // 404
    }

    @DeleteMapping("/{orderId}")
    public ResponseEntity<Void> deleteOrder(@PathVariable long orderId) {
        orderService.deleteById(orderId);
        return ResponseEntity.noContent().build();                                // 204
    }
}

Section 5: Microservices Architecture & Distributed Systems

Q1. How have microservices been used in a project? What are the key concepts and trade-offs?

Microservices structure an application as small, independently deployable services, each owning one well-bounded business capability (Order, Payment, Inventory), with its own codebase, deployment lifecycle, and often its own database, in contrast to a monolith's single unified codebase and deployment unit.

  • Independent deployability — a Payment Service fix doesn't require redeploying everything.
  • Decentralized data — each service owns its data store; others go through its API, avoiding coupling through a shared database.
  • Inter-service communication — synchronous REST/gRPC where an immediate answer is needed, asynchronous messaging (Kafka, RabbitMQ) for decoupled, eventually consistent interactions.
  • API Gateway — a single entry point that routes external requests to the right service, hiding internal topology.
  • Service discovery — Eureka, Consul, or Kubernetes DNS let services find each other's current location as instances come and go.
  • Resilience patterns — the circuit breaker (stop calling a repeatedly failing service so it can recover) and timeouts matter because network calls fail in ways in-process calls never do.
  • Independent scalability — scale just the Search service during a sale, not the whole app.

Note: Balance your answer: microservices are a trade-off, not an unconditional upgrade. They add network latency, partial-failure handling, harder testing and debugging across many services, and operational overhead. Many good systems start as (or stay) a well-structured monolith and migrate only when a concrete pain point, such as independent team release schedules or a component with a very different load profile, justifies the cost.

Q2. How do you decide between synchronous (REST/gRPC) and asynchronous (Kafka/RabbitMQ) communication? MQ vs REST?

Use synchronous calls when the caller genuinely needs the result to proceed (“is this payment authorized?” before showing a success page). gRPC beats REST for internal service-to-service calls needing lower latency and higher throughput (binary protobuf, HTTP/2 multiplexing); REST/JSON stays preferable for public or partner APIs for its ubiquity and easy debugging.

Use asynchronous messaging when the caller needn't block, when producer and consumer availability should be decoupled (a consumer can be down without blocking the producer), when a burst of load should be buffered to protect a slower downstream system, when delivery must be guaranteed even if the receiver is offline, or when one event must fan out to several independent consumers (order placed leads to inventory, billing, analytics, notifications).

// Synchronous: the caller needs this result now
@PostMapping("/orders/{id}/authorize-payment")
public PaymentAuthResponse authorizePayment(@PathVariable String id) {
    return paymentServiceClient.authorize(id);
}
 
// Asynchronous: fire-and-forget, multiple independent downstream consumers
@Transactional
public void placeOrder(OrderRequest orderRequest) {
    Order savedOrder = orderRepository.save(Order.from(orderRequest));
    kafkaTemplate.send("order-events", new OrderPlacedEvent(savedOrder.getId(), savedOrder.getItems()));
    // InventoryService, BillingService, NotificationService each consume independently
}

Trade-off to articulate: synchronous calls create runtime coupling (if Service B is down, A's request fails or hangs; mitigate with circuit breakers and timeouts), while asynchronous calls trade immediate consistency for resilience and scalability, requiring you to design for eventual consistency and for duplicate or out-of-order delivery. Mature systems use both, choosing per interaction.

Note: Watch for the “distributed monolith” anti-pattern: services technically split but chained by synchronous calls (A calls B calls C calls D), which relocates the monolith's coupling into network latency and failure surface. Default to async for anything that isn't a genuine real-time read.

Q3. How do you implement distributed tracing with OpenTelemetry, and why does it matter?

One user request can touch 5–15 services; without tracing, correlating logs during an incident means manually grepping timestamps across systems. OpenTelemetry, the current industry standard, auto-instruments HTTP clients, JDBC, and messaging clients, propagating a trace-id/span-id across service boundaries through the W3C traceparent header so you can view the full request path in Jaeger, Zipkin, or a commercial APM (Datadog, New Relic, Dynatrace).

# application.yml: minimal Spring Boot + OpenTelemetry setup
management:
  tracing:
    sampling:
      probability: 1.0   # 100% in staging; typically 0.05-0.1 in production for high-traffic services
otel:
  exporter:
    otlp:
      endpoint: http://otel-collector:4317
 
@Service
public class OrderService {
    private final Tracer tracer;
 
    public void processOrder(Order order) {
        Span processingSpan = tracer.spanBuilder("processOrder")
                .setAttribute("order.id", order.getId())
                .startSpan();
        try (Scope scope = processingSpan.makeCurrent()) {
            inventoryClient.reserve(order); // child span auto-created if instrumented
            paymentClient.charge(order);
        } finally {
            processingSpan.end();
        }
    }
}

Sample at a lower rate for high-throughput services (storing every trace is costly), but always keep traces for errors and slow requests (tail-based sampling), which are exactly what you need during an incident. Treat observability as a first-class deliverable of every new service, not an afterthought.

Q4. What is the Database-per-Service pattern, and how do you query data spanning services?

Each service owns its schema (ideally its own database instance) and no other service queries it directly; all cross-service access goes through the owning service's API. That gives true encapsulation and independent schema evolution, but a SQL JOIN across service boundaries is impossible. Two solutions, by complexity:

  • API composition — the caller (or an API gateway / BFF) calls the owning services in parallel and joins in application code. Simple, but adds latency and scales poorly for complex multi-entity queries or pagination across joined data.
  • CQRS with a read-optimized materialized view — a read-side service consumes domain events (OrderPlaced, CustomerUpdated) from Kafka and maintains a denormalized view (often Elasticsearch or a reporting database) tailored to the query. Right for frequent, complex, or search-style queries, at the cost of eventual consistency and another pipeline to operate.

Problem statement: Build an order summary that joins Order and Customer data owned by two different services.

public OrderSummary getOrderSummary(String orderId) {
    CompletableFuture<Order> orderFuture =
            CompletableFuture.supplyAsync(() -> orderClient.get(orderId));
    // the customer call depends on the order's customerId, so chain it with thenCompose
    CompletableFuture<Customer> customerFuture = orderFuture.thenCompose(
            order -> CompletableFuture.supplyAsync(() -> customerClient.get(order.getCustomerId())));
    return new OrderSummary(orderFuture.join(), customerFuture.join());
}

Q5. How would you handle distributed transactions across microservices without two-phase commit? Explain Saga and Outbox.

Two-phase commit is generally avoided in microservices: it introduces tight coupling, blocking, and a coordinator that becomes a single point of failure, all at odds with independent scalability and availability. The Saga pattern is the preferred alternative, in two forms:

  • Choreography — each service publishes a domain event (often via Kafka) after its local transaction, and other services react with their own local transactions; on failure, compensating events undo prior steps (a PaymentFailed event triggers an OrderCancelled compensation).
  • Orchestration — a central orchestrator (built with Spring State Machine or a dedicated saga engine) explicitly directs each participant through the sequence and invokes compensating actions on failure.

Because messages may be delivered more than once, every operation must be idempotent (idempotency keys, or checking current state before applying a change). The Outbox pattern complements sagas by writing the event to an outbox table in the same local transaction as the state change, with a separate relay publishing it, guaranteeing that the database update and the event publication happen atomically and avoiding the dual-write inconsistency of naive implementations.

Q6. How does the circuit breaker pattern (Resilience4j) work, and why is it needed?

A circuit breaker monitors calls to a dependency. After a failure threshold is crossed it opens, failing subsequent calls immediately (optionally invoking a fallback) instead of letting them time out slowly, which prevents cascading failures and thread-pool exhaustion. After a wait duration it goes half-open to probe recovery and closes again if the probe succeeds. It contains the blast radius of a struggling downstream service and is often combined with bulkheading (isolated thread pools per dependency).

@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public PaymentResult chargeCustomer(PaymentRequest paymentRequest) {
    return paymentClient.charge(paymentRequest); // the unreliable downstream call
}
 
// invoked while the circuit is open or when the call fails
private PaymentResult paymentFallback(PaymentRequest paymentRequest, Throwable failureCause) {
    return PaymentResult.queuedForRetry(paymentRequest.getOrderId());
}

Q7. How do you approach API versioning for a service with external partner consumers?

Never ship a backward-incompatible change (removing or renaming a field, changing a type or required-ness) silently to an endpoint with external consumers. In order of preference:

  • 1. Additive, backward-compatible changes (new optional fields, never repurpose an existing one) — no versioning needed; this should be the default mode of evolution.
  • 2. URI versioning (/v1/orders, /v2/orders) for genuinely breaking changes — the most explicit and cache-friendly, easiest for partners to understand, at the cost of parallel code paths during a deprecation window.
  • 3. Header-based versioning (Accept: application/vnd.company.orders.v2+json) — clean URLs but harder for partners to test and debug, so used less for external-facing APIs.

Maintain old versions for a defined deprecation window with clear sunset communication, and use contract testing (Pact) to catch breaking changes before they reach consumers.

@RestController
@RequestMapping("/v2/orders")
public class OrderControllerV2 {
    @GetMapping("/{id}")
    public OrderResponseV2 getOrder(@PathVariable String id) {
        return orderService.getOrderV2(id); // new response shape
    }
}
 
@RestController
@RequestMapping("/v1/orders")
@Deprecated
public class OrderControllerV1 {
    @GetMapping("/{id}")
    public OrderResponseV1 getOrder(@PathVariable String id) {
        // adapt the new internal model back to the old contract
        return OrderResponseV1.from(orderService.getOrderV2(id));
    }
}

Q8. How do you manage configuration and secrets across dev/QA/UAT/prod?

Follow the 12-factor principle: config varies by deployment, code does not. Use Spring profiles (application-{profile}.yml) for non-sensitive environment config and a dedicated secrets manager for credentials; never commit secrets to source control or bake environment-specific values into the built artifact. For centralized config across many services use Spring Cloud Config Server (Git-backed) or a cloud-native option (AWS Parameter Store/Secrets Manager, HashiCorp Vault, Azure Key Vault).

# application.yml (defaults)
spring:
  config:
    import: optional:configserver:http://config-server:8888
 
# application-prod.yml
spring:
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}   # injected from a secrets manager, never hardcoded

Note: Vault is a strong choice for banking-grade rotation because it supports dynamic, short-lived credentials (a database password that rotates every few hours). In regulated environments, secret rotation and audit logging of secret access are non-negotiable and far cheaper to design in from day one than to retrofit.
