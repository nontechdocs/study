Section 1: System Design & Architecture

Interview framing for every design question: (1) clarify functional and non-functional requirements first, (2) state scale numbers, (3) sketch the core components, (4) narrate the trade-offs out loud. For lead-level roles, the trade-off reasoning matters more than landing on one “correct” architecture.

Q1. Design a URL shortener (e.g. bit.ly) handling 100M writes/day and 1B reads/day.

Requirements and scale

The read:write ratio is about 10:1, so optimize heavily for read latency and cache hit rate. Codes should be unique and short (6–8 characters), with eventual click analytics. 100M writes/day is roughly 1,150 writes/sec on average (plan for 5–10x peak); 1B reads/day is roughly 11,500 reads/sec on average. A well-cached key-value architecture across a handful of nodes handles this comfortably.

Core design

  • ID generation — avoid a single auto-increment counter (a bottleneck, and predictable). Use a distributed generator (Snowflake-style: timestamp + machine ID + sequence) or pre-allocate ID ranges per app server to avoid per-request coordination. Base62-encode the numeric ID for a compact short code.
  • Storage — a key-value store (DynamoDB/Cassandra) mapping shortCode to longUrl; the access pattern needs no joins, so a KV store beats a relational database.
  • Caching — Redis/Memcached in front of the KV store for hot URLs; with a 10:1 ratio and power-law traffic, a cache easily absorbs 90%+ of reads.
  • Redirect service — a stateless HTTP service issuing 301/302 redirects, scaled horizontally behind a load balancer. 302 preserves per-request click analytics; 301 is cacheable by browsers and CDNs, reducing backend load but losing per-click visibility.
  • Analytics — never write click events synchronously on the read path; publish to Kafka asynchronously and aggregate downstream (data warehouse or a counts table).
  • Custom aliases — check existence in the KV store; on collision, regenerate or reject.

Problem statement: Convert a numeric ID into a compact Base62 short code.

public class ShortCodeGenerator {
    private static final String BASE62_ALPHABET =
            "0123456789abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ";
 
    // Converts a unique numeric ID into a short string, e.g. 125 -> "21"
    public String encodeToBase62(long uniqueIdentifier) {
        if (uniqueIdentifier == 0) {
            return String.valueOf(BASE62_ALPHABET.charAt(0));
        }
        StringBuilder encodedResult = new StringBuilder();
        while (uniqueIdentifier > 0) {
            int remainderIndex = (int) (uniqueIdentifier % 62);
            encodedResult.append(BASE62_ALPHABET.charAt(remainderIndex));
            uniqueIdentifier /= 62;
        }
        return encodedResult.reverse().toString(); // digits were produced least-significant first
    }
}

Note: Narrate trade-offs aloud (301 vs. 302, synchronous vs. asynchronous analytics). That is what separates a lead from an individual-contributor candidate: showing you would make and defend architecture decisions, not just produce a design.

Q2. Design a rate limiter for an API gateway. Compare Token Bucket, Leaky Bucket, Fixed Window, and Sliding Window.

  • Fixed Window Counter — a counter reset each window. Simple, but bursts at window boundaries (0:59 and 1:01) can let through nearly 2x the intended rate.
  • Sliding Window Log — stores a timestamp per request and counts those in the trailing window. Accurate but memory-heavy at scale.
  • Sliding Window Counter — approximates the log with a weighted average of the current and previous fixed windows; a good accuracy/memory trade-off widely used in production.
  • Token Bucket — tokens refill at a fixed rate up to a capacity and each request consumes one. It allows short bursts up to capacity while enforcing a long-term average; the usual default for API gateways because it models real client burst behavior.
  • Leaky Bucket — requests queue and drain at a constant rate; smooths bursts completely but adds queuing latency, so it suits traffic shaping better than rejecting excess client requests.

At scale, back the limiter with Redis so limits hold across gateway instances, using atomic INCR+EXPIRE or a Lua script executed via EVAL to avoid race conditions between replicas. Apply it at the gateway, return HTTP 429 with a Retry-After header, and consider tiered limits (per-user, per-IP, global). In a single JVM, an AtomicLong token count with scheduled refill, or Guava's RateLimiter / Resilience4j, works.

Problem statement: Implement a distributed token-bucket check that is atomic across gateway instances.

public boolean allowRequest(String clientIdentifier, int bucketCapacity, int refillRatePerSecond) {
    String tokenBucketScript = """
        local tokens_key = KEYS[1]
        local timestamp_key = KEYS[2]
        local capacity = tonumber(ARGV[1])
        local refill_rate = tonumber(ARGV[2])
        local now = tonumber(ARGV[3])
        local last_tokens = tonumber(redis.call('get', tokens_key) or capacity)
        local last_refreshed = tonumber(redis.call('get', timestamp_key) or now)
        local elapsed = math.max(0, now - last_refreshed)
        local refilled = math.min(capacity, last_tokens + (elapsed * refill_rate))
        local allowed = refilled >= 1
        local remaining = refilled
        if allowed then remaining = refilled - 1 end
        redis.call('set', tokens_key, remaining)
        redis.call('set', timestamp_key, now)
        return allowed and 1 or 0
        """;
    // executed atomically via EVAL, so concurrent gateway replicas cannot race
    return redisTemplate.execute(
            RedisScript.of(tokenBucketScript, Boolean.class),
            List.of("tokens:" + clientIdentifier, "ts:" + clientIdentifier),
            String.valueOf(bucketCapacity),
            String.valueOf(refillRatePerSecond),
            String.valueOf(System.currentTimeMillis() / 1000));
}

Note: Clarify per-client vs. global limiting up front; a wrong assumption early is a classic cause of expensive rework. Bring it up proactively.

Q3. Design a scalable, reliable notification system (push, email, SMS) with retries.

  • Ingestion API — validates a request and writes it to a durable queue (Kafka). Never process synchronously: providers (APNs, FCM, Twilio, SES) have variable latency and failure rates.
  • Channel-specific consumers — push, email, and SMS consumers subscribe to their own topics and scale independently (SMS volume rarely matches email).
  • Provider abstraction layer — an interface with ordered providers so you can fail over (SES to SendGrid) without touching business logic.
  • Retries — exponential backoff with jitter, a capped retry count, then a dead-letter queue for manual or automated reprocessing; idempotency keys prevent duplicate sends on retry.
  • Delivery tracking — provider webhook callbacks update a status table, exposed for support and debugging.
  • Provider rate limiting — respect third-party quotas (e.g. Twilio's per-second cap) using the token-bucket design above.
public interface NotificationProvider {
    NotificationResult send(NotificationRequest notificationRequest);
}
 
@Service
public class EmailNotificationService {
    private final List<NotificationProvider> orderedProviders; // highest priority first
 
    public NotificationResult sendWithFailover(NotificationRequest notificationRequest) {
        for (NotificationProvider currentProvider : orderedProviders) {
            try {
                return currentProvider.send(notificationRequest);
            } catch (ProviderUnavailableException providerFailure) {
                log.warn("Provider {} failed, trying next",
                        currentProvider.getClass().getSimpleName());
            }
        }
        throw new AllProvidersFailedException(notificationRequest.getId());
    }
}

Delivery guarantee: at-least-once is realistic and acceptable when consumers are idempotent; exactly-once is prohibitively complex for external channels (you can't guarantee a user's phone dedupes an SMS). Lead-level extras: write on-call runbooks for DLQ replay, and make provider failover configuration-driven rather than a code deploy so an on-call engineer can react to an outage immediately.

Q4. What is the CAP theorem, and how does it guide choosing a relational vs. NoSQL store for an order-management service?

During a network partition a distributed system must choose between Consistency (every read sees the latest write) and Availability (every request gets a non-error response, possibly stale). Since partitions are inevitable, the real trade-off is CP vs. AP: CP systems (traditional RDBMS with synchronous replication, ZooKeeper) sacrifice availability to guarantee consistency, suiting financial data; AP systems (Cassandra, DynamoDB) favor availability with eventual consistency, suiting session stores and similar workloads. In practice PACELC is more accurate, since it also covers the latency-vs-consistency trade-off when there is no partition.

For order management: order creation, payment status, and inventory decrement need strong consistency (two customers must not both “successfully” buy the last unit). Choose a relational database (PostgreSQL/MySQL, or distributed SQL such as CockroachDB/YugabyteDB if write scale demands it) with proper isolation and explicit row locking. Adjacent concerns like order history/search or recommendations tolerate eventual consistency, so a NoSQL store (DynamoDB, Cassandra, Elasticsearch) populated via CDC or domain events fits there.

@Transactional(isolation = Isolation.SERIALIZABLE)
public OrderResult placeOrder(OrderRequest orderRequest) {
    // SELECT ... FOR UPDATE: locks the inventory row so two buyers cannot both take the last unit
    Inventory productInventory =
            inventoryRepository.findByIdForUpdate(orderRequest.getProductId());
    if (productInventory.getQuantity() < orderRequest.getQuantity()) {
        throw new InsufficientStockException(orderRequest.getProductId());
    }
    productInventory.decrement(orderRequest.getQuantity());
    inventoryRepository.save(productInventory);
    return orderRepository.save(Order.from(orderRequest));
}

Note: The right answer is rarely “one database for everything.” Identify which sub-domains truly need strong consistency versus which tolerate eventual consistency, and architect polyglot persistence accordingly, while being honest about the added operational complexity.

Q5. Design an idempotent payment API that prevents double-charging on client retries.

The client generates a unique idempotency key (a UUID) per logical payment attempt and sends it in a header. Before attempting the charge, the server persists a mapping of key to result, using a database unique constraint so concurrent duplicate requests are rejected atomically instead of relying on an application-level check-then-act (which has a race condition). If the key already exists: return the stored response when complete, or a 409 Conflict while the first attempt is still in progress.

@PostMapping("/payments")
public ResponseEntity<PaymentResponse> processPayment(
        @RequestHeader("Idempotency-Key") String idempotencyKey,
        @RequestBody PaymentRequest paymentRequest) {
 
    Optional<IdempotencyRecord> existingRecord = idempotencyRepository.findByKey(idempotencyKey);
    if (existingRecord.isPresent()) {
        IdempotencyRecord previousAttempt = existingRecord.get();
        if (previousAttempt.getStatus() == Status.IN_PROGRESS) {
            // first attempt still running: avoid double execution mid-flight
            return ResponseEntity.status(HttpStatus.CONFLICT).body(PaymentResponse.processing());
        }
        return ResponseEntity.ok(previousAttempt.getCachedResponse()); // safe to replay
    }
 
    try {
        // DB unique constraint makes this insert atomic under concurrent duplicates
        idempotencyRepository.insertInProgress(idempotencyKey);
    } catch (DuplicateKeyException concurrentDuplicate) {
        return ResponseEntity.status(HttpStatus.CONFLICT).body(PaymentResponse.processing());
    }
 
    PaymentResult paymentResult = paymentGateway.charge(paymentRequest);
    idempotencyRepository.completeWithResult(idempotencyKey, paymentResult);
    return ResponseEntity.ok(PaymentResponse.from(paymentResult));
}

Production hardening

  • Expire keys (e.g. after 24 hours) to bound storage growth.
  • Scope the unique constraint to (idempotencyKey, merchantId).
  • Forward the same key to the downstream payment gateway (Stripe, Razorpay, core banking) so that call is itself idempotent, since your service can also crash mid-call and retry.

Note: Expect this banking follow-up: “what if your service crashes after charging the gateway but before writing the result?” The answer is a reconciliation job that periodically queries the gateway for the true status of any IN_PROGRESS record past a timeout. Always mention this safety net; it shows you design for failure modes, not just the happy path.

Q6. Explain the Saga pattern. Choreography vs. orchestration?

Two-phase commit doesn't scale across independently owned, independently deployed services (blocking, tight coupling, poor availability during a partition). A Saga breaks a distributed transaction into local transactions, each with a compensating transaction to undo it if a later step fails. It trades immediate consistency for eventual consistency and requires idempotent, compensable operations at every step; the Outbox pattern (Part 5, Section 5) keeps state changes and event publication atomic.

  • Choreography — each service publishes domain events and the next reacts (OrderCreated, then StockReserved, PaymentCompleted, OrderCompleted). Fully decoupled with no single point of failure, but hard to trace the overall flow (“what state is order #123 in?” means stitching events across services) and cyclic dependencies can creep in as steps grow.
  • Orchestration — a central orchestrator calls each service and tracks state: a clear, centralized, observable state machine, preferable beyond 2–3 steps or when the business needs auditability. Costs: the orchestrator must itself be highly available and risks becoming a “god service” if not scoped carefully.
public class OrderSagaOrchestrator {
    public void execute(OrderSagaContext sagaContext) {
        try {
            inventoryClient.reserve(sagaContext.getOrderId(), sagaContext.getItems());
            paymentClient.charge(sagaContext.getOrderId(), sagaContext.getAmount());
            shippingClient.schedule(sagaContext.getOrderId());
            sagaContext.markCompleted();
        } catch (PaymentFailedException paymentFailure) {
            inventoryClient.release(sagaContext.getOrderId()); // compensating transaction
            sagaContext.markFailed("Payment failed: " + paymentFailure.getMessage());
        } catch (ShippingUnavailableException shippingFailure) {
            paymentClient.refund(sagaContext.getOrderId());    // compensate in reverse order
            inventoryClient.release(sagaContext.getOrderId());
            sagaContext.markFailed("Shipping unavailable: " + shippingFailure.getMessage());
        }
    }
}

Note: In banking, orchestration's auditability usually wins outright: regulators and auditors want a clear, queryable record of what state a transaction was in at time T, which choreographed event trails make much harder to reconstruct. Choose orchestration for complex, business-critical workflows needing visibility, and choreography for simpler, high-throughput event flows.

Q7. Design a system for 10,000 concurrent WebSocket connections delivering real-time stock prices.

A single Tomcat or Netty instance using NIO can handle tens of thousands of concurrent WebSocket connections, because each connection is a lightweight event-loop registration rather than a dedicated OS thread (the key contrast with old thread-per-connection servlet models).

  • WebSocket gateway — Spring WebFlux + Netty (or raw Netty), stateless with respect to business logic, holding only the open connection and a subscription list (which symbols each client wants).
  • Price feed ingestion — the market data feed (or internal price engine) publishes updates to Kafka, partitioned by symbol for parallelism.
  • Fan-out — each gateway instance consumes relevant partitions and pushes to its locally subscribed connections; use a pub/sub layer (Redis Pub/Sub or Kafka directly) so a client on gateway A still receives symbols ingested by gateway B.
  • Scaling out — multiple gateway instances behind a load balancer with session affinity (WebSockets are stateful connections); Kafka consumer groups ensure each partition is processed once.
  • Backpressure — slow clients must not block the fan-out loop: use bounded per-session send queues and drop or coalesce stale ticks for a lagging client.
@Component
public class PriceUpdateHandler extends TextWebSocketHandler {
    // symbol -> set of sessions subscribed to it
    private final Map<String, Set<WebSocketSession>> subscriptionsBySymbol = new ConcurrentHashMap<>();
 
    @Override
    public void handleTextMessage(WebSocketSession clientSession, TextMessage subscribeMessage) {
        String requestedSymbol = subscribeMessage.getPayload(); // client subscribes to a symbol
        subscriptionsBySymbol
                .computeIfAbsent(requestedSymbol, symbol -> ConcurrentHashMap.newKeySet())
                .add(clientSession);
    }
 
    @KafkaListener(topics = "price-updates")
    public void onPriceUpdate(PriceUpdate priceUpdate) {
        Set<WebSocketSession> subscribedSessions =
                subscriptionsBySymbol.getOrDefault(priceUpdate.getSymbol(), Set.of());
        String jsonPayload = toJson(priceUpdate);
        subscribedSessions.parallelStream().forEach(session -> sendSafely(session, jsonPayload));
    }
}

Note: Push the team toward “coalesce, don't queue indefinitely” for real-time feeds: a client only cares about the latest price, so an unbounded backlog is waste and a memory-leak risk under a slow client. Catch this in design review before it becomes an incident.

Q8. How do you decide between horizontal and vertical scaling for a legacy monolith under load?

Vertical scaling (scale up: more CPU/RAM/disk) is simple, needs no code changes, but has a hard ceiling and a single point of failure. Horizontal scaling (scale out: more instances behind a load balancer) is effectively unbounded and improves fault tolerance, but requires the application to be stateless or to externalize state, often meaning re-architecture for a monolith holding session state in memory.

Decision framework for a legacy monolith:

  • 1. Buy time — scale vertically immediately if under acute load; it's a same-day mitigation while a proper fix is planned.
  • 2. Audit stateful blockers — in-memory session state, local file caches, and in-JVM schedulers (which would run duplicated across instances). Externalize them first: a Redis session store, shared object storage, a distributed scheduler (Quartz with DB locking) or a dedicated job service.
  • 3. Externalize, then scale out — once stateless, add a load balancer with health checks and autoscaling on CPU or request-latency metrics.
  • 4. Check the database — scaling app servers is pointless if the single database is the real constraint; read replicas, connection-pool limits (HikariCP sizing), and query optimization often matter more than the app tier.

Note: Resist scaling out blindly under pressure: teams that horizontally scale a monolith with in-memory session-affinity issues end up with intermittent “logged out” bugs. Audit statefulness first; a lead's job is to slow the team down just enough to avoid that trap.

Q9. Implement the circuit breaker pattern with Resilience4j for an unreliable downstream API.

A circuit breaker stops a service from repeatedly calling an already failing dependency, which would waste threads and connections and cascade upstream (a thundering herd against a struggling service). States: Closed (normal; failures counted), Open (calls fail fast after the failure threshold is breached), Half-Open (after a wait, a limited number of trial calls test recovery). The basic mechanics are in Part 5, Section 5; here is a fuller configuration.

@CircuitBreaker(name = "inventoryService", fallbackMethod = "fallbackInventoryCheck")
@Retry(name = "inventoryService")
@TimeLimiter(name = "inventoryService")
public CompletableFuture<InventoryStatus> checkInventory(String productId) {
    return CompletableFuture.supplyAsync(() -> inventoryClient.check(productId));
}
 
public CompletableFuture<InventoryStatus> fallbackInventoryCheck(String productId, Throwable failureCause) {
    log.warn("Inventory check failed for {}, using cached/default status", productId, failureCause);
    return CompletableFuture.completedFuture(InventoryStatus.unknown());
}
 
# application.yml
resilience4j:
  circuitbreaker:
    instances:
      inventoryService:
        sliding-window-size: 20
        failure-rate-threshold: 50
        wait-duration-in-open-state: 10s
        permitted-number-of-calls-in-half-open-state: 5

Design decisions to discuss

  • Annotation order matters: TimeLimiter wraps the async call, with CircuitBreaker and Retry composed around it.
  • Retries need backoff and must not be layered naively on a circuit breaker: retrying against an already open circuit should fail fast, not hammer a dead service.
  • Fallbacks should be business-appropriate (last-known-good cached value, a degraded feature, or an explicit error), not a silent generic default that masks a real outage.

Note: Resilience patterns are cheap to add but easy to misconfigure (wrong thresholds cause flapping or mask real outages). Insist on chaos/failure testing, deliberately killing the downstream in staging, before trusting the configuration in production.

Q10. Design a distributed caching strategy for an e-commerce product catalog. How do you handle invalidation?

Use cache-aside (lazy loading) for a read-heavy catalog: on a miss, read the database, populate the cache, and return. On writes, update the database first, then invalidate (don't update) the cache entry; invalidation is simpler and safer than write-through updating, which risks stale data if the cache step fails independently of the database write.

public Product getProduct(String productId) {
    String cacheKey = "product:" + productId;
    Product cachedProduct = redisTemplate.opsForValue().get(cacheKey);
    if (cachedProduct != null) {
        return cachedProduct; // cache hit
    }
    Product databaseProduct = productRepository.findById(productId)
            .orElseThrow(() -> new ProductNotFoundException(productId));
    // TTL is a safety net: even buggy invalidation self-heals within a bounded time
    redisTemplate.opsForValue().set(cacheKey, databaseProduct, Duration.ofMinutes(30));
    return databaseProduct;
}
 
@Transactional
public void updateProduct(Product updatedProduct) {
    productRepository.save(updatedProduct);
    redisTemplate.delete("product:" + updatedProduct.getId()); // invalidate, don't update
}

Hard cases

  • Cache stampede — many requests miss at once on a hot, just-expired key. Use a short-lived lock/mutex or request coalescing so only one thread repopulates while others wait briefly.
  • Stale reads across instances — if instances also keep a local in-process cache, a write on instance A must invalidate instance B's copy: broadcast via a Redis Pub/Sub channel, or avoid local caching for frequently updated entities.
  • Always set a TTL, since even correct invalidation logic can have bugs or race conditions.

Note: Cache-invalidation bugs are timing-dependent and hard to reproduce. Mandate cache hit/miss metrics and stale-data alerting (periodically compare a sampled cache value to the database) so problems surface through monitoring rather than customer complaints.

Q12. Design a real-time dashboard that shows the top 10 players in a game.

  • Ingest: game servers publish score events to Kafka (partitioned by player id).
  • Store: a Redis sorted set (ZADD/ZINCRBY) keeps players ordered by score; ZREVRANGE leaderboard 0 9 returns the top 10 in O(log n + 10).
  • Deliver: push updates over WebSocket/SSE, throttled (for example once per second), with a short cache for polling clients.
  • Scale: shard leaderboards by game or region, keep durable scores in a database, and rebuild Redis from it on failure.

Problem statement: Maintain a top-N leaderboard in memory using a bounded min-heap.

public class LeaderboardTracker {
    private final int leaderboardSize;
    private final PriorityQueue<PlayerScore> minimumHeap =
            new PriorityQueue<>(Comparator.comparingInt(PlayerScore::scoreValue));

    public record PlayerScore(String playerName, int scoreValue) { }

    public LeaderboardTracker(int leaderboardSize) {
        this.leaderboardSize = leaderboardSize;
    }

    public void recordScore(PlayerScore newScore) {
        minimumHeap.offer(newScore);
        if (minimumHeap.size() > leaderboardSize) {
            minimumHeap.poll();            // drop the lowest score, keep top N
        }
    }

    public List<PlayerScore> currentTopPlayers() {
        List<PlayerScore> rankedPlayers = new ArrayList<>(minimumHeap);
        rankedPlayers.sort(Comparator.comparingInt(PlayerScore::scoreValue).reversed());
        return rankedPlayers;
    }
}

Q13. What are the alternatives to a database, and how would you compute over 1 billion records?

  • Alternatives: in-memory cache (Redis), search engine (Elasticsearch), key-value or document store, flat files / object storage (S3) with Parquet, data warehouse.
  • 1 billion records: do not load them into one JVM. Use divide and conquer: partition the data, compute partial results in parallel, then merge (MapReduce idea).
  • Tools: Spark/Flink/Hadoop for batch, Kafka Streams for streaming, columnar formats for scans, pre-aggregation (rollups), and approximate algorithms (HyperLogLog, Count-Min Sketch) when exactness is not needed.
  • On a single machine: stream the file line by line (never hold everything in memory), use external sort, and chunk with a parallel stream per partition.

Arrays, Strings & Hashing

Q1. Two Sum

Problem statement: Given an array of integers and a target, return the indices of the two numbers that add up to the target.

Approach: store each number's value and index in a HashMap as you iterate; for each element, check whether (target minus current value) is already in the map. This is O(n) instead of the brute-force O(n²).

public int[] findTwoSumIndices(int[] numbers, int targetSum) {
    Map<Integer, Integer> valueToIndex = new HashMap<>();
    for (int currentIndex = 0; currentIndex < numbers.length; currentIndex++) {
        int neededComplement = targetSum - numbers[currentIndex];
        if (valueToIndex.containsKey(neededComplement)) {
            // the complement was seen earlier, so we found the pair
            return new int[] { valueToIndex.get(neededComplement), currentIndex };
        }
        valueToIndex.put(numbers[currentIndex], currentIndex);
    }
    throw new IllegalArgumentException("No two sum solution");
}

Complexity: time O(n), space O(n).

Q2. Reverse Words in a String

Problem statement: Reverse the order of the words in a sentence, collapsing any extra whitespace.

Approach: split on a whitespace regex that handles multiple spaces, then rebuild the words in reverse order.

public String reverseWordOrder(String sentence) {
    String[] wordArray = sentence.trim().split("\\s+"); // handles runs of spaces
    StringBuilder reversedSentence = new StringBuilder();
    for (int wordIndex = wordArray.length - 1; wordIndex >= 0; wordIndex--) {
        reversedSentence.append(wordArray[wordIndex]);
        if (wordIndex != 0) {
            reversedSentence.append(" ");
        }
    }
    return reversedSentence.toString();
}

Complexity: time O(n), space O(n).

Q3. First Unique Character in a String

Problem statement: Return the index of the first character that does not repeat, or -1 if none.

Approach: count each character's frequency in one pass, then scan the string again and return the first index whose count is 1.

public int findFirstUniqueCharacter(String inputText) {
    int[] characterCounts = new int[256]; // fixed-size table covers extended ASCII
    for (char currentCharacter : inputText.toCharArray()) {
        characterCounts[currentCharacter]++;
    }
    for (int position = 0; position < inputText.length(); position++) {
        if (characterCounts[inputText.charAt(position)] == 1) {
            return position;
        }
    }
    return -1;
}

Complexity: time O(n), space O(1) (fixed-size array).

Q4. Majority Element (Boyer–Moore Voting)

Problem statement: In an array where one element appears more than n/2 times, find that element.

Approach: keep a candidate and a count. When the count is 0, adopt the current element as candidate; increment the count on a match, decrement otherwise. Because the majority element occurs more than half the time, it survives as the final candidate.

public int findMajorityElement(int[] numbers) {
    int voteCount = 0;
    int candidateValue = 0;
    for (int currentNumber : numbers) {
        if (voteCount == 0) {
            candidateValue = currentNumber; // adopt a new candidate when votes cancel out
        }
        voteCount += (currentNumber == candidateValue) ? 1 : -1;
    }
    return candidateValue;
}

Complexity: time O(n), space O(1).

Q5. Valid Anagram

Problem statement: Determine whether two strings contain the same characters with the same frequencies.

Approach: differing lengths can't be anagrams. Otherwise increment counts from the first string and decrement from the second; all counts must end at zero.

public boolean areAnagrams(String firstText, String secondText) {
    if (firstText.length() != secondText.length()) {
        return false;
    }
    int[] letterBalance = new int[26]; // lowercase letters only
    for (int position = 0; position < firstText.length(); position++) {
        letterBalance[firstText.charAt(position) - 'a']++;
        letterBalance[secondText.charAt(position) - 'a']--;
    }
    for (int balance : letterBalance) {
        if (balance != 0) {
            return false;
        }
    }
    return true;
}

Complexity: time O(n), space O(1).

Q6. Group Anagrams

Problem statement: Group an array of strings so that anagrams are together.

Approach: compute a canonical key for each string (its characters sorted); anagrams share the same key, so group them in a HashMap keyed by that form.

public List<List<String>> groupAnagramWords(String[] wordArray) {
    Map<String, List<String>> wordsByCanonicalKey = new HashMap<>();
    for (String currentWord : wordArray) {
        char[] sortedLetters = currentWord.toCharArray();
        Arrays.sort(sortedLetters);
        String canonicalKey = new String(sortedLetters); // identical for all anagrams
        wordsByCanonicalKey.computeIfAbsent(canonicalKey, key -> new ArrayList<>()).add(currentWord);
    }
    return new ArrayList<>(wordsByCanonicalKey.values());
}

Complexity: time O(n · k log k) where k is the average word length; space O(n · k).

Q7. Top K Frequent Elements

Problem statement: Return the k most frequent elements of an integer array.

Approach: count frequencies in a HashMap, then keep a min-heap of size k ordered by frequency, evicting the least frequent whenever the heap exceeds k.

public int[] findTopKFrequent(int[] numbers, int topCount) {
    Map<Integer, Integer> frequencyByValue = new HashMap<>();
    for (int currentNumber : numbers) {
        frequencyByValue.merge(currentNumber, 1, Integer::sum);
    }
    // min-heap by frequency: the root is always the least frequent of the current top-k
    PriorityQueue<Integer> frequencyHeap =
            new PriorityQueue<>((first, second) -> frequencyByValue.get(first) - frequencyByValue.get(second));
    for (int distinctValue : frequencyByValue.keySet()) {
        frequencyHeap.offer(distinctValue);
        if (frequencyHeap.size() > topCount) {
            frequencyHeap.poll(); // evict the least frequent
        }
    }
    int[] topElements = new int[topCount];
    for (int position = topCount - 1; position >= 0; position--) {
        topElements[position] = frequencyHeap.poll();
    }
    return topElements;
}

Complexity: time O(n log k), space O(n).

Q8. Valid Palindrome

Problem statement: Decide whether a string is a palindrome after removing non-alphanumeric characters and ignoring case.

Approach: two pointers from both ends, skipping non-alphanumeric characters, comparing lowercase characters, moving inward; any mismatch means not a palindrome.

public boolean isPalindromeIgnoringSymbols(String inputText) {
    int leftPointer = 0;
    int rightPointer = inputText.length() - 1;
    while (leftPointer < rightPointer) {
        while (leftPointer < rightPointer && !Character.isLetterOrDigit(inputText.charAt(leftPointer))) {
            leftPointer++;
        }
        while (leftPointer < rightPointer && !Character.isLetterOrDigit(inputText.charAt(rightPointer))) {
            rightPointer--;
        }
        if (Character.toLowerCase(inputText.charAt(leftPointer))
                != Character.toLowerCase(inputText.charAt(rightPointer))) {
            return false;
        }
        leftPointer++;
        rightPointer--;
    }
    return true;
}

Complexity: time O(n), space O(1).

Q9. Longest Substring Without Repeating Characters (sliding window)

Problem statement: Find the length of the longest substring with no repeated characters.

Approach: a sliding window with two pointers and a map of each character's last-seen index; when a repeat falls inside the window, jump the left edge just past its previous occurrence.

public int lengthOfLongestUniqueSubstring(String inputText) {
    Map<Character, Integer> lastSeenIndex = new HashMap<>();
    int longestLength = 0;
    int windowStart = 0;
    for (int windowEnd = 0; windowEnd < inputText.length(); windowEnd++) {
        char currentCharacter = inputText.charAt(windowEnd);
        if (lastSeenIndex.containsKey(currentCharacter)
                && lastSeenIndex.get(currentCharacter) >= windowStart) {
            windowStart = lastSeenIndex.get(currentCharacter) + 1; // shrink past the duplicate
        }
        lastSeenIndex.put(currentCharacter, windowEnd);
        longestLength = Math.max(longestLength, windowEnd - windowStart + 1);
    }
    return longestLength;
}

Complexity: time O(n), space O(min(n, alphabet size)).

Q10. Sliding Window Maximum

Problem statement: Given an array and window size k, return the maximum of every window of size k as it slides across.

Approach: keep a deque of indices whose values are in decreasing order; the front is always the current window's maximum.

public int[] findSlidingWindowMaximums(int[] numbers, int windowSize) {
    Deque<Integer> candidateIndices = new ArrayDeque<>(); // values decrease from front to back
    int[] windowMaximums = new int[numbers.length - windowSize + 1];
    for (int currentIndex = 0; currentIndex < numbers.length; currentIndex++) {
        // drop the front index if it has slid out of the window
        while (!candidateIndices.isEmpty() && candidateIndices.peekFirst() <= currentIndex - windowSize) {
            candidateIndices.pollFirst();
        }
        // drop smaller values from the back: they can never be a maximum again
        while (!candidateIndices.isEmpty()
                && numbers[candidateIndices.peekLast()] < numbers[currentIndex]) {
            candidateIndices.pollLast();
        }
        candidateIndices.offerLast(currentIndex);
        if (currentIndex >= windowSize - 1) {
            windowMaximums[currentIndex - windowSize + 1] = numbers[candidateIndices.peekFirst()];
        }
    }
    return windowMaximums;
}

Complexity: time O(n), space O(k).

Q11. Longest Palindromic Substring (expand around center)

Problem statement: Return the longest palindromic substring of a given string.

Approach: for each index, expand outward while characters match, once for odd-length centers and once for even-length ones, tracking the best span.

public String findLongestPalindrome(String inputText) {
    if (inputText == null || inputText.length() < 1) {
        return "";
    }
    int bestStart = 0;
    int bestEnd = 0;
    for (int centerIndex = 0; centerIndex < inputText.length(); centerIndex++) {
        int oddLength = expandAroundCenter(inputText, centerIndex, centerIndex);      // single-char center
        int evenLength = expandAroundCenter(inputText, centerIndex, centerIndex + 1); // between two chars
        int longerLength = Math.max(oddLength, evenLength);
        if (longerLength > bestEnd - bestStart + 1) {
            bestStart = centerIndex - (longerLength - 1) / 2;
            bestEnd = centerIndex + longerLength / 2;
        }
    }
    return inputText.substring(bestStart, bestEnd + 1);
}
 
private int expandAroundCenter(String inputText, int leftEdge, int rightEdge) {
    while (leftEdge >= 0 && rightEdge < inputText.length()
            && inputText.charAt(leftEdge) == inputText.charAt(rightEdge)) {
        leftEdge--;
        rightEdge++;
    }
    return rightEdge - leftEdge - 1; // length of the palindrome found
}

Complexity: time O(n²), space O(1).

Q12. Maximum Subarray (Kadane's Algorithm)

Problem statement: Find the contiguous subarray with the largest sum and return that sum.

Approach: track the best sum ending at the current index and the best overall; at each element decide whether to extend the previous subarray or start fresh, whichever gives the larger sum.

public int findMaximumSubarraySum(int[] numbers) {
    int sumEndingHere = numbers[0];
    int bestSumOverall = numbers[0];
    for (int position = 1; position < numbers.length; position++) {
        // extend the running subarray, or restart at the current element
        sumEndingHere = Math.max(numbers[position], sumEndingHere + numbers[position]);
        bestSumOverall = Math.max(bestSumOverall, sumEndingHere);
    }
    return bestSumOverall;
}

Complexity: time O(n), space O(1).

Q13. Best Time to Buy and Sell Stock

Problem statement: Maximize profit from one buy followed by a later sell, given daily prices.

Approach (greedy): track the minimum price so far and the best profit if selling at each day's price.

public int findMaximumProfit(int[] dailyPrices) {
    int lowestPriceSoFar = Integer.MAX_VALUE;
    int bestProfit = 0;
    for (int currentPrice : dailyPrices) {
        lowestPriceSoFar = Math.min(lowestPriceSoFar, currentPrice);
        bestProfit = Math.max(bestProfit, currentPrice - lowestPriceSoFar);
    }
    return bestProfit;
}

Complexity: time O(n), space O(1).

Q14. Merge Intervals

Problem statement: Merge all overlapping intervals in a collection.

Approach: sort by start time; extend the last merged interval when the next one overlaps, otherwise begin a new interval.

public int[][] mergeOverlappingIntervals(int[][] intervals) {
    Arrays.sort(intervals, (first, second) -> first[0] - second[0]); // sort by start time
    List<int[]> mergedIntervals = new ArrayList<>();
    for (int[] currentInterval : intervals) {
        int lastMergedIndex = mergedIntervals.size() - 1;
        if (mergedIntervals.isEmpty() || mergedIntervals.get(lastMergedIndex)[1] < currentInterval[0]) {
            mergedIntervals.add(currentInterval); // no overlap: start a new interval
        } else {
            // overlap: extend the end of the last merged interval
            mergedIntervals.get(lastMergedIndex)[1] =
                    Math.max(mergedIntervals.get(lastMergedIndex)[1], currentInterval[1]);
        }
    }
    return mergedIntervals.toArray(new int[mergedIntervals.size()][]);
}

Complexity: time O(n log n), space O(n).

Q15. Trapping Rain Water

Problem statement: Given elevation heights, compute the total rainwater trapped between them.

Approach: two pointers from both ends, tracking the running maximum on each side; always advance the side with the smaller maximum, since water there is bounded by its own maximum.

public int computeTrappedWater(int[] elevationHeights) {
    int leftPointer = 0;
    int rightPointer = elevationHeights.length - 1;
    int leftMaximum = 0;
    int rightMaximum = 0;
    int totalWater = 0;
    while (leftPointer < rightPointer) {
        if (elevationHeights[leftPointer] < elevationHeights[rightPointer]) {
            leftMaximum = Math.max(leftMaximum, elevationHeights[leftPointer]);
            totalWater += leftMaximum - elevationHeights[leftPointer]; // bounded by leftMaximum
            leftPointer++;
        } else {
            rightMaximum = Math.max(rightMaximum, elevationHeights[rightPointer]);
            totalWater += rightMaximum - elevationHeights[rightPointer]; // bounded by rightMaximum
            rightPointer--;
        }
    }
    return totalWater;
}

Complexity: time O(n), space O(1).

Linked Lists, Stacks & Searching

Q16. Reverse a Linked List

Problem statement: Reverse a singly linked list in place.

Approach: walk the list keeping the previous node; at each step point the current node's next at the previous node, then advance both.

public ListNode reverseLinkedList(ListNode headNode) {
    ListNode previousNode = null;
    ListNode currentNode = headNode;
    while (currentNode != null) {
        ListNode nextNode = currentNode.next; // remember the rest before overwriting the link
        currentNode.next = previousNode;      // reverse this node's pointer
        previousNode = currentNode;
        currentNode = nextNode;
    }
    return previousNode; // the old tail is the new head
}

Complexity: time O(n), space O(1).

Q17. Detect a Cycle in a Linked List (Floyd's algorithm)

Problem statement: Determine whether a linked list contains a cycle.

Approach: move a slow pointer one step and a fast pointer two steps; if they ever meet there is a cycle, and if fast reaches null there is none.

public boolean hasCycle(ListNode headNode) {
    ListNode slowPointer = headNode;
    ListNode fastPointer = headNode;
    while (fastPointer != null && fastPointer.next != null) {
        slowPointer = slowPointer.next;          // one step
        fastPointer = fastPointer.next.next;     // two steps
        if (slowPointer == fastPointer) {
            return true; // the fast pointer lapped the slow one
        }
    }
    return false;
}

Complexity: time O(n), space O(1).

Q18. Valid Parentheses

Problem statement: Check that a string of ( ) [ ] { } brackets is balanced. (A longer, object-oriented version with tests is in Part 3, Section 4.)

Approach: push opening brackets on a stack; on a closing bracket, the top of the stack must be its matching opener.

public boolean areBracketsValid(String bracketText) {
    Deque<Character> openBracketStack = new ArrayDeque<>();
    Map<Character, Character> closingToOpening = Map.of(')', '(', ']', '[', '}', '{');
    for (char currentCharacter : bracketText.toCharArray()) {
        if (closingToOpening.containsValue(currentCharacter)) {
            openBracketStack.push(currentCharacter); // opening bracket
        } else {
            if (openBracketStack.isEmpty()
                    || openBracketStack.pop() != closingToOpening.get(currentCharacter)) {
                return false; // nothing to match, or the wrong opener
            }
        }
    }
    return openBracketStack.isEmpty(); // leftover openers mean unbalanced
}

Complexity: time O(n), space O(n).

Q19. Binary Search

Problem statement: In a sorted array, return the index of a target, or -1 if absent.

Approach: keep low/high bounds, compare the middle element to the target, and halve the range each iteration.

public int binarySearchIndex(int[] sortedNumbers, int targetValue) {
    int lowIndex = 0;
    int highIndex = sortedNumbers.length - 1;
    while (lowIndex <= highIndex) {
        int middleIndex = lowIndex + (highIndex - lowIndex) / 2; // avoids int overflow of (low + high)
        if (sortedNumbers[middleIndex] == targetValue) {
            return middleIndex;
        }
        if (sortedNumbers[middleIndex] < targetValue) {
            lowIndex = middleIndex + 1;
        } else {
            highIndex = middleIndex - 1;
        }
    }
    return -1;
}

Complexity: time O(log n), space O(1).

Backtracking & Dynamic Programming

Q20. Permutations

Problem statement: Return all permutations of a list of distinct integers.

Approach: backtracking; build a partial permutation, try every unused number at each step, recurse, then remove the number to try the next option.

public List<List<Integer>> generatePermutations(int[] numbers) {
    List<List<Integer>> allPermutations = new ArrayList<>();
    buildPermutations(allPermutations, new ArrayList<>(), numbers);
    return allPermutations;
}
 
private void buildPermutations(List<List<Integer>> allPermutations,
                               List<Integer> currentPermutation, int[] numbers) {
    if (currentPermutation.size() == numbers.length) {
        allPermutations.add(new ArrayList<>(currentPermutation)); // snapshot a complete permutation
        return;
    }
    for (int candidateNumber : numbers) {
        if (currentPermutation.contains(candidateNumber)) {
            continue; // already used in this branch
        }
        currentPermutation.add(candidateNumber);                              // choose
        buildPermutations(allPermutations, currentPermutation, numbers);      // explore
        currentPermutation.remove(currentPermutation.size() - 1);             // undo (backtrack)
    }
}

Complexity: time O(n · n!), space O(n) recursion depth plus output.

Q21. Combination Sum II

Problem statement: Find all unique combinations, from a list that may contain duplicates, that sum to a target, using each number at most once.

Approach: sort first, then backtrack while skipping same-valued siblings at the same recursion level to avoid duplicate combinations.

public List<List<Integer>> findCombinationSum(int[] candidateNumbers, int targetSum) {
    Arrays.sort(candidateNumbers); // sorting lets us skip duplicates and stop early
    List<List<Integer>> validCombinations = new ArrayList<>();
    searchCombinations(candidateNumbers, targetSum, 0, new ArrayList<>(), validCombinations);
    return validCombinations;
}
 
private void searchCombinations(int[] candidateNumbers, int remainingSum, int startIndex,
                                List<Integer> currentCombination, List<List<Integer>> validCombinations) {
    if (remainingSum == 0) {
        validCombinations.add(new ArrayList<>(currentCombination));
        return;
    }
    for (int index = startIndex; index < candidateNumbers.length; index++) {
        if (index > startIndex && candidateNumbers[index] == candidateNumbers[index - 1]) {
            continue; // skip a duplicate value at the same level
        }
        if (candidateNumbers[index] > remainingSum) {
            break; // sorted, so no later number can fit either
        }
        currentCombination.add(candidateNumbers[index]);
        searchCombinations(candidateNumbers, remainingSum - candidateNumbers[index],
                index + 1, currentCombination, validCombinations); // index+1: use each number once
        currentCombination.remove(currentCombination.size() - 1);
    }
}

Complexity: time O(2ⁿ) worst case, space O(n).

Q22. Edit Distance (dynamic programming)

Problem statement: Find the minimum number of insertions, deletions, or substitutions needed to convert one string into another.

Approach: build a table where entry [i][j] is the edit distance between the first i characters of one word and the first j of the other. A match reuses the diagonal; a mismatch costs 1 plus the minimum of insert, delete, or replace.

public int computeEditDistance(String sourceWord, String targetWord) {
    int sourceLength = sourceWord.length();
    int targetLength = targetWord.length();
    int[][] distanceTable = new int[sourceLength + 1][targetLength + 1];
    for (int row = 0; row <= sourceLength; row++) {
        distanceTable[row][0] = row;      // delete every source character
    }
    for (int column = 0; column <= targetLength; column++) {
        distanceTable[0][column] = column; // insert every target character
    }
    for (int row = 1; row <= sourceLength; row++) {
        for (int column = 1; column <= targetLength; column++) {
            if (sourceWord.charAt(row - 1) == targetWord.charAt(column - 1)) {
                distanceTable[row][column] = distanceTable[row - 1][column - 1]; // characters match
            } else {
                distanceTable[row][column] = 1 + Math.min(
                        distanceTable[row - 1][column - 1],            // replace
                        Math.min(distanceTable[row - 1][column],       // delete
                                 distanceTable[row][column - 1]));     // insert
            }
        }
    }
    return distanceTable[sourceLength][targetLength];
}

Complexity: time O(m·n), space O(m·n).

Q23. Regular Expression Matching (dynamic programming)

Problem statement: Implement matching that supports '.' (any single character) and '*' (zero or more of the preceding element).

Approach: a boolean table where [i][j] means the first i characters of the text match the first j characters of the pattern. A '*' either matches zero preceding elements (skip two pattern characters) or one more when the preceding pattern element matches the current text character.

public boolean isPatternMatch(String inputText, String pattern) {
    int textLength = inputText.length();
    int patternLength = pattern.length();
    boolean[][] matchTable = new boolean[textLength + 1][patternLength + 1];
    matchTable[0][0] = true; // empty text matches empty pattern
    for (int column = 1; column <= patternLength; column++) {
        if (pattern.charAt(column - 1) == '*') {
            matchTable[0][column] = matchTable[0][column - 2]; // x* can match zero characters
        }
    }
    for (int row = 1; row <= textLength; row++) {
        for (int column = 1; column <= patternLength; column++) {
            char textCharacter = inputText.charAt(row - 1);
            char patternCharacter = pattern.charAt(column - 1);
            if (patternCharacter == '.' || patternCharacter == textCharacter) {
                matchTable[row][column] = matchTable[row - 1][column - 1];
            } else if (patternCharacter == '*') {
                matchTable[row][column] = matchTable[row][column - 2]; // zero occurrences
                char precedingPatternCharacter = pattern.charAt(column - 2);
                if (precedingPatternCharacter == '.' || precedingPatternCharacter == textCharacter) {
                    matchTable[row][column] = matchTable[row][column] || matchTable[row - 1][column]; // one more
                }
            }
        }
    }
    return matchTable[textLength][patternLength];
}

Complexity: time O(m·n), space O(m·n).

Trees, Graphs & Design

Q24. Lowest Common Ancestor of a Binary Tree

Problem statement: Given a binary tree and two nodes, find their lowest common ancestor.

Approach: recurse; if both the left and right subtree calls return non-null, the current node is the LCA; otherwise propagate the non-null side upward.

public TreeNode findLowestCommonAncestor(TreeNode rootNode, TreeNode firstTarget, TreeNode secondTarget) {
    if (rootNode == null || rootNode == firstTarget || rootNode == secondTarget) {
        return rootNode; // found a target, or ran off the tree
    }
    TreeNode foundInLeft = findLowestCommonAncestor(rootNode.left, firstTarget, secondTarget);
    TreeNode foundInRight = findLowestCommonAncestor(rootNode.right, firstTarget, secondTarget);
    if (foundInLeft != null && foundInRight != null) {
        return rootNode; // targets are on different sides, so this node is the ancestor
    }
    return foundInLeft != null ? foundInLeft : foundInRight;
}

Complexity: time O(n), space O(h) for tree height h.

Q25. Binary Tree Level Order Traversal

Problem statement: Return a binary tree's values level by level.

Approach: breadth-first search with a queue, processing exactly one level per outer-loop iteration using a snapshot of the queue's size.

public List<List<Integer>> traverseLevelOrder(TreeNode rootNode) {
    List<List<Integer>> levelValues = new ArrayList<>();
    if (rootNode == null) {
        return levelValues;
    }
    Queue<TreeNode> nodeQueue = new LinkedList<>();
    nodeQueue.add(rootNode);
    while (!nodeQueue.isEmpty()) {
        int nodesInThisLevel = nodeQueue.size(); // snapshot: exactly one level per pass
        List<Integer> currentLevel = new ArrayList<>();
        for (int counter = 0; counter < nodesInThisLevel; counter++) {
            TreeNode currentNode = nodeQueue.poll();
            currentLevel.add(currentNode.val);
            if (currentNode.left != null) nodeQueue.add(currentNode.left);
            if (currentNode.right != null) nodeQueue.add(currentNode.right);
        }
        levelValues.add(currentLevel);
    }
    return levelValues;
}

Complexity: time O(n), space O(n).

Q26. Serialize and Deserialize a Binary Tree

Problem statement: Convert a binary tree to a string and reconstruct the identical tree from it.

Approach: pre-order DFS writing a 'null' marker for each empty child on serialize; rebuild recursively in the same order on deserialize.

public String serializeTree(TreeNode rootNode) {
    StringBuilder serializedText = new StringBuilder();
    appendNodeToText(rootNode, serializedText);
    return serializedText.toString();
}
 
private void appendNodeToText(TreeNode currentNode, StringBuilder serializedText) {
    if (currentNode == null) {
        serializedText.append("null,"); // marker keeps the shape recoverable
        return;
    }
    serializedText.append(currentNode.val).append(",");
    appendNodeToText(currentNode.left, serializedText);   // pre-order: node, left, right
    appendNodeToText(currentNode.right, serializedText);
}
 
public TreeNode deserializeTree(String serializedText) {
    Deque<String> tokenQueue = new ArrayDeque<>(Arrays.asList(serializedText.split(",")));
    return rebuildTree(tokenQueue);
}
 
private TreeNode rebuildTree(Deque<String> tokenQueue) {
    String nextToken = tokenQueue.poll();
    if (nextToken.equals("null")) {
        return null;
    }
    TreeNode rebuiltNode = new TreeNode(Integer.parseInt(nextToken));
    rebuiltNode.left = rebuildTree(tokenQueue);  // same pre-order sequence as serialization
    rebuiltNode.right = rebuildTree(tokenQueue);
    return rebuiltNode;
}

Complexity: time O(n), space O(n).

Q27. Number of Islands

Problem statement: Given a grid of land ('1') and water ('0') cells, count the connected land regions.

Approach: scan cells; on an unvisited land cell, run a depth-first search that “sinks” the entire connected region, and count it as one island.

public int countIslands(char[][] landGrid) {
    int islandCount = 0;
    for (int row = 0; row < landGrid.length; row++) {
        for (int column = 0; column < landGrid[0].length; column++) {
            if (landGrid[row][column] == '1') {
                islandCount++;                    // new, unvisited island
                sinkConnectedLand(landGrid, row, column);
            }
        }
    }
    return islandCount;
}
 
private void sinkConnectedLand(char[][] landGrid, int row, int column) {
    if (row < 0 || column < 0 || row >= landGrid.length
            || column >= landGrid[0].length || landGrid[row][column] != '1') {
        return; // out of bounds, water, or already visited
    }
    landGrid[row][column] = '0'; // mark visited by turning land into water
    sinkConnectedLand(landGrid, row + 1, column);
    sinkConnectedLand(landGrid, row - 1, column);
    sinkConnectedLand(landGrid, row, column + 1);
    sinkConnectedLand(landGrid, row, column - 1);
}

Complexity: time O(rows · cols), space O(rows · cols) for recursion depth.

Q28. Course Schedule (topological sort)

Problem statement: Given prerequisite pairs, decide whether all courses can be finished (i.e. the dependency graph has no cycle).

Approach: Kahn's algorithm. Repeatedly remove nodes with zero in-degree; if every node gets processed, there is no cycle.

public boolean canFinishAllCourses(int courseCount, int[][] prerequisitePairs) {
    List<List<Integer>> dependentCourses = new ArrayList<>();
    int[] incomingEdgeCount = new int[courseCount];
    for (int course = 0; course < courseCount; course++) {
        dependentCourses.add(new ArrayList<>());
    }
    for (int[] prerequisitePair : prerequisitePairs) {
        dependentCourses.get(prerequisitePair[1]).add(prerequisitePair[0]); // prerequisite -> course
        incomingEdgeCount[prerequisitePair[0]]++;
    }
    Deque<Integer> readyCourses = new ArrayDeque<>();
    for (int course = 0; course < courseCount; course++) {
        if (incomingEdgeCount[course] == 0) {
            readyCourses.add(course); // no prerequisites left
        }
    }
    int processedCourses = 0;
    while (!readyCourses.isEmpty()) {
        int finishedCourse = readyCourses.poll();
        processedCourses++;
        for (int unlockedCourse : dependentCourses.get(finishedCourse)) {
            if (--incomingEdgeCount[unlockedCourse] == 0) {
                readyCourses.add(unlockedCourse);
            }
        }
    }
    return processedCourses == courseCount; // fewer processed means a cycle exists
}

Complexity: time O(V+E), space O(V+E).

Q29. LRU Cache

Problem statement: Design a Least-Recently-Used cache with O(1) get and put. (A TTL variant with locking is in Part 2, Section 2, Q7.)

Approach: a LinkedHashMap in access-order mode plus removeEldestEntry gives an O(1) LRU directly.

class LeastRecentlyUsedCache extends LinkedHashMap<Integer, Integer> {
    private final int maximumCapacity;
 
    public LeastRecentlyUsedCache(int maximumCapacity) {
        super(maximumCapacity, 0.75f, true); // true = access order (most recent moves to the end)
        this.maximumCapacity = maximumCapacity;
    }
 
    public int get(int key) {
        return super.getOrDefault(key, -1);
    }
 
    public void put(int key, int value) {
        super.put(key, value);
    }
 
    @Override
    protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldestEntry) {
        return size() > maximumCapacity; // evict the least recently used when over capacity
    }
}

Complexity: time O(1) average, space O(capacity).

Q31. How would you design an immutable, thread-safe Money class for a financial system?

Make the class final with private final BigDecimal amount and Currency fields (never double, because of rounding). No setters: arithmetic returns new instances. Implement equals()/hashCode() on value, and validate currency compatibility before any operation. (The general immutable-class rules and defensive-copy details are in Part 1, Section 1.)

public final class Money {
    private final BigDecimal amount;   // BigDecimal, never double: exact decimal arithmetic
    private final Currency currency;
 
    public Money(BigDecimal amount, Currency currency) {
        this.amount = Objects.requireNonNull(amount);
        this.currency = Objects.requireNonNull(currency);
    }
 
    public Money add(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Currency mismatch");
        }
        return new Money(this.amount.add(other.amount), this.currency); // returns a NEW instance
    }
 
    @Override
    public boolean equals(Object otherObject) {
        if (this == otherObject) return true;
        if (!(otherObject instanceof Money)) return false;
        Money otherMoney = (Money) otherObject;
        return amount.compareTo(otherMoney.amount) == 0 && currency.equals(otherMoney.currency);
    }
 
    @Override
    public int hashCode() {
        return Objects.hash(amount.stripTrailingZeros(), currency); // consistent with equals
    }
}

Q32. How do you size a thread pool for a Java service?

CPU-bound work: roughly the number of cores (more threads only add context switching). I/O-bound work: larger, since threads mostly wait; a common starting formula is threads = cores × (1 + wait time / compute time), then tune with load testing. Use separate bounded pools for distinct kinds of work so one slow dependency can't exhaust the threads serving everything else (bulkheading). On Java 21, virtual threads (Part 2, Section 2) largely remove the need to size pools for blocking I/O.

Q35. Find the longest common prefix among an array of strings.

Problem statement: Given {"flower", "flow", "flight"}, return "fl". Return an empty string if there is no common prefix.

public static String longestCommonPrefix(String[] wordArray) {
    if (wordArray == null || wordArray.length == 0) {
        return "";
    }
    String commonPrefix = wordArray[0];            // start with the first word
    for (int index = 1; index < wordArray.length; index++) {
        // shrink the prefix until the current word starts with it
        while (!wordArray[index].startsWith(commonPrefix)) {
            commonPrefix = commonPrefix.substring(0, commonPrefix.length() - 1);
            if (commonPrefix.isEmpty()) {
                return "";
            }
        }
    }
    return commonPrefix;       // O(total characters) time, O(1) extra space
}

Q36. Merge two sorted arrays into one sorted array.

Problem statement: Given {1, 3, 5} and {2, 4, 6, 8}, return {1, 2, 3, 4, 5, 6, 8} in O(n + m) time.

public static int[] mergeSortedArrays(int[] firstArray, int[] secondArray) {
    int[] mergedArray = new int[firstArray.length + secondArray.length];
    int firstIndex = 0, secondIndex = 0, mergedIndex = 0;

    // take the smaller head element from either array
    while (firstIndex < firstArray.length && secondIndex < secondArray.length) {
        if (firstArray[firstIndex] <= secondArray[secondIndex]) {
            mergedArray[mergedIndex++] = firstArray[firstIndex++];
        } else {
            mergedArray[mergedIndex++] = secondArray[secondIndex++];
        }
    }
    // copy whatever remains in the array that is not yet exhausted
    while (firstIndex < firstArray.length) mergedArray[mergedIndex++] = firstArray[firstIndex++];
    while (secondIndex < secondArray.length) mergedArray[mergedIndex++] = secondArray[secondIndex++];
    return mergedArray;
}

Q37. Rearrange an array so all even numbers come before all odd numbers.

Problem statement: Given {3, 1, 2, 4, 7, 6}, produce an array such as {6, 2, 4, 1, 7, 3} (evens first) in O(n) time and O(1) space. If each group must also be sorted, sort the two halves afterwards.

public static void moveEvenNumbersFirst(int[] numberArray) {
    int leftPointer = 0;
    int rightPointer = numberArray.length - 1;

    while (leftPointer < rightPointer) {
        if (numberArray[leftPointer] % 2 == 0) {
            leftPointer++;                       // already in the even zone
        } else if (numberArray[rightPointer] % 2 != 0) {
            rightPointer--;                      // already in the odd zone
        } else {
            int temporaryValue = numberArray[leftPointer];   // odd on left, even on right: swap
            numberArray[leftPointer] = numberArray[rightPointer];
            numberArray[rightPointer] = temporaryValue;
            leftPointer++;
            rightPointer--;
        }
    }
}

Q38. Find the length of the longest valid (well-formed) parentheses substring.

Problem statement: For "(()" the answer is 2; for ")()())" it is 4; for "((()))(())" it is 10.

public static int longestValidParentheses(String inputText) {
    Deque<Integer> indexStack = new ArrayDeque<>();
    indexStack.push(-1);                       // base marker just before the string
    int longestLength = 0;

    for (int index = 0; index < inputText.length(); index++) {
        if (inputText.charAt(index) == '(') {
            indexStack.push(index);            // remember where '(' was seen
        } else {
            indexStack.pop();                  // match a '(' or remove the base marker
            if (indexStack.isEmpty()) {
                indexStack.push(index);        // unmatched ')' becomes the new base marker
            } else {
                longestLength = Math.max(longestLength, index - indexStack.peek());
            }
        }
    }
    return longestLength;                      // O(n) time, O(n) space
}

Q39. Schedule a round-robin match tournament among N teams. How do you handle an odd N, and who sits out?

  • Use the circle method: fix one team, rotate the others each round; every team plays every other team once in N-1 rounds (N even).
  • Odd N: add a dummy "BYE" team to make N even; whoever is paired with BYE sits out that round. Rotation guarantees each team sits out exactly once.
  • To choose who sits out on another basis (fairness, rest days, fewest games played), replace the rotation by a priority rule, for example the team with the most games played or the longest wait.

Problem statement: Print each round's pairings for a tournament among the given team names; a team paired with BYE rests.

public static void printRoundRobinSchedule(List<String> teamNames) {
    List<String> rotationList = new ArrayList<>(teamNames);
    if (rotationList.size() % 2 != 0) {
        rotationList.add("BYE");               // odd number of teams: one rests each round
    }
    int totalTeams = rotationList.size();
    for (int roundNumber = 1; roundNumber < totalTeams; roundNumber++) {
        System.out.println("Round " + roundNumber);
        for (int pairIndex = 0; pairIndex < totalTeams / 2; pairIndex++) {
            String homeTeam = rotationList.get(pairIndex);
            String awayTeam = rotationList.get(totalTeams - 1 - pairIndex);
            System.out.println("  " + homeTeam + " vs " + awayTeam);
        }
        // keep the first team fixed and rotate the rest by one position
        rotationList.add(1, rotationList.remove(totalTeams - 1));
    }
}

Section 3: Leadership, Team Management & Behavioral

Use STAR (Situation, Task, Action, Result). For Amazon, map stories explicitly to a Leadership Principle, since interviewers score against them. The answers below are frameworks to adapt to your real experience, not scripted stories.

Q1. Tell me about a time you disagreed with a decision made by your manager or a senior architect.

Interviewers are screening for one thing: did you raise the disagreement constructively, with evidence, and then commit fully once a decision was made, even if it didn't go your way? (Amazon: “Have Backbone; Disagree and Commit.”)

  • Situation — brief context, e.g. “Our architect proposed a synchronous call chain across four services for checkout; I was concerned about cascading latency and availability risk under load.”
  • Task — what was at stake and why you felt compelled to speak up rather than privately worry.
  • Action — raise it with data (a rough latency-budget calculation, or a past incident) in an appropriate private forum first, and propose a concrete alternative (“what if the notification step were asynchronous via Kafka?”) rather than just objecting.
  • Result — be honest about the outcome. If you disagreed and committed, explain how you supported the decision fully in execution and what you learned; this is often more impressive than “and I was proven right.”

Note: Avoid a story where you were simply right and everyone else wrong; it reads as an inability to see other perspectives, a red flag for a lead who must operate through influence. Practice this story aloud; it is one of the highest-probability questions in any lead interview.

Q2. How do you handle a team member who consistently misses deadlines or delivers low-quality code?

Start with diagnosis, not judgment.

  • 1. Understand the root cause privately and non-confrontationally: a skills gap, an estimation or scope problem, a personal issue affecting focus, unclear requirements they were hesitant to raise, or an engagement problem. Each needs a different fix, and misdiagnosing damages trust.
  • 2. Set explicit, specific expectations. “Code quality needs to improve” isn't actionable; “let's pair on the next two PRs, focusing on test coverage and null-safety, the recurring review comment” is.
  • 3. Provide the right support: pairing, smaller reviewable increments, a mentor, or temporarily adjusted workload if it's a burnout issue.
  • 4. Document and follow up on a cadence, not to build a paper trail against them but so both of you share an unambiguous view of whether things are improving.
  • 5. Escalate appropriately if there's no improvement after genuine support; this is also a duty to the rest of the team, who are affected by consistently under-delivered work.

Note: Interviewers listen for empathy plus accountability. Leads who show only empathy let poor performance persist; leads who show only accountability burn trust by skipping straight to write-ups. Both fail.

Q3. How do you balance technical debt against feature delivery pressure?

Don't frame it as “tech debt vs. features” (which sounds like engineering's pet concern competing with business value). Translate debt into business-legible risk and cost: “this shortcut will cost about two extra days on every future feature touching this module, with a meaningful risk of a production incident within two quarters.”

  • Categorize debt explicitly: “reckless and inadvertent” (bugs from not knowing better) versus “prudent and deliberate” (a conscious shortcut for a real deadline, with a plan to revisit), which is often a legitimate decision, not a failure.
  • Make debt visible and trackable: a tagged, estimated backlog category reviewed with the team and referenced in planning.
  • Negotiate a standing “tax rate” (e.g. 15–20% of each sprint's capacity) instead of a dedicated tech-debt sprint, which is a hard sell and the first thing cut under pressure.
  • Tie the highest-priority items to actual business risk: “the authentication module hasn't been load-tested past 500 concurrent users and a marketing campaign launches next quarter” is actionable; “this code is messy” is not.

The skill being tested is stakeholder communication and business framing: any senior engineer can spot debt, but a lead gets organizational buy-in and sustained capacity to address it.

Q4. How do you conduct code reviews as a tech lead without becoming a bottleneck?

  • Review correctness and design first, style second; automate formatting entirely (Checkstyle, Spotless, pre-commit hooks) so human time goes to what automation can't catch.
  • Mark comments as blocking or non-blocking (“blocking:”, “nit:”, “consider:”) so authors aren't left guessing.
  • Set a review turnaround SLA (e.g. first pass within 4 business hours) and protect calendar time for it; a lead who is the review bottleneck is one of the most common and avoidable causes of lost velocity.
  • Don't be the only reviewer: distribute review responsibility among senior engineers, which scales capacity, develops their review skills, and removes a bus-factor risk.
  • Use review as teaching, not just a gate: explain why something is a problem, with a link or brief rationale.

Treat review process design as a leadership deliverable: periodically look at PR open-to-merge time like any other team-health metric. (Review red flags to look for are in Part 5, Section 3, Q4.)

Q5. How do you run sprint planning and estimation for a team of mixed experience?

  • Refine stories before planning, in a separate earlier session, so planning is about commitment and sequencing rather than rediscovering scope live.
  • Use relative estimation (story points via Planning Poker) rather than absolute hours, calibrated periodically against actual velocity so points stay meaningful.
  • Pair juniors and seniors on unfamiliar work: a junior's honest estimate for an unfamiliar area often surfaces risks a senior would silently absorb.
  • Guard against systematic optimism: track estimate-versus-actual over several sprints and use the data in retrospectives.
  • Leave explicit buffer for unplanned work (production support, urgent bugs) instead of planning at 100% theoretical capacity.

Good estimation isn't about better guessing; it is about making real capacity and risk visible early enough to adjust scope gracefully. (For the full Agile planning lifecycle, see Section 5, Q1.)

Q6. How do you mentor junior and mid-level engineers into senior roles while still delivering?

  • Delegate stretch work with real ownership, not just busywork. It's slower short-term but is the actual mechanism of growth.
  • Build in explicit early design-review checkpoints rather than “come to me if you're stuck,” since juniors don't know what they don't know.
  • Make your reasoning visible: explain the “why” and point to a broader principle so the lesson generalizes.
  • Protect mentoring time on your calendar like a customer deadline; unscheduled, it's the first thing dropped.
  • Give specific feedback tied to the next level's expectations (“seniors proactively flag cross-team dependencies during design”).

Without formal authority, influence through technical credibility: pairing and reviews as teaching moments, design docs/RFCs that make trade-offs explicit, guiding questions instead of dictating, and consensus built with data and prototypes. The question tests whether you understand that a lead's primary output shifts from personal code to the team's collective output and growth.

Q7. How would you handle a Sev-1 production incident during off-hours, technically and in communication?

First 15 minutes (technical)

  • Stabilize before diagnosing: stop customer/business impact first via reversible, low-risk actions (roll back the last deploy, fail over to a healthy region, disable a feature flag).
  • Establish an incident commander early (often you, or explicitly delegated), avoiding five engineers independently trying different fixes.
  • Communicate on a fixed cadence (every 15–30 minutes) even with no news; “still investigating, next update in 15 minutes” beats silence.

Communication

  • Notify stakeholders early so business and support teams can manage customer communication in parallel; under-communicating a Sev-1 compounds the damage.
  • Keep updates factual and blameless during the incident; save “whose deploy broke this” for the postmortem.

After resolution

  • Hold a blameless postmortem within 48 hours, focused on systemic factors (why didn't tests or monitoring catch it? why was rollback slow?) so people surface information in future incidents.
  • Track concrete, owned, time-bound action items to completion; a postmortem with no follow-through is theater.

Interviewers, especially at banks where outages carry regulatory and financial impact, assess composure under pressure and communication discipline as much as technical skill. Cover detection, mitigation, root cause (logs, traces, metrics correlation), stakeholder cadence, and prevention in your story.

Q8. How do you make an architecture decision when the team is split and time is short?

  • 1. Make the decision criteria explicit before debating options (“time-to-market beats long-term flexibility for this three-month pilot”), so the debate isn't a proxy battle over personal technology preferences.
  • 2. Use a lightweight Architecture Decision Record: list two or three real options, their trade-offs against the agreed criteria, and a recommendation. Writing it surfaces reasoning gaps and gives quieter members a structured way to contribute.
  • 3. Time-box it (“input until Thursday EOD; I decide Friday morning if we haven't converged”).
  • 4. As lead you own the final call after genuinely hearing dissent; avoid false consensus-seeking that just delays an unavoidable trade-off.
  • 5. Note in the ADR what would make you reconsider, so reversing later is a planned response to new information, not a failure.

The question tests whether you can drive convergence without steamrolling the team (resentment) or seeking endless consensus (paralysis). The same reasoning applies to a difficult architectural trade-off under time pressure: state the competing constraints, the options and trade-offs, why you chose your path, how you mitigated the downside (documented debt, a planned follow-up refactor), and the measurable outcome.

Q9. How do you handle scope creep mid-sprint, especially in a client-services model?

  • Distinguish genuine urgent business need (a production-blocking client issue) from habitual scope drift (“nice to have while you're in there”).
  • Make the trade-off visible: “we can add this, but it pushes out [specific item] by [amount], or we add it next sprint with no impact; which do you prefer?” Silently absorbing it trains stakeholders that scope creep is free.
  • Protect the sprint commitment as a team promise; if stakeholders can add work mid-sprint with no visible trade-off, planning credibility erodes.
  • In client-services contexts, tie scope changes to the contractual/change-request process; it protects both the team and the client relationship by keeping cost and timeline changes explicit and agreed.
  • Keep a small buffer for genuinely reasonable minor asks; rigidity about every request damages the relationship more than it protects the sprint.

The core skill is making trade-offs visible rather than absorbing them silently, since silent absorption (unpaid overtime, cut corners) builds morale and quality debt over quarters.

Q10. What do you look for when interviewing a candidate for a senior or lead role?

  • Reasoning process over memorized answers: do they ask clarifying questions, state assumptions, and reason through trade-offs aloud? A confident design produced without ever asking about scale or consistency is a red flag.
  • How they handle being wrong or challenged: I deliberately push back mid-interview to see whether they defend with evidence, genuinely reconsider, or get defensive, which maps to real design reviews.
  • Ownership and impact, not just task completion: probe “what did you personally decide or drive” versus “what I did within an effort someone else directed.”
  • Communication clarity, especially translating technical trade-offs for non-technical stakeholders.
  • Calibrated confidence: comfortable saying “I don't know, but here's how I'd find out”; bluffing is a bigger red flag than a knowledge gap, since leads set the team's norm for intellectual honesty.

Q11. Quick-reference STAR story bank.

Before interviews, prepare five to seven real stories that each flex across several questions above, and practice each in under two minutes with a clear Situation, Task, Action, Result arc. Have ready:

  • A technical decision under significant ambiguity or time pressure.
  • A disagreement with leadership and how it resolved.
  • A production incident you led the response to.
  • Someone you mentored into a promotion or major capability jump.
  • Influencing another team without direct authority.
  • A project that failed or missed its goal, and what you learned.
  • Pushing back on scope or deadline pressure and managing the trade-off conversation.

Note: Be ready for follow-up “why” questions probing your specific reasoning at each step; that depth is usually where lead-level candidates separate from individual-contributor candidates telling similar surface stories. Also cover the tech-lead layer at banks: production ownership under regulatory rigor (change control, audit trails, rollback plans).

Section 4: Domain Knowledge & Application-Server Clustering

Q1. What is a swap (in finance)?

A swap is a derivative contract in which two parties agree to exchange a series of future cash flows under a predetermined formula over a set period. Swaps are used for hedging (reducing exposure to interest-rate or currency movements) and for speculation. This appears on Java interview lists because financial-services roles expect engineers to understand the instruments their systems process; the interviewer is checking domain familiarity, not a pure Java skill.

  • Interest rate swap — the most commonly intended type. The parties exchange interest payment obligations on an agreed notional principal (the notional itself is never exchanged; it only drives the calculation). The plain-vanilla structure swaps a fixed rate for a floating rate tied to a benchmark (historically LIBOR, increasingly SOFR in USD markets). A company with a floating-rate loan that wants predictable payments can convert to an effectively fixed rate without refinancing.
  • Currency swap — the parties exchange principal and interest denominated in different currencies, e.g. a multinational raising financing in a foreign currency at a better effective rate than borrowing there directly.
  • Credit default swap (CDS) — conceptually closer to insurance: the protection buyer pays a regular premium to the seller, who compensates the buyer if a specified debt instrument (a corporate or government bond) defaults.

From a software perspective, a swap-processing system must store each swap's terms (notional, fixed rate, floating-rate reference index, payment schedule, start and maturity dates); calculate each party's cash-flow obligation on every scheduled date (the floating leg needs the current reference rate at that time); and compute the mark-to-market value (its theoretical worth if unwound today, from discounting all remaining expected cash flows to present value) for risk management and reporting.

Q2. What is WebLogic clustering?

Oracle WebLogic Server is a full Java EE (now Jakarta EE) application server, historically common in banking, insurance, and telecom for complex, transaction-heavy applications. A cluster is a group of WebLogic server instances (on one machine or several) configured to act as one logical unit, delivering two related benefits:

  • High availability — if one instance fails or is taken down for maintenance, the others keep serving. For stateful applications, session replication copies each user's HTTP session data to at least one other instance, so if the original instance fails mid-session another takes over seamlessly with no re-login or lost state.
  • Scalability — requests are distributed across instances (via a dedicated load balancer or WebLogic's cluster-aware HTTP proxy plugin), so aggregate capacity exceeds any single instance.

Underlying mechanisms

  • In-memory replication — each instance designates another as the replica holding a synchronized backup of a session's data; if the primary fails, the replica takes over immediately.
  • Multicast or unicast cluster communication — members continuously exchange heartbeats to know who is in the cluster and healthy so failed instances are excluded from routing (unicast is the modern, firewall-friendly recommendation over historical IP multicast).
  • JNDI replication — cluster-aware JNDI lookups let clients find clustered EJBs and resources without hard-coding which instance serves a request.

Note: The concepts being tested (load balancing across instances, session replication/affinity for high availability, cluster membership and health monitoring) transfer across every mainstream Java EE server (JBoss/WildFly, WebSphere, GlassFish/Payara) and, conceptually, to how Kubernetes load-balances replicas of a containerized app.

Section 5: Agile Project Planning

Q1. How do you plan a complex project in Agile?

Work at several granularities and time horizons at once instead of producing one giant, fully detailed upfront (waterfall) plan.

  • 1. Break the project into epics — large bodies of related work representing significant business value (“Customer Self-Service Portal”, “Payment Processing Overhaul”), too big for one sprint and used as an organizing layer.
  • 2. Decompose epics into user stories — small, independently deliverable units ideally finishable in one sprint, written from the user's perspective (“As a [role], I want [capability], so that [benefit]”) and meeting the INVEST criteria: Independent, Negotiable, Valuable, Estimable, Small, Testable.
  • 3. Prioritize the backlog by business value and risk. On a complex, higher-risk project, tackle the biggest technical unknowns early (a “walking skeleton” or spike) to surface blockers while there's time to adjust.
  • 4. Estimate relatively with story points, determined collaboratively (Planning Poker) to reconcile differing views of complexity before committing.
  • 5. Establish velocity — the empirically observed average points completed per sprint over several sprints — to forecast realistically how many sprints the project needs.
  • 6. Plan and execute in sprints (typically 1–4 weeks), committing at each start to a subset of the highest-priority stories that fits velocity.
  • 7. Hold retrospectives at each sprint's end to decide concrete process changes for the next one, so estimation and delivery improve instead of repeating avoidable mistakes.
  • 8. Keep stakeholders informed through sprint reviews/demos of working software and a current backlog/roadmap, so feedback arrives early instead of only at the end.

For very large projects with multiple teams, frameworks such as SAFe (Scaled Agile Framework), LeSS (Large-Scale Scrum), or Spotify's tribes-and-squads model add higher-level structure for coordinating dependencies and shared priorities across teams.

Note: Agile planning is deliberately iterative and adaptive, not a one-time exercise. Backlog, priorities, and even the overall timeline are continuously revisited as the team learns from feedback on delivered increments, unexpected technical findings, and its own increasingly accurate estimation.
