Section 1: Multithreading & Concurrency

The Executor Framework

Before java.util.concurrent existed, developers managed threads manually by creating new Thread objects directly — which does not scale well and makes it hard to control the number of concurrently running threads. The Executor framework decouples task submission from the mechanics of how each task actually runs: how threads are created, scheduled, reused, and shut down.

Executor

The simplest interface in the framework, in java.util.concurrent. It exposes a single method, execute(Runnable), whose entire purpose is to separate “submitting a task” from “deciding how and when that task actually runs.”

Executors

A factory class, also in java.util.concurrent, providing static factory methods that return various kinds of ExecutorService, ScheduledExecutorService, and ThreadFactory instances, so you rarely need to implement Executor yourself.

newFixedThreadPool()

One of the most commonly used factory methods on Executors. It creates a thread pool with a fixed number of reusable threads. If a thread dies unexpectedly before its task completes, a fresh thread from the pool automatically takes over remaining work, keeping the pool size constant.

Problem statement: Submit a recurring background task to a fixed-size thread pool without managing threads manually.

// RecurringCounterTask.java - prints an incrementing counter every second
package com.interviewguide.concurrency;
 
public class RecurringCounterTask implements Runnable {
    @Override
    public void run() {
        try {
            for (int counterValue = 0; ; counterValue++) {
                System.out.println(counterValue);
                Thread.sleep(1000);
            }
        } catch (InterruptedException interruptedException) {
            // restore the interrupt status so calling code can observe it
            Thread.currentThread().interrupt();
        }
    }
}
 
// TaskRunner.java - submits the task to a fixed-size thread pool
package com.interviewguide.concurrency;
 
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;
 
public class TaskRunner {
    public static void main(String[] args) {
        Executor threadPoolExecutor = Executors.newFixedThreadPool(10);
        threadPoolExecutor.execute(new RecurringCounterTask());
    }
}

Executor vs. ExecutorService

Both are interfaces in java.util.concurrent. ExecutorService extends Executor and adds significant lifecycle and coordination control:

  • shutdown() / shutdownNow() — gracefully or forcibly stop accepting and running tasks.
  • awaitTermination(timeout, unit) — block until all tasks complete or the timeout elapses.
  • isShutdown() / isTerminated() — query the pool's lifecycle state.
  • invokeAny(...) / invokeAll(...) — submit a batch of Callable tasks and either get the first successful result, or wait for all of them.
  • submit(...) — unlike execute(), returns a Future so you can retrieve a result or exception.
ExecutorService threadPoolExecutor = Executors.newFixedThreadPool(10);
threadPoolExecutor.execute(new RecurringCounterTask());
// attempts to interrupt all running tasks and stop the pool immediately
threadPoolExecutor.shutdownNow();

Note: shutdownNow() attempts to stop all actively executing tasks by interrupting them. In the example above, the task is blocked inside Thread.sleep(), so the interrupt causes sleep() to throw an InterruptedException immediately, unwinding that task's run() method.

Thread Safety & Synchronization Fundamentals

Thread.sleep()

  • The static method Thread.sleep(long millis) forces the currently executing thread to pause for at least the given duration.
  • sleep() declares a checked exception, InterruptedException, so every call must either be wrapped in a try/catch or the enclosing method must declare it in its own throws clause.
  • Calling sleep() gives other threads a chance to run, but there is no guarantee about scheduling order afterward — sleep() is a simple (if crude) way to encourage fair thread switching, not a substitute for proper synchronization.
try {
    Thread.sleep(200); // pause this thread for ~200 milliseconds
} catch (InterruptedException interruptedException) {
    Thread.currentThread().interrupt(); // restore the interrupt flag
}

Why shared mutable state is dangerous

  • Serious problems arise when two or more threads have access to the same mutable object on the heap.
  • If one thread is interrupted mid-way through modifying an object's internal state, another thread could observe or modify that object while it's only half-updated, corrupting data.
  • To make a class thread-safe, you must decide which sequences of statements need to be treated as a single atomic operation — one that runs to completion, uninterrupted by any other thread, before another thread may touch the same object's state.

The synchronized keyword

  • Use synchronized on a method declaration to prevent more than one thread from entering that method (on the same object instance) at the same time.
  • Every object has a single intrinsic lock (monitor). It only becomes relevant once an object has one or more synchronized methods.
  • A thread attempting to enter a synchronized method must first acquire that object's lock; if another thread holds it, the requesting thread blocks until it becomes available.
  • Even with multiple synchronized methods on a class, there is still only one lock per object instance — once any thread enters one synchronized method on an object, no other thread can enter any other synchronized method on that same object concurrently. This is precisely what protects an object's internal data.
public class BankAccount {
    private double currentBalance;
 
    // synchronized: only one thread at a time can execute THIS method
    // on a given BankAccount instance
    public synchronized void withdrawFunds(double withdrawalAmount) {
        if (currentBalance >= withdrawalAmount) {
            currentBalance -= withdrawalAmount;
        }
    }
 
    // this method is ALSO locked out while withdrawFunds() is running,
    // because they share the same object-level lock
    public synchronized void depositFunds(double depositAmount) {
        currentBalance += depositAmount;
    }
}

Note: Synchronizing an entire method is the simplest approach, but locks out ALL synchronized methods on that instance for the duration, even unrelated ones. For finer-grained control, synchronize only the specific block of code that touches shared state, as shown in Q1 below.

Multithreading Interview Questions

Q1. What is the difference between a synchronized method and a synchronized block?

A synchronized method locks the entire method body using the intrinsic lock of the object it's called on (or the Class object, if the method is static). A synchronized block lets you lock on any explicit object you choose, and only for the specific statements inside the block. Synchronized blocks are generally preferred because they minimize the amount of code executed while holding the lock, reducing contention and improving throughput.

Problem statement: Reduce inventory stock safely under concurrent access, locking only the critical section rather than the entire method.

public class InventoryManager {
    private int stockCount;
    private final Object stockLock = new Object();
 
    public void reduceStock(int quantity) {
        // only this critical section is locked, not the whole method
        synchronized (stockLock) {
            if (stockCount >= quantity) {
                stockCount -= quantity;
            }
        }
        // any non-shared-state work can happen here, outside the lock
        logStockChange(quantity);
    }
 
    private void logStockChange(int quantity) {
        System.out.println("Reduced stock by " + quantity);
    }
}

Q2. What is a deadlock, and how can you avoid it?

A deadlock occurs when two or more threads are each waiting for a lock held by one of the others, so none of them can ever proceed. The classic example is Thread A holding Lock 1 and waiting for Lock 2, while Thread B holds Lock 2 and waits for Lock 1.

Common ways to avoid deadlock:

  • Always acquire multiple locks in a consistent, global order across all threads.
  • Use tryLock(timeout) from java.util.concurrent.locks.Lock instead of blocking indefinitely, so a thread can back off and retry if it cannot acquire a lock within a reasonable time.
  • Minimize the scope and duration for which locks are held.
  • Avoid calling out to unknown/overridable code while holding a lock.
// Deadlock-prone: threads may acquire lockA and lockB in different orders
synchronized (lockA) {
    synchronized (lockB) {
        // ...
    }
}
 
// Fix: always acquire locks in the same global order (e.g. by a consistent ID)
Object firstLock  = accountA.getId() < accountB.getId() ? lockA : lockB;
Object secondLock = accountA.getId() < accountB.getId() ? lockB : lockA;
synchronized (firstLock) {
    synchronized (secondLock) {
        // safe: every thread acquires locks in the same order
    }
}

Q3. What is the difference between wait()/notify() and sleep()?

wait() and notify() are methods on Object, used for inter-thread communication. A thread calling wait() must already hold the object's monitor lock; calling wait() releases that lock and suspends the thread until another thread calls notify() or notifyAll() on the same object. sleep(), by contrast, is a static Thread method that pauses the current thread for a fixed duration WITHOUT releasing any locks it holds.

Problem statement: Implement a simple producer/consumer handoff using wait()/notify() on a shared buffer.

class SharedBuffer {
    private final Object bufferLock = new Object();
    private boolean dataReady = false;
 
    void produce() {
        synchronized (bufferLock) {
            dataReady = true;
            bufferLock.notify(); // wake up a thread waiting on bufferLock
        }
    }
 
    void consume() throws InterruptedException {
        synchronized (bufferLock) {
            while (!dataReady) {
                bufferLock.wait(); // releases the lock and waits to be notified
            }
            // process the data
        }
    }
}

Figure: wait()/notify() vs sleep()

Q4. What is a race condition? Give an example.

A race condition occurs when the correctness of a program depends on the relative timing of multiple threads, and the outcome varies depending on which thread happens to execute first. A classic example is two threads incrementing a shared counter without synchronization: the increment (read, add one, write back) is not atomic, so both threads can read the same initial value before either writes back, and one increment is silently lost.

public class UnsafeCounter {
    private int count = 0;
 
    public void increment() {
        count++; // NOT atomic: read, add 1, write back - three separate steps
    }
}
// If two threads call increment() concurrently on the same instance without
// synchronization, one of the increments can be lost due to interleaving.
 
public class SafeCounter {
    private int count = 0;
 
    public synchronized void increment() {
        count++; // now atomic with respect to other synchronized calls
    }
}

Q5. What is the volatile keyword, and when should you use it?

volatile guarantees two things for a field: (1) every read of the field always sees the most recently written value from any thread (visibility), and (2) the compiler and CPU will not reorder instructions around accesses to that field. It does NOT make compound operations like count++ atomic. volatile is appropriate for simple flags or references that are written by one thread and read by others, such as a shutdown flag or the double-checked-locking Singleton pattern shown in Section 2.

public class Worker implements Runnable {
    private volatile boolean shutdownRequested = false;
 
    public void requestShutdown() {
        shutdownRequested = true; // visible to the worker thread immediately
    }
 
    @Override
    public void run() {
        while (!shutdownRequested) {
            // do work
        }
    }
}

Q6. What is the difference between Callable and Runnable?

Runnable's run() method returns void and cannot throw checked exceptions. Callable<V>'s call() method returns a value of type V and can throw a checked exception. Callable is designed to be used with ExecutorService.submit(), which returns a Future<V> that lets you retrieve the result once the task finishes.

Callable<Integer> computeSquareTask = () -> {
    int inputValue = 7;
    return inputValue * inputValue;
};
 
ExecutorService threadPoolExecutor = Executors.newSingleThreadExecutor();
Future<Integer> resultFuture = threadPoolExecutor.submit(computeSquareTask);
Integer squareResult = resultFuture.get(); // blocks until the result is ready
System.out.println(squareResult); // 49
threadPoolExecutor.shutdown();

Q7. What is the difference between Executor.submit() and Executor.execute()?

Both methods schedule a task for execution on a thread pool, but they differ in what they return and how they handle exceptions:

  • execute(Runnable) returns void. There is no way to retrieve a result or check whether the task completed successfully from the call itself.
  • submit(Callable) or submit(Runnable) returns a Future object, which lets you call get() to retrieve the task's result (blocking until it's done) or check isDone()/cancel().

The exception handling behavior also differs. If a task submitted with execute() throws an uncaught exception, it propagates to the thread's UncaughtExceptionHandler (by default this just prints a stack trace to System.err). If a task is submitted with submit(), any exception — checked or unchecked — is instead captured and stored inside the returned Future, surfacing only when you call future.get(), which re-throws it wrapped in an ExecutionException.

ExecutorService threadPool = Executors.newFixedThreadPool(4);
 
// execute(): fire-and-forget, exceptions go to the uncaught exception handler
threadPool.execute(() -> { throw new RuntimeException("boom"); });
 
// submit(): exception is captured inside the Future
Future<Integer> resultFuture = threadPool.submit(() -> {
    throw new RuntimeException("boom");
});
try {
    resultFuture.get(); // throws ExecutionException wrapping the RuntimeException
} catch (ExecutionException wrappedException) {
    System.out.println("Caught: " + wrappedException.getCause());
} catch (InterruptedException interruptedException) {
    Thread.currentThread().interrupt();
}

Q8. What is ConcurrentHashMap, and how is it different from a synchronized HashMap?

ConcurrentHashMap (java.util.concurrent) is a thread-safe map designed for high concurrency. Unlike Collections.synchronizedMap(new HashMap<>()), which uses a single lock for the entire map (so only one thread can access it at a time, even for unrelated keys), ConcurrentHashMap internally partitions its data so that multiple threads can read and write concurrently with minimal contention. In modern JDKs (Java 8+) it uses a combination of CAS (compare-and-swap) operations and fine-grained locking per bin, rather than locking the whole map.

  • Read operations in ConcurrentHashMap generally do not block at all.
  • Iterators returned by ConcurrentHashMap are weakly consistent: they never throw ConcurrentModificationException, and reflect the state of the map at some point at or after the iterator was created.
  • A synchronized HashMap's iterator, by contrast, throws ConcurrentModificationException if the map is structurally modified by another thread during iteration.

Internally (JDK 8+), ConcurrentHashMap achieves this without locking the entire map by using CAS-based updates for the common case of inserting into an empty bin, and synchronizing only on the head node of a single bin when a collision chain must be modified — so writes to different bins never contend with each other.

Q9. What is a ThreadLocal, and what memory-leak risk does it carry in application-server or thread-pool environments?

ThreadLocal<T> gives each thread its own independent copy of a variable, invisible to other threads — useful for per-thread context such as a database connection, a user session, or a SimpleDateFormat instance (which is not itself thread-safe). Internally, each Thread object holds a small map from ThreadLocal instance to value.

The memory-leak risk arises specifically in thread-pool environments (application servers, ExecutorService pools) because pooled threads are long-lived and reused across many logical tasks. If a task sets a ThreadLocal value and never calls remove() when it finishes, the value (and anything it references) stays attached to that pooled thread indefinitely, since the thread itself is never garbage collected. Over time and many task executions, this silently accumulates memory — and can also leak stale/incorrect context into a later, unrelated task reusing the same pooled thread. The fix is to always clear a ThreadLocal in a finally block once the task using it completes.

private static final ThreadLocal<SimpleDateFormat> DATE_FORMAT_HOLDER =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
 
public String formatOrderDate(Date orderDate) {
    try {
        return DATE_FORMAT_HOLDER.get().format(orderDate);
    } finally {
        // essential in a pooled-thread environment: prevents the value (and
        // anything it references) from leaking into the next task on this thread
        DATE_FORMAT_HOLDER.remove();
    }
}

Q10. Explain the Java Memory Model (JMM) and why volatile alone doesn't make compound operations atomic.

The Java Memory Model defines the rules for how and when writes made by one thread become visible to reads made by another thread, in the presence of compiler, JIT, and CPU-level instruction reordering. Without any synchronization, the JMM makes almost no visibility guarantees — one thread can run indefinitely without ever observing another thread's write to a shared, non-volatile field, because the reader may be working from a cached or reordered view of memory. Synchronization primitives (synchronized, volatile, java.util.concurrent locks) establish happens-before relationships, which are the JMM's formal guarantee that everything a thread did before a given point is visible to another thread after it reaches a corresponding point.

volatile establishes happens-before ordering for reads and writes of that single field, and prevents reordering around it — but a compound operation like count++ is actually three separate steps (read, increment, write). Even with count declared volatile, another thread can interleave between those steps: Thread A reads the current value, Thread B reads the same (still-old) value, both increment locally, and both write back, so one increment is lost. volatile guarantees visibility of the field, not atomicity of multi-step operations performed on it. True atomicity requires either synchronized around the whole read-modify-write sequence, or an atomic class from java.util.concurrent.atomic (e.g. AtomicInteger.incrementAndGet(), which performs the operation as a single CAS-based primitive).

Q11. ConcurrentHashMap internals — how does it achieve thread safety without locking the entire map?

Modern ConcurrentHashMap (Java 8+) is backed by the same array-of-buckets structure as HashMap, but synchronizes at the level of an individual bin (bucket) rather than the whole table. Inserting into an empty bin is done with a CAS (compare-and-swap) operation — lock-free. Only when a collision occurs and the bin's linked list (or, for large bins, its red-black tree) must be modified does the implementation synchronize, and it synchronizes only on that bin's head node, not on the map as a whole. This means writes targeting different bins never contend with each other, and reads are largely lock-free throughout, giving far higher throughput under concurrent access than a single coarse-grained lock over the entire map would.

Q12. What are the differences between synchronized, ReentrantLock, and StampedLock? When would you choose each?

synchronized is the built-in intrinsic lock: simplest to use, automatically released even if an exception is thrown, but strictly block-structured (you can't try to acquire it with a timeout, can't interrupt a thread waiting on it, and can't inspect whether it's currently held).

ReentrantLock (java.util.concurrent.locks) offers everything synchronized does, plus: tryLock() and tryLock(timeout, unit) for non-blocking or bounded-wait acquisition; lockInterruptibly() so a waiting thread can respond to interruption; fairness ordering (an optional constructor flag that grants the lock in the order threads requested it, avoiding thread starvation); and multiple associated Condition objects (in place of a single implicit wait/notify per object). The cost is that you must remember to unlock() in a finally block yourself — the JVM won't do it for you on an exception.

StampedLock (Java 8+) adds a third mode beyond simple read/write locking: an optimistic read, which doesn't block writers at all and instead returns a stamp that the reader later validates; if a write occurred in the meantime, the optimistic read is discarded and retried under a full read lock. This makes StampedLock significantly faster than ReentrantReadWriteLock for read-heavy workloads, at the cost of a more error-prone API (it is not reentrant, and forgetting to validate the optimistic stamp silently reads torn/stale data).

Choice: use synchronized for simple cases where its block-structured nature is sufficient; use ReentrantLock when you need tryLock/timeouts, interruptible waiting, fairness, or multiple wait conditions; use StampedLock for very read-heavy hot paths where the optimistic-read fast path's extra throughput is worth the added complexity and care.

Q13. Explain the difference between CompletableFuture and traditional Future. Design an async pipeline with error handling.

A plain Future only supports blocking retrieval of a result via get() (optionally with a timeout) — there is no way to register a callback, chain further work onto its completion, or combine it with another Future without a separate thread blocking on get(). CompletableFuture (java.util.concurrent, Java 8+) implements both Future and CompletionStage, adding a rich set of composition methods: thenApply() to transform a result, thenCompose() to chain a dependent async operation, thenCombine() to join two independent futures, and exceptionally()/handle() for error handling — all without blocking a thread to wait for the prior stage.

Problem statement: Build an asynchronous pipeline that fetches a customer's profile, then fetches their order history, combines both into a summary, and falls back to a default summary if any stage fails.

public CompletableFuture<CustomerSummary> buildCustomerSummaryAsync(String customerId) {
    CompletableFuture<CustomerProfile> profileFuture =
            CompletableFuture.supplyAsync(() -> customerService.fetchProfile(customerId));
 
    CompletableFuture<List<Order>> orderHistoryFuture =
            CompletableFuture.supplyAsync(() -> orderService.fetchOrderHistory(customerId));
 
    return profileFuture
            // thenCombine: merge two independent async results once both complete
            .thenCombine(orderHistoryFuture, CustomerSummary::new)
            // exceptionally: fall back to a safe default if any prior stage failed
            .exceptionally(pipelineError -> {
                logger.warn("Falling back to default summary for " + customerId, pipelineError);
                return CustomerSummary.defaultFor(customerId);
            });
}

Section 2: Additional Concurrency Topics

The following concurrency questions were not covered in Section 1 and add further depth on thread creation, producer-consumer coordination, lock-free algorithms, and modern virtual threads.

Q1. What is the difference between a Process and a Thread, and what are the ways to create a thread in Java?

A process is an independent, isolated program with its own memory space; a thread is a lightweight sub-unit of a process, sharing the process's memory (heap, static fields) but with its own private stack and program counter. Threads are far cheaper to create than processes and enable concurrent execution within a single program.

Three ways to create a thread in Java:

  • Extend the Thread class and override run().
  • Implement the Runnable interface and pass an instance to a Thread's constructor.
  • Implement Callable<V> (returns a value, can throw checked exceptions) and submit it to an ExecutorService.

Implementing Runnable/Callable is generally preferred over extending Thread, since Java supports only single inheritance — extending Thread uses up your one available superclass slot, and separates the “task” from the “thread that runs it,” which is a cleaner design and works naturally with thread pools.

Q2. Explain the producer-consumer problem and how BlockingQueue solves it.

Producer-consumer involves one or more threads producing data items and one or more threads consuming them, requiring coordination so producers don't overwhelm a full buffer and consumers don't busy-wait on an empty one. Implementing this correctly by hand requires careful wait()/notify() coordination and is easy to get subtly wrong.

BlockingQueue (e.g. ArrayBlockingQueue, LinkedBlockingQueue) handles this internally: put() blocks the producer when the queue is full, and take() blocks the consumer when the queue is empty, eliminating manual wait()/notify() coordination entirely.

Problem statement: Coordinate two threads so one prints odd numbers and the other prints even numbers, strictly in ascending order from 1 to 10.

class NumberPrinter {
    private int currentNumber = 1;
    private final int maxLimit = 10;
    private boolean isOddTurn = true;
 
    public synchronized void printOddNumbers() {
        while (currentNumber <= maxLimit) {
            while (!isOddTurn) {
                try { wait(); } catch (InterruptedException ignored) { }
            }
            if (currentNumber <= maxLimit) {
                System.out.println("Odd: " + currentNumber++);
                isOddTurn = false;
                notifyAll(); // wake the even-number thread
            }
        }
    }
 
    public synchronized void printEvenNumbers() {
        while (currentNumber <= maxLimit) {
            while (isOddTurn) {
                try { wait(); } catch (InterruptedException ignored) { }
            }
            if (currentNumber <= maxLimit) {
                System.out.println("Even: " + currentNumber++);
                isOddTurn = true;
                notifyAll(); // wake the odd-number thread
            }
        }
    }
}
 
public class AlternatePrintDemo {
    public static void main(String[] arguments) {
        NumberPrinter sharedPrinter = new NumberPrinter();
        Thread oddThread = new Thread(sharedPrinter::printOddNumbers);
        Thread evenThread = new Thread(sharedPrinter::printEvenNumbers);
        oddThread.start();
        evenThread.start();
    }
}

Q3. What's the difference between wait()/notify() and the Lock/Condition API?

wait()/notify() are methods on Object, usable only inside a synchronized block, and offer a single implicit condition per monitor — every waiting thread wakes on the same notify()/notifyAll() call, with no way to selectively wake only threads waiting for a specific condition. Lock/Condition (java.util.concurrent.locks) let you create multiple named Condition objects per Lock, so you can wait on and signal distinct conditions independently (e.g. a “notFull” condition and a “notEmpty” condition on the same buffer), plus tryLock() with a timeout and interruptible lock acquisition — offering considerably more flexibility and finer control than intrinsic locking.

Q4. Explain ExecutorService's common thread pool types.

  • FixedThreadPool — a fixed number of reusable threads; good when you want to cap concurrent resource usage.
  • CachedThreadPool — elastic pool that creates new threads as needed and reuses idle ones, terminating threads that stay idle too long; good for many short-lived, bursty tasks.
  • SingleThreadExecutor — a single worker thread executing tasks sequentially in submission order; good when tasks must never run concurrently with each other.
  • ScheduledThreadPool — supports delayed and periodic task execution (schedule(), scheduleAtFixedRate(), scheduleWithFixedDelay()).

Q5. What is the difference between CAS (Compare-And-Swap) and lock-based synchronization? Explain the ABA problem.

CAS is a lock-free, hardware-supported atomic operation (used internally by AtomicInteger and ConcurrentHashMap) that atomically compares a memory location's current value to an expected value and, if they match, swaps in a new value — all as one indivisible CPU instruction. If another thread changed the value in the meantime, the CAS simply fails and the caller retries, rather than blocking. This avoids context-switch overhead under low contention, but can waste CPU cycles retrying under high contention, where a lock might actually perform better.

The ABA problem occurs when a value changes from A to B and back to A between a thread's initial read and its later CAS attempt: the CAS succeeds because the value matches what was expected (A), even though the value did in fact change in between — which can be incorrect if the intermediate change mattered (e.g. a linked-list node was freed and reused). It's solved with AtomicStampedReference, which pairs the value with a version stamp that increments on every change, so a CAS can detect that the value went A → B → A even though the final value looks unchanged.

Q6. What are Virtual Threads (Project Loom, Java 21), and how do they differ from platform threads?

Virtual threads are lightweight, JVM-managed threads multiplexed onto a small pool of “carrier” platform (OS) threads, rather than being mapped one-to-one onto an OS thread the way traditional platform threads are. When a virtual thread blocks on I/O, the JVM “unmounts” it from its carrier thread — freeing that carrier to run a different virtual thread — rather than blocking an entire OS thread for the duration. This enables applications to run millions of concurrent virtual threads using simple, familiar blocking-style code, instead of needing complex reactive/async pipelines purely to conserve OS threads. Virtual threads are ideal for high-throughput, I/O-bound workloads (web request handling, calling downstream services); they offer no benefit for CPU-bound work, since a CPU-bound virtual thread still occupies its carrier thread for its entire computation.

Q7. Design a thread-safe bounded cache with per-entry TTL (time-to-live) expiration.

Problem statement: Design a cache that supports put/get operations, enforces a maximum entry count (evicting the oldest entry when full), and expires individual entries after a configurable time-to-live, all safely under concurrent access.

package com.interviewguide.concurrency;
 
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.locks.ReentrantReadWriteLock;
 
public class ExpiringCache<KeyType, ValueType> {
 
    private static class CacheEntry<ValueType> {
        final ValueType storedValue;
        final long expirationTimeMillis;
 
        CacheEntry(ValueType storedValue, long expirationTimeMillis) {
            this.storedValue = storedValue;
            this.expirationTimeMillis = expirationTimeMillis;
        }
 
        boolean isExpired() {
            return System.currentTimeMillis() > expirationTimeMillis;
        }
    }
 
    private final int maximumCapacity;
    // LinkedHashMap with access-order=true gives a simple LRU eviction base
    private final LinkedHashMap<KeyType, CacheEntry<ValueType>> internalStorage;
    private final ReentrantReadWriteLock accessLock = new ReentrantReadWriteLock();
 
    public ExpiringCache(int maximumCapacity) {
        this.maximumCapacity = maximumCapacity;
        this.internalStorage = new LinkedHashMap<>(16, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<KeyType, CacheEntry<ValueType>> eldest) {
                return size() > maximumCapacity; // evict oldest when over capacity
            }
        };
    }
 
    public void putEntry(KeyType entryKey, ValueType entryValue, long timeToLiveMillis) {
        accessLock.writeLock().lock();
        try {
            long expirationTime = System.currentTimeMillis() + timeToLiveMillis;
            internalStorage.put(entryKey, new CacheEntry<>(entryValue, expirationTime));
        } finally {
            accessLock.writeLock().unlock();
        }
    }
 
    public Optional<ValueType> getEntry(KeyType entryKey) {
        accessLock.writeLock().lock(); // write lock: access-order mutates the map's internal ordering
        try {
            CacheEntry<ValueType> foundEntry = internalStorage.get(entryKey);
            if (foundEntry == null || foundEntry.isExpired()) {
                internalStorage.remove(entryKey); // lazy eviction on read
                return Optional.empty();
            }
            return Optional.of(foundEntry.storedValue);
        } finally {
            accessLock.writeLock().unlock();
        }
    }
}

Note: Note: getEntry() must take the write lock (not a read lock) because LinkedHashMap's access-order mode mutates its internal linked-list ordering on every get(), so a concurrent "read" is not actually read-only here.

Section 3: Advanced Concurrency & Memory Model (Rapid-Fire)

Building on Section 1 (JMM, volatile, ConcurrentHashMap internals, locks, ThreadLocal, CompletableFuture) and Section 2 (CAS/ABA, virtual threads, BlockingQueue), the following questions add the remaining nuances.

Q1. Can volatile make a non-atomic operation atomic? What guarantees does volatile actually provide?

In one specific case, yes: reads and writes of long and double. These 64-bit primitives may, per the JVM specification, be split into two 32-bit operations when non-volatile, so a thread could observe a “torn” value (half old, half new). Declaring the field volatile guarantees each 64-bit read or write is a single atomic operation.

More broadly, volatile provides visibility and ordering. A write is immediately visible to every thread that subsequently reads the field (the happens-before relationship), and the compiler, JVM, and CPU may not reorder the volatile access relative to surrounding statements. The JMM effectively inserts a write barrier after a volatile write and a read barrier before a volatile read, so a reader also sees every write the writer made before the volatile write. Practical uses: atomic long/double access, simple shared flags such as a shutdown signal, and safe publication in double-checked locking.

Q2. Should wait() be called inside an if or a loop? Why?

Always a loop. Between being notified and actually reacquiring the lock, the condition may no longer hold because another thread got there first (and spurious wakeups can also occur). Re-testing the condition on every wake-up protects against this.

synchronized (sharedLockObject) {
    while (!conditionHolds()) {
        sharedLockObject.wait(); // releases the lock; reacquires it automatically on wakeup
    }
    // the condition is now guaranteed true -- safe to proceed
}

Q3. Is synchronization fundamentally harder for 10 threads than for 2?

Not in code mechanics — synchronized, wait(), and notify() work identically. What changes is the strategy: more threads means more lock contention, which can push you toward techniques such as lock striping (splitting one lock into several, each guarding a partition of the data).

Q4. What is false sharing, and how do you avoid it?

On multi-core CPUs, each core has its own cache. False sharing occurs when threads on different cores modify separate variables that happen to sit on the same cache line (typically 64 bytes). The coherency protocol treats the whole line as a unit, so one core's write invalidates the line for the other core, forcing costly reloads despite no real data dependency. It is notoriously hard to detect. Mitigate by padding or aligning heavily contended fields onto separate cache lines, or with the JDK-internal @Contended annotation.

Problem statement: Keep two threads' counters from invalidating each other's cache lines by padding each counter.

public class PaddedCounter {
    // 7 long padding fields isolate the counter on its own cache line
    private long padding1, padding2, padding3, padding4, padding5, padding6, padding7;
    private volatile long counterValue;
 
    public void incrementCounter() {
        counterValue++;
    }
 
    public long getCounterValue() {
        return counterValue;
    }
}
// Two threads updating separate PaddedCounter instances no longer invalidate
// each other's CPU cache lines, improving throughput.

Q5. What is busy-spinning, and when should you use it?

Busy-spinning waits for an event by looping on a condition without releasing the CPU or sleeping, avoiding the loss of CPU cache state that occurs when a paused thread resumes (possibly on another core). It only pays off for very short expected waits (microseconds to low milliseconds); otherwise the wasted cycles outweigh the benefit. Low-latency trading systems are the classic use — the LMAX Disruptor's BusySpinWaitStrategy is built on this idea.

Q6. Explain happens-before, memory fences, and why double-checked locking fails without volatile.

Happens-before is a partial ordering guaranteeing that writes before a point are visible after it; without it the JMM permits arbitrary reordering under the as-if-serial rule. Key sources: program order within a thread; a volatile write happens-before a subsequent volatile read of the same field; a monitor unlock happens-before the next lock of that monitor; Thread.start() happens-before the started thread's actions; and a thread's actions happen-before another thread's join() returns.

A memory fence prevents reordering across it. The four reordering types are LoadLoad, StoreStore, LoadStore, and StoreLoad (the most expensive to prevent). A volatile write inserts StoreStore and LoadStore barriers before it and a StoreLoad barrier after.

Double-checked locking fails without volatile because object construction is not atomic from the JVM's view: the JIT or CPU can publish the reference before the constructor finishes, so a second thread can read a non-null reference to a half-initialized object. volatile's barrier forces the object to be fully constructed before the reference becomes visible (see Part 1, Section 9, Q4).

Q7. Why is Thread.stop() deprecated, and how do you cancel a thread safely?

Thread.stop() kills a thread at an arbitrary point, releasing monitors mid-update and leaving shared objects in an inconsistent, corrupted state with no guarantee of cleanup. The safe alternative is cooperative cancellation: set a volatile boolean flag or call Thread.interrupt(); the task checks periodically (or is unblocked from a blocking call by an InterruptedException) and exits cleanly on its own terms.

Q8. What is a livelock, and how does it differ from a deadlock? What is reentrancy?

In a deadlock, threads are blocked and make no progress. In a livelock, threads stay active and keep changing state in response to each other (for example, both repeatedly backing off and retrying) but never make forward progress, burning CPU. Prevent it with randomized backoff or a strict resource-acquisition ordering/priority scheme that breaks the symmetric retry.

Java's intrinsic locks (synchronized) and ReentrantLock are reentrant: a thread already holding a lock can re-acquire it (e.g. calling another synchronized method on the same object) without blocking, tracked by a per-thread hold count decremented on each exit. A naive non-reentrant lock would deadlock a thread against itself in that scenario.

Q9. How does the fork/join framework achieve work stealing?

ForkJoinPool gives each worker thread its own double-ended work queue. A thread pushes and pops tasks from the head of its own queue (LIFO, cache-friendly), but when idle it steals from the tail of another thread's queue (FIFO, minimizing contention with the owner). This suits recursive divide-and-conquer workloads with uneven task sizes, since idle threads rebalance load automatically without a central coordinator.

Figure: Fork/Join work stealing

Q10. How do CompletableFuture's handle(), exceptionally(), and whenComplete() differ? What production practices apply?

  • exceptionally() runs only on failure, supplies a recovery value, and is skipped entirely on success.
  • handle() always runs, receiving either the result or the exception (one is null), and can transform either path into a new result.
  • whenComplete() always runs but cannot alter the result; it only observes (useful for logging) and passes the original outcome through unless it itself throws.

Production practices: always supply a custom Executor (the default ForkJoinPool.commonPool() is shared JVM-wide and can starve under load); always set timeouts (orTimeout / completeOnTimeout) so pipelines can't hang indefinitely; and propagate correlation/trace IDs through the chain with structured logging, since async code is harder to debug.

CompletableFuture<UserProfile> userProfilePipeline =
        CompletableFuture.supplyAsync(() -> fetchUser(userId), customExecutor)
                // thenCompose chains a dependent async call, avoiding nested futures
                .thenCompose(user -> fetchOrdersAsync(user.getId())
                        .thenApply(orders -> enrich(user, orders)))
                .exceptionally(pipelineError -> {
                    log.error("Pipeline failed for user {}", userId, pipelineError);
                    return UserProfile.fallback(userId);
                })
                .orTimeout(2, TimeUnit.SECONDS); // never hang indefinitely
 
userProfilePipeline.thenAccept(profile -> render(profile));

Q11. How does biased locking work, and why was it removed?

Biased locking (pre-Java 15) optimistically assumes a monitor will be locked repeatedly by the same thread, storing that thread's ID in the object header so re-entry needs only a fast ID comparison rather than a CAS. It was disabled by default in Java 15+ because modern JIT lock elision (via escape analysis) and cheap hardware CAS instructions made the header-state complexity and expensive revocation (when the bias assumption is violated) no longer worthwhile.

Q12. Why can HashMap's resize cause an infinite loop or lost data in multithreaded code?

Pre-Java 8 HashMap rebuilt each bucket's linked list by re-inserting nodes during resize; concurrent structural modification could reverse a bucket's node order across two racing threads, creating a circular reference (an infinite loop on the next traversal) or silently dropping entries. Java 8 preserves relative order and splits buckets in place, reducing but not eliminating the risk: HashMap remains fundamentally not thread-safe, and ConcurrentHashMap must be used for concurrent access.

Section 4: JVM Internals & Garbage Collection

Q1. What are the JVM memory areas (heap, stack, metaspace), and what is the difference between stack and heap?

  • Heap — stores all objects (created via new) and instance variables; shared across all threads; the area garbage collection manages. Divided into Young Generation (Eden + Survivor spaces) and Old (Tenured) Generation.
  • Stack — stores method frames, local variables, and partial results; one per thread, so never shared between threads and inherently thread-safe; typically much smaller than the heap; space is reclaimed automatically as each method returns.
  • Metaspace (Java 8+, replacing PermGen) — stores class metadata, static variables, and the runtime constant pool, using native memory rather than the heap.

Figure: JVM memory areas

Q2. What is garbage collection, and how do generations work?

Garbage collection is the JVM's automatic reclamation of heap memory for objects no longer reachable from any GC root. Production collectors use a generational strategy based on the observation that most objects die young: new objects are allocated in the Young Generation and collected frequently via cheap minor GCs (copying algorithms); objects that survive enough minor collections are promoted to the Old Generation, which is collected less often by more expensive major/full GCs. Focusing effort on the young generation avoids scanning the entire heap.

Figure: Generational garbage collection flow

Q3. What are GC roots?

GC roots are the starting points the collector uses to decide reachability; any object not reachable from a root (directly or through a chain of references) is eligible for collection. Kinds of roots:

  • Class — classes loaded by the system class loader; never unloaded and can hold objects alive via static fields.
  • Thread — currently live threads.
  • Stack Local — local variables and parameters on a Java method's call stack.
  • JNI Local / JNI Global — references held by native code.
  • Monitor Used — objects currently used as a synchronization monitor.
  • Held by JVM — objects the JVM itself keeps alive (system class loader, certain built-in exception classes); the exact set is implementation-specific.

Figure: GC roots and reachability

Q4. Compare the Serial, Parallel, G1, ZGC, and Shenandoah collectors. How would you choose one for a low-latency banking system?

  • Serial — single GC thread, stop-the-world; suits small heaps or single-CPU environments.
  • Parallel — multiple GC threads, stop-the-world; maximizes throughput with longer pauses, good for batch jobs.
  • G1 (Garbage First) — default since Java 9; region-based heap that collects the regions with the most garbage first; configurable pause target (-XX:MaxGCPauseMillis); a good general-purpose choice, though very large heaps can still see pauses of tens of milliseconds.
  • ZGC (production-ready since Java 15) — targets sub-millisecond pauses regardless of heap size (tested to multi-terabyte) using colored pointers and load barriers to do nearly all work concurrently.
  • Shenandoah — similar goal to ZGC (concurrent compaction) with different mechanics (Brooks pointers).

For a latency-sensitive banking or trading system with strict pause SLAs (e.g. sub-5ms p99), choose ZGC (for example -XX:+UseZGC -Xmx16g -XX:+ZGenerational), accepting a modest throughput cost. For typical microservices where 50–100ms pauses are acceptable and throughput matters slightly more, G1 is the better fit. Before switching in production: baseline with GC logs (-Xlog:gc*), load test with production-like traffic, and roll out via canary rather than big-bang.

Design discussion: tuning GC for a low-latency service (sub-5ms pauses, 16GB heap, high allocation rate)

  • Choose ZGC or Shenandoah for concurrent, pause-predictable collection.
  • Set -Xms equal to -Xmx to avoid resize pauses; pre-size the heap from load testing, not defaults.
  • Reduce the allocation rate: pool high-frequency short-lived objects, avoid autoboxing in hot paths, use primitive collections.
  • Enable Java Flight Recorder (JFR) continuously to capture allocation profiles and pause histograms.
  • Validate under realistic load and track p99/p999 pause times as the key SLO, not average throughput.

Note: For a tech-lead answer, add: document the GC decision and rationale in an ADR so the next engineer doesn't “helpfully” revert it during an unrelated incident.

Q5. Can you force garbage collection? How do you find memory usage from inside a program?

No. System.gc() or Runtime.gc() is only a hint; the JVM may ignore it. Runtime exposes basic statistics:

Runtime jvmRuntime = Runtime.getRuntime();
long freeMemoryBytes  = jvmRuntime.freeMemory();   // currently free memory
long totalMemoryBytes = jvmRuntime.totalMemory();  // total currently allocated to the JVM
long maxMemoryBytes   = jvmRuntime.maxMemory();    // maximum the JVM will attempt to use
long usedMemoryBytes  = totalMemoryBytes - freeMemoryBytes;
double percentHeapUsed = (usedMemoryBytes * 100.0) / maxMemoryBytes;

Q6. Compare strong, soft, weak, and phantom references. How does WeakHashMap work?

  • Strong — the default; prevents GC while reachable.
  • Soft — not reclaimed while memory is not under pressure, but may be reclaimed before an OutOfMemoryError; ideal for memory-sensitive caches.
  • Weak — eligible for collection as soon as no strong references remain, regardless of memory pressure.
  • Phantom — enqueued after finalization; used for cleanup actions after the object is finalized but before memory is reclaimed.

WeakHashMap behaves like a HashMap but holds its keys via WeakReference: if a key has no other strong references, that entry is automatically removed — useful for caches keyed by objects whose lifecycle the cache shouldn't control.

Q7. What is -XX:+UseCompressedOops, and what are the heap limits of 32-bit vs. 64-bit JVMs?

Moving from a 32-bit to a 64-bit JVM doubles the size of object pointers, inflating heap usage and reducing how much useful data fits in CPU cache. -XX:+UseCompressedOops lets the JVM represent references with a compressed 32-bit encoding (valid for heaps up to roughly 32GB), recovering most of that efficiency. A 32-bit JVM can theoretically address 4GB but practically much less (historically ~1.5GB on Windows, ~3GB on some Solaris setups); a 64-bit JVM practically supports 100GB+ heaps, and specialized JVMs (e.g. Azul's) have supported terabyte-scale heaps. To check the architecture at runtime, read the sun.arch.data.model (or os.arch) system property.

Q8. What is the difference between JRE, JDK, JVM, and JIT? How does tiered compilation (C1 vs. C2) work?

  • JRE — everything needed to run a Java application (JVM + core libraries), without development tools.
  • JDK — a superset of the JRE adding development tools, chiefly the javac compiler.
  • JVM — the engine that executes compiled bytecode and provides platform independence.
  • JIT — the JVM component that compiles frequently executed (“hot”) bytecode into native code at runtime.

Tiered compilation combines two compilers: C1 (the client compiler) compiles quickly with light optimization and lightweight profiling instrumentation; C2 (the server compiler) compiles slower but applies aggressive optimizations (inlining, loop unrolling, escape analysis). Methods start interpreted, are promoted to C1 once warm, and are recompiled by C2 once invocation/loop counters cross a threshold — balancing fast startup with peak throughput.

Q9. What happens when you run “java MyApp”, from class loading to execution? What are the three built-in class loaders?

Class loading follows a parent-first delegation model, which stops core classes from being overridden and prevents security issues. The Bootstrap ClassLoader loads core JDK classes (java.lang.*); the Extension/Platform ClassLoader loads classes from extension directories; the Application/System ClassLoader loads classes from the application classpath.

Loading proceeds in three phases: Loading (read the bytecode), Linking (verify the bytecode, prepare static fields with defaults, resolve symbolic references), and Initialization (run static initializers). The JVM then interprets main(), and the JIT compiles hot paths identified by invocation counters.

Figure: Class loading process

Q10. What causes a StackOverflowError vs. an OutOfMemoryError?

StackOverflowError occurs when the call stack exceeds its size limit, typically from unbounded or infinitely deep recursion. OutOfMemoryError occurs when the heap (or metaspace) cannot allocate more objects/classes even after GC attempts — caused by memory leaks, an undersized heap, or genuinely excessive object retention.

Q11. What is escape analysis, and how does it enable stack allocation, scalar replacement, and lock elision?

Escape analysis is a JIT optimization that determines whether an object's reference escapes the method or thread that created it. If it provably doesn't, the JIT can allocate the object on the stack, or apply scalar replacement (decomposing it into individual primitive fields held in registers), eliminating heap allocation and GC pressure entirely. It also enables lock elision: unnecessary synchronized locks on a non-escaping object can be removed, since no other thread could ever observe or contend for that lock.

Q12. What is a safepoint, and why can it cause unpredictable GC pause delays?

A safepoint is a point where all threads have a consistent, known state, required for stop-the-world operations such as GC. The JVM inserts safepoint polls at loop back-edges and method returns; a thread stuck in a tight loop without a poll (for example, a counted loop the JIT over-optimized) can delay the whole JVM from reaching a global safepoint, producing unexpectedly long pauses.

Q13. What are G1's remembered sets and card tables, and why are they needed?

G1 divides the heap into regions and must track cross-region references (e.g. an old-region object pointing to a young-region object) without scanning the whole heap during a young collection. Each region keeps a remembered set of incoming references from other regions. These are populated incrementally via a card table — a byte array marking 512-byte heap chunks as “dirty” when a reference inside them is mutated — using a write barrier on every reference store.

Q14. How do you diagnose a production memory leak in a live JVM without restarting it? What is the difference between a heap dump and a thread dump?

Take a heap dump with jcmd <pid> GC.heap_dump and analyze it in Eclipse MAT, looking at the dominator tree for retained-size hotspots and GC-root reference paths. Cross-check jstat -gcutil to see whether Old Gen keeps climbing despite full GCs, and compare heap histograms over time (jmap -histo:live). For continuous production monitoring prefer low-overhead tools such as async-profiler and JFR, since heap dumps pause the JVM.

A heap dump is a snapshot of all live objects and their reference graph, used for memory leaks and excessive retention. A thread dump captures every thread's stack trace and state (RUNNABLE, BLOCKED, WAITING), used to diagnose deadlocks, contention, or hung threads — taken via jstack <pid>, kill -3 <pid> on Linux/Unix, or Ctrl+Break on Windows.

Java VisualVM (jvisualvm, bundled in the JDK's bin directory) consolidates JConsole, jstat, jinfo, jstack, and jmap into one GUI: heap dumps, MBeans, live GC monitoring per memory pool (via the Visual GC plugin), and CPU/memory profiling. A healthy heap graph shows a regular sawtooth (climbing as objects are allocated, dropping sharply after GC); a baseline that keeps rising and never falls after a full GC strongly suggests a leak.

Q15. What are common JVM tuning flags?

  • -Xms / -Xmx — initial and maximum heap size; setting them equal avoids resize overhead.
  • -XX:+UseG1GC — selects the G1 collector.
  • -XX:MaxGCPauseMillis — sets a target pause-time goal.
  • -Xss — per-thread stack size.
  • -XX:MetaspaceSize — initial metaspace sizing.

Q16. What causes memory leaks in Java despite garbage collection?

A leak occurs whenever an object stays reachable from a GC root longer than intended. Common patterns:

  • Static fields holding references — static fields are GC roots (via the Class root), so anything reachable through them lives as long as the class is loaded.
  • Calling String.intern() on many distinct, large strings, bloating the string pool in a way that's hard to reverse.
  • Unclosed streams, connections, and sockets — fix with try-with-resources.
  • Native/JNI allocations invisible to the garbage collector: the heap looks healthy while the process footprint grows.
  • Objects stored in long-lived application scope (e.g. ServletContext attributes) and never removed.
  • Listener/callback registrations never removed, and ThreadLocal misuse in pooled threads (see Section 1).
  • Non-static inner classes, which implicitly hold their enclosing instance: a long-lived inner-class listener keeps the outer object alive. Lambdas capture only the variables they use (and this only if instance members are referenced), which often reduces accidental retention.
  • Inappropriate JVM options that disable class unloading (a historical example: noclassgc on some old IBM JDKs), problematic for application servers loading many classes.
// Leak: this static list lives for the whole application lifetime,
// and anything added to it is never eligible for garbage collection
class ConfigurationCache {
    static final ArrayList<Object> cachedItems = new ArrayList<>(100);
}
 
// Fix for unclosed resources: try-with-resources closes the reader even on exceptions
try (BufferedReader fileReader = new BufferedReader(new FileReader(inputFile))) {
    // ... use fileReader ...
} catch (Exception readException) {
    readException.printStackTrace();
}

Note: Rule of thumb: use static final for true constants or thread-safe immutable shared objects; for per-instance state prefer a plain final instance field, and minimize mutable state generally.

Q17. How does a JDBC connection pool work?

A pool front-loads the expensive work of establishing database connections so application code never pays that cost on the request path:

  • 1. At startup the pool creates a predetermined number of physical Connection objects and holds them.
  • 2. Application code looks up a DataSource (often via JNDI in Java EE) and calls getConnection() — exactly the same code as with a non-pooled DataSource.
  • 3. The pool returns a lightweight Connection handle wrapping an underlying PooledConnection.
  • 4. When code calls close() on the handle, the pool intercepts the event (PooledConnection supports event listeners) and performs a “pseudo-close”: the physical connection returns to the pool for reuse after housekeeping such as resetting state.
  • 5. The real connection is only closed when the pool retires it — at orderly shutdown or when it is found broken.

This is transparent to application code. Many pools also pool PreparedStatement objects through an analogous StatementEventListener mechanism, avoiding repeated re-preparation of the same SQL.
