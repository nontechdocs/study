Section 2: Java Serialization

Q1. How do you exclude fields from serialization, and which kinds of fields are typically transient?

Declare them transient. The default serialization mechanism skips them, and on deserialization they revert to their type's default (null / 0 / false). Typical transient fields are those that cannot be meaningfully serialized or should not be persisted for security reasons:

  • Logger references, file handles, and I/O streams (live runtime/OS resources).
  • Auditing or exception-handling helper instances (runtime-context specific).
  • Security-sensitive data such as passwords and raw cryptographic keys, to keep them out of a byte stream that might be logged, cached, or transmitted insecurely.
public class UserSession implements Serializable {
    private String username;                  // serialized normally
    private transient Connection dbConnection; // NOT serialized: live resource
}

Q2. Are static variables serialized?

No. Static variables belong to the class, not to any instance, and serialization only captures instance state. To preserve a static value you must do so explicitly by writing/reading it yourself inside custom writeObject()/readObject() methods.

Q3. How do you implement custom serialization, and how does Serializable differ from Externalizable?

Serializable is a marker interface that opts a class into Java's built-in, reflection-based default serialization — convenient, but relatively expensive, fragile, and offering limited control over the byte format. There are two ways to customize:

  • Implement Externalizable: you must write writeExternal(ObjectOutput) and readExternal(ObjectInput) yourself, giving complete control, generally better performance, and room for extra validation — nothing happens automatically.
  • Keep Serializable but add private writeObject(ObjectOutputStream) and readObject(ObjectInputStream) methods; the default mechanism calls them if present, while you can still delegate to defaultWriteObject()/defaultReadObject() for the fields you don't customize.

Problem statement: Serialize a record normally but rebuild a derived (transient) summary field on deserialization.

public class AuditableRecord implements Serializable {
    private String recordId;
    private transient String computedSummary; // recomputed on read, not stored
 
    private void writeObject(java.io.ObjectOutputStream outputStream) throws IOException {
        outputStream.defaultWriteObject(); // serializes all non-transient fields normally
    }
 
    private void readObject(java.io.ObjectInputStream inputStream)
            throws IOException, ClassNotFoundException {
        inputStream.defaultReadObject();            // restores non-transient fields
        this.computedSummary = recomputeSummary();  // rebuild the transient field
    }
 
    private String recomputeSummary() {
        return "Summary for " + recordId;
    }
}

Section 3: Hibernate & SQL Basics

Q1. How do you generate a primary key (auto-generated ID) in Hibernate?

Use the @GeneratedValue annotation's strategy attribute:

  • GenerationType.AUTO — Hibernate picks a strategy based on the database dialect.
  • GenerationType.IDENTITY — relies on the database's auto-increment/identity column (e.g. MySQL AUTO_INCREMENT).
  • GenerationType.SEQUENCE — uses a database sequence object (common on Oracle, PostgreSQL).
  • GenerationType.TABLE — emulates a sequence using a dedicated table; portable but slower.
  • hilo — a Hibernate-specific “high/low” algorithm that reserves blocks of IDs in memory to minimize database round trips.
@Entity
public class Employee {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long employeeId;
    // other fields...
}

Note: Letting Hibernate assign IDs suits simple cases and testing. For performance-sensitive or portable systems, prefer an explicitly managed sequence or an application-assigned UUID; AUTO's behavior can vary between Hibernate versions and dialects.

Q2. How do you select columns from two tables that share a common field?

Use a SQL join. An INNER JOIN returns only rows with a match in both tables; a LEFT JOIN also returns employees with no matching department row.

-- INNER JOIN: only employees whose dept_id exists in department
SELECT e.emp_name, e.dept_id, d.dept_name
FROM employee e
INNER JOIN department d ON e.dept_id = d.dept_id;
 
-- LEFT JOIN: also keeps employees with a null/unknown dept_id
SELECT e.emp_name, e.dept_id, d.dept_name
FROM employee e
LEFT JOIN department d ON e.dept_id = d.dept_id;

Section 4: Java Object Fundamentals & Lifecycle

Q1. What is an object, and what three steps does a statement like Human person = new Human() perform?

An object is an instance of a class — a bundle of state (fields) and behavior (methods). Car, Bird, and Human are classes; a specific car with a given license plate is an object. The single statement performs three steps: Declaration (the name refers to an object of type Human), Instantiation (the new operator allocates memory), and Initialization (the constructor runs to set the initial state).

Q2. Describe the seven states in a Java object's lifecycle.

  • 1. Created — memory is allocated; if immediately assigned to a variable, the object moves straight to In Use.
  • 2. In Use — held by at least one strong reference (the default kind, as opposed to Weak/Soft/Phantom).
  • 3. Invisible — no strong reference is accessible from the currently executing program logic, even though one may technically still exist (e.g. a field that will never be read again).
  • 4. Unreachable — no strong reference exists from any GC root (local variables on a thread stack, active static fields, JNI references).
  • 5. Collected — the GC recognizes it as unreachable; if the class overrides finalize(), it is marked for that call.
  • 6. Finalized — still unreachable after finalize() ran, now awaiting deallocation.
  • 7. Deallocated — memory is reclaimed and made available for future allocations.

Note: Do not rely on finalize() to release important resources: there is no guarantee when (or if) it runs, and a finalizer can extend an object's lifetime and increase GC work. Prefer try-with-resources and AutoCloseable.

Section 5: JVM Internals & Garbage Collection

Q1. What are the JVM memory areas (heap, stack, metaspace), and what is the difference between stack and heap?

  • Heap — stores all objects (created via new) and instance variables; shared across all threads; the area garbage collection manages. Divided into Young Generation (Eden + Survivor spaces) and Old (Tenured) Generation.
  • Stack — stores method frames, local variables, and partial results; one per thread, so never shared between threads and inherently thread-safe; typically much smaller than the heap; space is reclaimed automatically as each method returns.
  • Metaspace (Java 8+, replacing PermGen) — stores class metadata, static variables, and the runtime constant pool, using native memory rather than the heap.

Figure: JVM memory areas

Q2. What is garbage collection, and how do generations work?

Garbage collection is the JVM's automatic reclamation of heap memory for objects no longer reachable from any GC root. Production collectors use a generational strategy based on the observation that most objects die young: new objects are allocated in the Young Generation and collected frequently via cheap minor GCs (copying algorithms); objects that survive enough minor collections are promoted to the Old Generation, which is collected less often by more expensive major/full GCs. Focusing effort on the young generation avoids scanning the entire heap.

Figure: Generational garbage collection flow

Q3. What are GC roots?

GC roots are the starting points the collector uses to decide reachability; any object not reachable from a root (directly or through a chain of references) is eligible for collection. Kinds of roots:

  • Class — classes loaded by the system class loader; never unloaded and can hold objects alive via static fields.
  • Thread — currently live threads.
  • Stack Local — local variables and parameters on a Java method's call stack.
  • JNI Local / JNI Global — references held by native code.
  • Monitor Used — objects currently used as a synchronization monitor.
  • Held by JVM — objects the JVM itself keeps alive (system class loader, certain built-in exception classes); the exact set is implementation-specific.

Figure: GC roots and reachability

Q4. Compare the Serial, Parallel, G1, ZGC, and Shenandoah collectors. How would you choose one for a low-latency banking system?

  • Serial — single GC thread, stop-the-world; suits small heaps or single-CPU environments.
  • Parallel — multiple GC threads, stop-the-world; maximizes throughput with longer pauses, good for batch jobs.
  • G1 (Garbage First) — default since Java 9; region-based heap that collects the regions with the most garbage first; configurable pause target (-XX:MaxGCPauseMillis); a good general-purpose choice, though very large heaps can still see pauses of tens of milliseconds.
  • ZGC (production-ready since Java 15) — targets sub-millisecond pauses regardless of heap size (tested to multi-terabyte) using colored pointers and load barriers to do nearly all work concurrently.
  • Shenandoah — similar goal to ZGC (concurrent compaction) with different mechanics (Brooks pointers).

For a latency-sensitive banking or trading system with strict pause SLAs (e.g. sub-5ms p99), choose ZGC (for example -XX:+UseZGC -Xmx16g -XX:+ZGenerational), accepting a modest throughput cost. For typical microservices where 50–100ms pauses are acceptable and throughput matters slightly more, G1 is the better fit. Before switching in production: baseline with GC logs (-Xlog:gc*), load test with production-like traffic, and roll out via canary rather than big-bang.

Design discussion: tuning GC for a low-latency service (sub-5ms pauses, 16GB heap, high allocation rate)

  • Choose ZGC or Shenandoah for concurrent, pause-predictable collection.
  • Set -Xms equal to -Xmx to avoid resize pauses; pre-size the heap from load testing, not defaults.
  • Reduce the allocation rate: pool high-frequency short-lived objects, avoid autoboxing in hot paths, use primitive collections.
  • Enable Java Flight Recorder (JFR) continuously to capture allocation profiles and pause histograms.
  • Validate under realistic load and track p99/p999 pause times as the key SLO, not average throughput.

Note: For a tech-lead answer, add: document the GC decision and rationale in an ADR so the next engineer doesn't “helpfully” revert it during an unrelated incident.

Q5. Can you force garbage collection? How do you find memory usage from inside a program?

No. System.gc() or Runtime.gc() is only a hint; the JVM may ignore it. Runtime exposes basic statistics:

Runtime jvmRuntime = Runtime.getRuntime();
long freeMemoryBytes  = jvmRuntime.freeMemory();   // currently free memory
long totalMemoryBytes = jvmRuntime.totalMemory();  // total currently allocated to the JVM
long maxMemoryBytes   = jvmRuntime.maxMemory();    // maximum the JVM will attempt to use
long usedMemoryBytes  = totalMemoryBytes - freeMemoryBytes;
double percentHeapUsed = (usedMemoryBytes * 100.0) / maxMemoryBytes;

Q6. Compare strong, soft, weak, and phantom references. How does WeakHashMap work?

  • Strong — the default; prevents GC while reachable.
  • Soft — not reclaimed while memory is not under pressure, but may be reclaimed before an OutOfMemoryError; ideal for memory-sensitive caches.
  • Weak — eligible for collection as soon as no strong references remain, regardless of memory pressure.
  • Phantom — enqueued after finalization; used for cleanup actions after the object is finalized but before memory is reclaimed.

WeakHashMap behaves like a HashMap but holds its keys via WeakReference: if a key has no other strong references, that entry is automatically removed — useful for caches keyed by objects whose lifecycle the cache shouldn't control.

Q7. What is -XX:+UseCompressedOops, and what are the heap limits of 32-bit vs. 64-bit JVMs?

Moving from a 32-bit to a 64-bit JVM doubles the size of object pointers, inflating heap usage and reducing how much useful data fits in CPU cache. -XX:+UseCompressedOops lets the JVM represent references with a compressed 32-bit encoding (valid for heaps up to roughly 32GB), recovering most of that efficiency. A 32-bit JVM can theoretically address 4GB but practically much less (historically ~1.5GB on Windows, ~3GB on some Solaris setups); a 64-bit JVM practically supports 100GB+ heaps, and specialized JVMs (e.g. Azul's) have supported terabyte-scale heaps. To check the architecture at runtime, read the sun.arch.data.model (or os.arch) system property.

Q8. What is the difference between JRE, JDK, JVM, and JIT? How does tiered compilation (C1 vs. C2) work?

  • JRE — everything needed to run a Java application (JVM + core libraries), without development tools.
  • JDK — a superset of the JRE adding development tools, chiefly the javac compiler.
  • JVM — the engine that executes compiled bytecode and provides platform independence.
  • JIT — the JVM component that compiles frequently executed (“hot”) bytecode into native code at runtime.

Tiered compilation combines two compilers: C1 (the client compiler) compiles quickly with light optimization and lightweight profiling instrumentation; C2 (the server compiler) compiles slower but applies aggressive optimizations (inlining, loop unrolling, escape analysis). Methods start interpreted, are promoted to C1 once warm, and are recompiled by C2 once invocation/loop counters cross a threshold — balancing fast startup with peak throughput.

Q9. What happens when you run “java MyApp”, from class loading to execution? What are the three built-in class loaders?

Class loading follows a parent-first delegation model, which stops core classes from being overridden and prevents security issues. The Bootstrap ClassLoader loads core JDK classes (java.lang.*); the Extension/Platform ClassLoader loads classes from extension directories; the Application/System ClassLoader loads classes from the application classpath.

Loading proceeds in three phases: Loading (read the bytecode), Linking (verify the bytecode, prepare static fields with defaults, resolve symbolic references), and Initialization (run static initializers). The JVM then interprets main(), and the JIT compiles hot paths identified by invocation counters.

Q10. What causes a StackOverflowError vs. an OutOfMemoryError?

StackOverflowError occurs when the call stack exceeds its size limit, typically from unbounded or infinitely deep recursion. OutOfMemoryError occurs when the heap (or metaspace) cannot allocate more objects/classes even after GC attempts — caused by memory leaks, an undersized heap, or genuinely excessive object retention.

Q11. What is escape analysis, and how does it enable stack allocation, scalar replacement, and lock elision?

Escape analysis is a JIT optimization that determines whether an object's reference escapes the method or thread that created it. If it provably doesn't, the JIT can allocate the object on the stack, or apply scalar replacement (decomposing it into individual primitive fields held in registers), eliminating heap allocation and GC pressure entirely. It also enables lock elision: unnecessary synchronized locks on a non-escaping object can be removed, since no other thread could ever observe or contend for that lock.

Q12. What is a safepoint, and why can it cause unpredictable GC pause delays?

A safepoint is a point where all threads have a consistent, known state, required for stop-the-world operations such as GC. The JVM inserts safepoint polls at loop back-edges and method returns; a thread stuck in a tight loop without a poll (for example, a counted loop the JIT over-optimized) can delay the whole JVM from reaching a global safepoint, producing unexpectedly long pauses.

Q13. What are G1's remembered sets and card tables, and why are they needed?

G1 divides the heap into regions and must track cross-region references (e.g. an old-region object pointing to a young-region object) without scanning the whole heap during a young collection. Each region keeps a remembered set of incoming references from other regions. These are populated incrementally via a card table — a byte array marking 512-byte heap chunks as “dirty” when a reference inside them is mutated — using a write barrier on every reference store.

Q14. How do you diagnose a production memory leak in a live JVM without restarting it? What is the difference between a heap dump and a thread dump?

Take a heap dump with jcmd <pid> GC.heap_dump and analyze it in Eclipse MAT, looking at the dominator tree for retained-size hotspots and GC-root reference paths. Cross-check jstat -gcutil to see whether Old Gen keeps climbing despite full GCs, and compare heap histograms over time (jmap -histo:live). For continuous production monitoring prefer low-overhead tools such as async-profiler and JFR, since heap dumps pause the JVM.

A heap dump is a snapshot of all live objects and their reference graph, used for memory leaks and excessive retention. A thread dump captures every thread's stack trace and state (RUNNABLE, BLOCKED, WAITING), used to diagnose deadlocks, contention, or hung threads — taken via jstack <pid>, kill -3 <pid> on Linux/Unix, or Ctrl+Break on Windows.

Java VisualVM (jvisualvm, bundled in the JDK's bin directory) consolidates JConsole, jstat, jinfo, jstack, and jmap into one GUI: heap dumps, MBeans, live GC monitoring per memory pool (via the Visual GC plugin), and CPU/memory profiling. A healthy heap graph shows a regular sawtooth (climbing as objects are allocated, dropping sharply after GC); a baseline that keeps rising and never falls after a full GC strongly suggests a leak.

Q15. What are common JVM tuning flags?

  • -Xms / -Xmx — initial and maximum heap size; setting them equal avoids resize overhead.
  • -XX:+UseG1GC — selects the G1 collector.
  • -XX:MaxGCPauseMillis — sets a target pause-time goal.
  • -Xss — per-thread stack size.
  • -XX:MetaspaceSize — initial metaspace sizing.

Q16. What causes memory leaks in Java despite garbage collection?

A leak occurs whenever an object stays reachable from a GC root longer than intended. Common patterns:

  • Static fields holding references — static fields are GC roots (via the Class root), so anything reachable through them lives as long as the class is loaded.
  • Calling String.intern() on many distinct, large strings, bloating the string pool in a way that's hard to reverse.
  • Unclosed streams, connections, and sockets — fix with try-with-resources.
  • Native/JNI allocations invisible to the garbage collector: the heap looks healthy while the process footprint grows.
  • Objects stored in long-lived application scope (e.g. ServletContext attributes) and never removed.
  • Listener/callback registrations never removed, and ThreadLocal misuse in pooled threads (see Part 1).
  • Non-static inner classes, which implicitly hold their enclosing instance: a long-lived inner-class listener keeps the outer object alive. Lambdas capture only the variables they use (and this only if instance members are referenced), which often reduces accidental retention.
  • Inappropriate JVM options that disable class unloading (a historical example: noclassgc on some old IBM JDKs), problematic for application servers loading many classes.
// Leak: this static list lives for the whole application lifetime,
// and anything added to it is never eligible for garbage collection
class ConfigurationCache {
    static final ArrayList<Object> cachedItems = new ArrayList<>(100);
}
 
// Fix for unclosed resources: try-with-resources closes the reader even on exceptions
try (BufferedReader fileReader = new BufferedReader(new FileReader(inputFile))) {
    // ... use fileReader ...
} catch (Exception readException) {
    readException.printStackTrace();
}

Note: Rule of thumb: use static final for true constants or thread-safe immutable shared objects; for per-instance state prefer a plain final instance field, and minimize mutable state generally.

Q17. How does a JDBC connection pool work?

A pool front-loads the expensive work of establishing database connections so application code never pays that cost on the request path:

  • 1. At startup the pool creates a predetermined number of physical Connection objects and holds them.
  • 2. Application code looks up a DataSource (often via JNDI in Java EE) and calls getConnection() — exactly the same code as with a non-pooled DataSource.
  • 3. The pool returns a lightweight Connection handle wrapping an underlying PooledConnection.
  • 4. When code calls close() on the handle, the pool intercepts the event (PooledConnection supports event listeners) and performs a “pseudo-close”: the physical connection returns to the pool for reuse after housekeeping such as resetting state.
  • 5. The real connection is only closed when the pool retires it — at orderly shutdown or when it is found broken.

This is transparent to application code. Many pools also pool PreparedStatement objects through an analogous StatementEventListener mechanism, avoiding repeated re-preparation of the same SQL.

Section 6: Security

Application-Level Security Questions

Q1. What is the difference between authentication and authorization?

Authentication verifies identity (“who are you”) via credentials, tokens, or certificates. Authorization determines permissions (“what are you allowed to do”) after identity is established, checking roles/scopes against protected resources. Spring Security handles both: the AuthenticationManager for authentication, and access-control rules / AccessDecisionManager for authorization.

Q2. What is a JWT, and what is its structure?

A JSON Web Token is a compact, self-contained token for transmitting claims between parties, made of three Base64Url-encoded parts separated by dots: Header (algorithm and type), Payload (claims such as user ID and expiry), and Signature (verifies integrity using a secret or private key). Being stateless, servers avoid session storage, which suits scalable, distributed REST authentication.

Figure: JWT structure

Q3. What are XSS and CSRF, and how does Spring Security help prevent them?

XSS injects malicious scripts into pages viewed by other users; mitigate with output encoding/escaping and Content-Security-Policy headers. CSRF tricks an authenticated user's browser into submitting unintended requests; mitigate with anti-CSRF tokens tied to the user session. Spring Security enables CSRF protection by default for state-changing requests and provides header utilities to reduce XSS exposure.

Secure Coding Guidelines (Condensed)

Adapted and condensed from Oracle's “Secure Coding Guidelines for Java SE”; captures the most interview-relevant points from each major topic area.

0. Fundamentals

  • Prefer code that is obviously correct over code that merely has “no obvious flaws.”
  • Design APIs with security in mind from the start; e.g. marking a class final prevents a malicious subclass from overriding methods or adding a finalizer.
  • Avoid duplicating code or data; a security fix applied to one copy is easily missed in another.
  • Follow least privilege: run code with the minimum permissions it needs, shrinking the blast radius of any flaw.
  • Establish clear trust boundaries and validate/sanitize any data crossing one.
  • Check permissions once and hand out a capability rather than re-checking throughout a call chain; encapsulate with private fields and a minimal public interface.

1. Denial of Service

Untrusted input must never trigger resource consumption wildly disproportionate to the request. Attack patterns to defend against:

  • Enormous requested image/vector-graphic sizes; integer overflow bypassing a size check.
  • A small payload expanding into a huge in-memory object graph; “zip bombs” (cap the decompressed size directly, never trust compressed size or metadata).
  • The “billion laughs” XML entity-expansion attack (enable XMLConstants.FEATURE_SECURE_PROCESSING).
  • Hash-flooding (many colliding keys degrading O(n) to O(n²)); catastrophic regex backtracking; unbounded XPath cost.
  • Unbounded resource use during deserialization of untrusted data; infinite loops on corner-case input (ensure each iteration makes forward progress).

Always release resources even when an exception occurs (try-with-resources), and watch for integer overflow in limit checks: rearrange arithmetic so no addition can overflow.

// Vulnerable: current + extra can overflow for large values and wrongly pass the check
if (current + extra > max) { throw new IllegalArgumentException(); }
 
// Safe: rearranged so no addition can overflow
private void checkGrowBy(long extra) {
    if (extra < 0 || current > max - extra) {
        throw new IllegalArgumentException();
    }
}

2. Confidential Information

  • Strip sensitive details from exception messages and stack traces before they reach an untrusted caller or lower-privilege log.
  • Never log passwords, session tokens, or full card numbers, even at debug level.
  • For very sensitive in-memory data, overwrite it when no longer needed; Strings are immutable and can't be cleared, which is why password APIs prefer char[].

3. Injection and Inclusion

  • Never build SQL, HTML, XML, or shell commands by concatenating untrusted input; use PreparedStatement bind parameters and proper templating/serialization libraries.
  • Never pass untrusted data onto a command line (Runtime.exec / ProcessBuilder) without careful validation.
  • Disable DTD processing / external entity resolution when parsing untrusted XML (XXE).
  • Treat evaluating untrusted expressions or scripts (scripting engines, EL) like executing arbitrary code.
// Vulnerable: string concatenation allows SQL injection
String unsafeQuery = "SELECT * FROM accounts WHERE username = '" + userInput + "'";
 
// Safe: PreparedStatement handles escaping correctly
PreparedStatement safeStatement =
        connection.prepareStatement("SELECT * FROM accounts WHERE username = ?");
safeStatement.setString(1, userInput);

4. Accessibility and Extensibility

  • Default to private and widen access only when genuinely needed; limit package accessibility and avoid unrelated classes sharing a package.
  • Limit exposure of ClassLoader instances, and mark security-sensitive classes final: a malicious subclass can override behavior, add a finalizer to resurrect a “destroyed” object, or violate invariants.
  • Be careful calling overridable methods from a superclass, especially constructors.

5. Input Validation

  • Validate all input crossing a trust boundary, including values returned by untrusted/overridable code.
  • Wrap native (JNI) methods in a Java-level wrapper that validates input before reaching native code, which lacks the JVM's memory-safety guarantees.

6. Mutability

  • Prefer immutable value types; return defensive copies of mutable fields and copy mutable inputs before storing them.
  • Don't rely on == identity for objects supplied by untrusted code; treat data passed into and returned from untrusted objects as output and unvalidated input respectively.
  • Make public static fields final and truly constant; never expose mutable static state publicly.

7. Object Construction

  • Prefer factory methods for sensitive classes so extra checks can be enforced; actively prevent unauthorized construction where it is a security problem.
  • Defend against partially initialized instances, never call overridable methods from a constructor, and guard non-final classes against malicious clone().

8. Serialization and Deserialization

  • Avoid making security-sensitive classes serializable; serialization is an alternate construction path that bypasses constructors.
  • Guard sensitive fields with transient or custom writeObject()/readObject().
  • Treat deserialization exactly like construction from attacker-controlled bytes: all validation and defensive-copying concerns apply to readObject().

Note: Deserializing untrusted data has caused numerous serious vulnerabilities, including remote code execution. If you must, use an object-input filter (ObjectInputFilter, standard since Java 9) to restrict which classes may be deserialized.

9. Access Control

  • Understand how SecurityManager checks walk the call stack to determine the effective caller.
  • Use AccessController.doPrivileged() carefully: it says “this trusted code knowingly exercises its own privilege on behalf of a possibly less-privileged caller.”
  • Don't cache the result of a privileged operation and hand it to a caller who couldn't have triggered it; know that security context does not automatically transfer to new threads; and be aware that reflection (Method.invoke) can obscure who the “real” caller is.

Note: SecurityManager and the sandbox-style permission model were deprecated for removal in Java 17 (JEP 411). This material remains useful for legacy code and the underlying concepts (trust boundaries, least privilege, privileged operations), but new applications should not be designed around SecurityManager.

Section 7: Spring Framework Quick Reference & Java Annotations

Q1. What is Dependency Injection, and how does Spring implement it? Which injection style is best?

DI supplies an object's dependencies from outside rather than having it construct or look them up itself, decoupling classes from concrete implementations and making unit tests easier (dependencies can be mocked). Spring's IoC container implements DI: you declare beans (via @Component, @Service, @Repository, or Java/XML configuration) and Spring wires them together. (See Part 1 for the IoC principle itself.)

  • Constructor injection (recommended) — makes dependencies explicit, enables immutability (final fields), fully initializes the object on construction, and fails fast if a bean is missing.
  • Setter injection — suits optional dependencies and reconfiguration after construction, but risks partially initialized objects if the setter is never called.
  • Field injection — concise, but hides dependencies and is harder to test and mock.

Rule of thumb: constructor injection for mandatory dependencies, setter injection for optional ones. Compared with the Factory pattern, DI yields cleaner code: the class is a plain POJO that declares what it needs, with no knowledge of how dependencies are built or of any factory API, so it is easier to test in isolation.

@Service
public class OrderProcessingService {
    private final PaymentGateway paymentGateway; // dependency
 
    // constructor injection -- Spring supplies a PaymentGateway bean automatically
    @Autowired
    public OrderProcessingService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}

Q2. What are Spring bean scopes, and how do they interact with thread safety?

  • singleton (default) — one shared instance per container. Spring does nothing special to make it thread-safe; it is an ordinary singleton, so concurrent access is the developer's responsibility.
  • prototype — a new instance every time the bean is requested.
  • request — one instance per HTTP request; thread-safe by construction since no two requests share an instance.
  • session — one instance per HTTP session; requests from multiple browser tabs in the same session CAN run concurrently against it, so mutable state needs care.

Any bean with no mutable instance state is a safe singleton candidate, which is why DAO, Service, and Controller beans are usually singletons: each thread passes what it needs as method arguments. A bad singleton candidate is a bean that carries per-use mutable state, such as a Person bean with mutable name/age fields, which concurrent callers would silently corrupt.

Q3. What is the difference between @Component, @Service, @Repository, and @Controller?

All are specializations of @Component, registered as Spring beans by component scanning and functionally similar; the distinction is semantic (and useful for AOP targeting). @Service marks business-logic classes; @Repository marks data-access classes and additionally enables automatic translation of persistence-technology exceptions into Spring's DataAccessException hierarchy; @Controller marks web-layer classes handling HTTP requests.

Q4. What is an annotation, and what are the standard built-in and meta-annotations?

An annotation is metadata attached to code elements (classes, methods, fields, parameters) without directly affecting the semantics of the annotated code; it is consumed by the compiler, build tools, or runtime reflection. By themselves annotations execute nothing — something (the compiler, an annotation processor, or a framework such as Spring or Hibernate) must read and act on them.

  • @Override — the compiler errors if the method doesn't actually override, catching signature typos.
  • @Deprecated — marks an element as discouraged; usage triggers a compiler warning.
  • @SuppressWarnings — suppresses specific warning categories (e.g. "unchecked").
  • @FunctionalInterface — asserts exactly one abstract method; the compiler errors otherwise.

Meta-annotations control custom annotations: @Target (which elements it may annotate), @Retention (SOURCE: discarded at compile time, useful for tools like Lombok; CLASS: kept in the .class file but invisible at runtime, the default; RUNTIME: available via reflection, required for framework-style annotations), @Documented (include in Javadoc), and @Inherited (class-level annotation inherited by subclasses).

Problem statement: Define a custom runtime annotation and read it via reflection to audit an operation.

import java.lang.annotation.*;
import java.lang.reflect.Method;
 
@Retention(RetentionPolicy.RUNTIME) // needed to read it via reflection
@Target(ElementType.METHOD)
@interface AuditableOperation {
    String description();
}
 
class OrderService {
    @AuditableOperation(description = "Processes customer order")
    public void placeOrder() {
        System.out.println("Order placed");
    }
}
 
public class AnnotationProcessorDemo {
    public static void main(String[] arguments) throws Exception {
        Method targetMethod = OrderService.class.getMethod("placeOrder");
        if (targetMethod.isAnnotationPresent(AuditableOperation.class)) {
            AuditableOperation annotationData = targetMethod.getAnnotation(AuditableOperation.class);
            System.out.println("Audit: " + annotationData.description());
        }
    }
}

Q5. What is reflection, and what are its use cases and drawbacks?

Reflection (java.lang.reflect) allows runtime inspection and manipulation of classes, methods, fields, and constructors, even private ones. Use cases: frameworks (Spring and Hibernate annotation processing), serialization libraries, and testing tools. Drawbacks: performance overhead, broken encapsulation, bypassed compile-time type safety, and blocking by module-system restrictions (Java 9+).

Section 8: Exception Handling

Q1. What is the difference between checked and unchecked exceptions, and between throw and throws?

Checked exceptions (subclasses of Exception that do not extend RuntimeException, e.g. IOException, SQLException) are verified at compile time: a method that might throw one must handle it or declare it, and they typically represent recoverable conditions. Unchecked exceptions (RuntimeException subclasses and Errors, e.g. NullPointerException, IllegalArgumentException) are not compiler-enforced and usually represent programming errors.

throw is a statement that raises a Throwable instance at a specific point (throw new IllegalArgumentException("size must be a multiple of 2")). throws is part of a method signature, listing the checked exceptions the method may propagate so the caller knows what to handle.

Q2. Can there be multiple catch blocks? What is multi-catch?

Yes: multiple catch blocks are evaluated top-down, most specific first. Since Java 7, multi-catch — catch (IOException | SQLException exception) — handles unrelated types in one block (no superclass/subclass pairs; the variable is implicitly final), reducing duplicated handling logic.

Q3. What is try-with-resources, and what happens if exceptions occur in both try and finally?

Introduced in Java 7, try-with-resources automatically closes resources implementing AutoCloseable/Closeable after the block, even on exceptions, eliminating manual finally cleanup. Resources close in reverse declaration order, and exceptions thrown by close() are attached to the primary exception as suppressed exceptions (retrievable via getSuppressed()).

With a plain try/finally, an exception thrown from the finally block replaces the one from try, and the original is lost unless captured — which is why finally blocks should avoid throwing exceptions or returning values.

Problem statement: Read a file line by line and guarantee the reader is closed without writing a finally block.

import java.io.*;
 
public class FileReadingDemo {
    public static void readFileContents(String filePath) {
        try (BufferedReader fileReader = new BufferedReader(new FileReader(filePath))) {
            String currentLine;
            while ((currentLine = fileReader.readLine()) != null) {
                System.out.println(currentLine);
            }
        } catch (IOException fileException) {
            System.out.println("Error reading file: " + fileException.getMessage());
        } // fileReader is auto-closed here, no finally needed
    }
}

Q4. What is exception chaining, and how do you write a custom checked exception?

Exception chaining wraps a lower-level exception inside a higher-level one via the cause constructor (new ServiceException("msg", originalException)) or initCause(), preserving the original stack trace/root cause while letting each layer throw domain-appropriate exceptions.

Problem statement: Reject a bank withdrawal that exceeds the balance by throwing a custom checked exception.

class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String errorMessage) {
        super(errorMessage);
    }
}
 
class BankAccount {
    private double accountBalance;
 
    public BankAccount(double initialBalance) {
        this.accountBalance = initialBalance;
    }
 
    public void withdrawAmount(double requestedAmount) throws InsufficientFundsException {
        if (requestedAmount > accountBalance) {
            // explicitly throw a custom exception carrying context
            throw new InsufficientFundsException(
                    "Requested $" + requestedAmount + " exceeds balance $" + accountBalance);
        }
        accountBalance -= requestedAmount;
    }
}
 
public class BankDemo {
    public static void main(String[] arguments) {
        BankAccount savingsAccount = new BankAccount(500.0);
        try {
            savingsAccount.withdrawAmount(700.0); // triggers the custom exception
        } catch (InsufficientFundsException exceptionDetails) {
            System.out.println("Transaction failed: " + exceptionDetails.getMessage());
        }
    }
}

Section 9: Generics

Type erasure (why List<String> and List<Integer> share the same runtime class, and the Class<T> token / TypeToken workarounds) is covered in Part 1, Section 1, Q16.

Q1. What is the difference between ? extends T and ? super T (PECS)?

? extends T (upper-bounded wildcard) allows reading T or its subtypes — use it for producers (Producer Extends). ? super T (lower-bounded) allows writing T or its subtypes into the structure — use it for consumers (Consumer Super). Comparator<? super T> accepting comparators for T or its supertypes is a canonical example.

Problem statement: Copy elements from a source list of a subtype into a destination list of a supertype.

import java.util.*;
 
public class BoundedWildcardDemo {
    // PECS: the source produces (extends), the destination consumes (super)
    public static <ElementType> void copyElements(
            List<? extends ElementType> sourceList,
            List<? super ElementType> destinationList) {
        for (ElementType currentElement : sourceList) {
            destinationList.add(currentElement);
        }
    }
 
    public static void main(String[] arguments) {
        List<Integer> integerSource = Arrays.asList(1, 2, 3);
        List<Number> numberDestination = new ArrayList<>();
        copyElements(integerSource, numberDestination);
        System.out.println(numberDestination); // [1, 2, 3]
    }
}

Q2. Why can't you create generic arrays like new T[10]?

Because of type erasure the JVM doesn't know T's runtime type, and arrays are covariant with runtime type checks (ArrayStoreException), so a raw T[] could let incompatible elements in. The workaround is an unchecked cast, @SuppressWarnings("unchecked") T[] array = (T[]) new Object[10], or, better, using ArrayList<T>.

Q3. What are bounded type parameters?

They restrict acceptable types using extends, with multiple bounds allowed: <T extends Comparable<T> & Serializable>. This lets the generic code call methods defined by the bound; for example <T extends Number> permits calling doubleValue() on T, which a plain <T> would not.

Section 10: Java 7–21 Features & Modern Java

Q1. Name key features introduced in Java 7 and Java 8.

Java 7:

  • try-with-resources for automatic resource closing.
  • The Fork/Join framework for divide-and-conquer parallel algorithms that balance work across cores.
  • Strings in switch statements (compiled to a hashCode()-based comparison plus an equals() check).
  • The diamond operator <> for generic type inference.
  • Multi-catch: catch (IOException | SQLException e).

Java 8:

  • Lambda expressions and method references.
  • The Stream API, with optional parallel execution.
  • The java.time package: an immutable, thread-safe replacement for Date/Calendar.
  • Default and static methods on interfaces.
  • Repeatable annotations, and Optional.

Q2. What is a lambda expression, and what are functional interfaces?

A lambda is a concise anonymous-function implementation of a functional interface — an interface with exactly one abstract method — e.g. (a, b) -> a + b. @FunctionalInterface is optional but recommended for compile-time checking. Built-in examples: Runnable, Comparator<T>, Function<T,R>, Predicate<T>, Supplier<T>, Consumer<T>; they underpin the lambda and Stream APIs.

Q3. What is the Stream API, and how do intermediate and terminal operations differ?

A Stream is a sequence of elements supporting declarative, functional-style pipelines (map, filter, reduce) that can run sequentially or in parallel. Unlike collections, streams don't store data and are consumed once. Intermediate operations (filter, map, sorted) are lazy and return a new Stream; nothing executes until a terminal operation (collect, forEach, reduce, count) triggers processing and closes the stream.

Problem statement: Given [1,2,3,4,5,6], filter the even numbers, square them, and sum the result in one pipeline (expected 4 + 16 + 36 = 56).

import java.util.*;
 
public class SumOfSquaresDemo {
    public static void main(String[] arguments) {
        List<Integer> numberCollection = Arrays.asList(1, 2, 3, 4, 5, 6);
 
        int sumOfEvenSquares = numberCollection.stream()
                .filter(currentValue -> currentValue % 2 == 0)  // intermediate: keep evens
                .map(currentValue -> currentValue * currentValue) // intermediate: square each
                .reduce(0, Integer::sum);                         // terminal: accumulate the sum
 
        System.out.println("Sum of squares of even numbers: " + sumOfEvenSquares); // 56
    }
}

Q4. What is the difference between map() and flatMap()?

map() transforms each element into exactly one other element (one-to-one), potentially yielding nested structures like Stream<List<T>>. flatMap() transforms each element into a stream and flattens all of them into a single-level Stream<T> — useful when each element maps to multiple elements, e.g. flattening List<List<Integer>> into List<Integer>.

Q5. What is Optional, and why was it introduced?

Optional<T> is a container that may or may not hold a non-null value, introduced to make absence explicit in method signatures and reduce NullPointerException risk. Use orElse(), orElseGet(), map(), and ifPresent() rather than manual null checks, and avoid calling get() without checking presence.

Q6. What are method references, and what are their four types?

Method references are shorthand lambdas that name an existing method: (1) static method — ClassName::staticMethod; (2) instance method of a particular object — object::instanceMethod; (3) instance method of an arbitrary object of a type — ClassName::instanceMethod; (4) constructor reference — ClassName::new.

Q7. What is the difference between Collectors.toList()/toSet() and groupingBy()?

toList()/toSet() collect elements into a plain collection. groupingBy() partitions elements into a Map<K, List<V>> by a classifier function, optionally with downstream collectors (counting, summing, mapping) — the Java equivalent of SQL GROUP BY.

Problem statement: Group employee names by department.

import java.util.*;
import java.util.stream.*;
 
public class EmployeeGroupingDemo {
    public static void main(String[] arguments) {
        List<String[]> employeeRecords = Arrays.asList(
                new String[]{"Alice", "Engineering"},
                new String[]{"Bob", "Sales"},
                new String[]{"Charlie", "Engineering"});
 
        Map<String, List<String>> employeesByDepartment = employeeRecords.stream()
                .collect(Collectors.groupingBy(
                        employeeRecord -> employeeRecord[1],   // classifier: department
                        Collectors.mapping(employeeRecord -> employeeRecord[0], // extract name
                                Collectors.toList())));
 
        System.out.println(employeesByDepartment);
        // {Engineering=[Alice, Charlie], Sales=[Bob]}
    }
}

Q8. What are default and static interface methods, and what problem do they solve? What is the diamond problem?

Before Java 8, adding a method to an interface broke every implementer. Default methods carry a body so existing implementers keep compiling — essential for evolving APIs such as adding Collection.stream() without breaking millions of implementations. Static methods belong to the interface itself, are called via InterfaceName.method(), and can't be overridden.

The diamond problem arises when a class inherits conflicting default implementations from two interfaces. Java forces the class to override the method explicitly, and it can call a specific version with InterfaceName.super.methodName(), avoiding the ambiguity multiple inheritance of state would cause.

Problem statement: Show an interface with an abstract, a default, and a static method, used by an implementing class.

interface PaymentProcessor {
    // abstract method: must be implemented
    void processPayment(double transactionAmount);
 
    // default method: shared behavior inherited for free
    default void logTransaction(double transactionAmount) {
        System.out.println("Logging transaction: " + transactionAmount);
    }
 
    // static method: utility bound to the interface itself
    static boolean isValidAmount(double transactionAmount) {
        return transactionAmount > 0;
    }
}
 
class CreditCardProcessor implements PaymentProcessor {
    @Override
    public void processPayment(double transactionAmount) {
        if (PaymentProcessor.isValidAmount(transactionAmount)) {
            logTransaction(transactionAmount);
            System.out.println("Processed: " + transactionAmount);
        }
    }
}

Q9. What is var (Java 10) and what are Text Blocks (Java 15)?

var lets the compiler infer a local variable's type from its initializer at compile time (it is not dynamic typing; the type is fixed). It reduces verbosity for complex generics but requires an initializer and can't be used for fields, parameters, or return types.

Text blocks (triple-quote """ delimiters) allow multi-line string literals without \n concatenation or escaping, preserving formatting for embedded SQL, JSON, or HTML. The compiler strips incidental leading whitespace based on the closing delimiter's indentation.

Q10. What are Records (Java 14+), Sealed classes (Java 17), and pattern matching for switch (Java 21)? Why do tech leads push for them?

Records are concise, immutable data carriers that auto-generate the constructor, equals(), hashCode(), toString(), and accessors, eliminating boilerplate and the bugs of hand-written equals/hashCode. Sealed types restrict which classes may extend or implement them via permits, giving a closed, compile-time-known hierarchy. Pattern matching for switch matches on types and deconstructs records directly; combined with sealed types the compiler enforces exhaustiveness, so no default branch is needed.

Problem statement: Model payment events as a sealed hierarchy of records and handle each case exhaustively.

public record Money(BigDecimal amount, Currency currency) {
    public Money {  // compact constructor: validation runs on every construction
        if (amount.signum() < 0) throw new IllegalArgumentException("Amount cannot be negative");
    }
}
 
public sealed interface PaymentEvent permits PaymentInitiated, PaymentSettled, PaymentFailed { }
public record PaymentInitiated(String transactionId) implements PaymentEvent { }
public record PaymentSettled(String transactionId, Instant settledAt) implements PaymentEvent { }
public record PaymentFailed(String transactionId, String reason) implements PaymentEvent { }
 
String eventDescription = switch (paymentEvent) {
    case PaymentInitiated initiated -> "Initiated: " + initiated.transactionId();
    case PaymentSettled settled     -> "Settled at " + settled.settledAt();
    case PaymentFailed failed       -> "Failed: " + failed.reason();
    // no default needed: the compiler knows every permitted type is covered
};

If a new event type is added later, this switch fails to compile until updated, turning a class of runtime bugs into compile-time errors — especially valuable in event-driven financial systems.

Note: Tech-lead takeaway: push for adoption of these features in new modules even inside legacy Java 8/11 codebases undergoing modernization; the reduction in boilerplate and “forgot to handle the new enum value” bugs pays for itself quickly. Virtual threads (Java 21) are covered in Part 2, Section 8.

Language basics

Q1. What is the difference between a == b and a.equals(b)? And between final, finally, and finalize?

== compares references for objects (and values for primitives); equals() expresses logical equality and depends on the class overriding it — the inherited Object default is identical to ==, while String overrides it to compare characters.

  • final — a modifier: a final variable can't be reassigned, a final method can't be overridden, a final class can't be subclassed (supporting immutability, security, and design intent).
  • finally — a block paired with try/catch that always executes, whether or not an exception was thrown (short of System.exit() or a JVM crash).
  • finalize() — a method called by the GC just before reclaiming an object; deprecated since Java 9 and never guaranteed to run, so don't use it for critical cleanup.

Q2. What is the difference between a = a + b and a += b for narrower primitive types?

+= implicitly casts the result back to the left-hand type. For byte/short, a + b promotes both operands to int, so assigning it back without a cast is a compile error, whereas a += b compiles because the compiler inserts the narrowing cast.

byte firstValue = 127;
byte secondValue = 127;
secondValue = firstValue + secondValue; // COMPILE ERROR: int cannot be assigned to byte
secondValue += firstValue;              // OK: compiler implicitly casts back to byte

Q3. Can you store a double in a long without casting? Does 3 * 0.1 == 0.3?

No, an explicit cast is required: double has a different representation and range, and the narrowing cast truncates the fraction. And 3 * 0.1 == 0.3 is false: many decimal fractions can't be represented exactly in IEEE 754 binary floating point, so the result is extremely close to, but not bit-identical to, 0.3. Never compare floating-point values for exact equality; check that the difference is within an epsilon, or use BigDecimal when exact decimal arithmetic matters (such as money).

double sourceValue = 123.456;
long targetValue = (long) sourceValue; // 123 -- fraction truncated, cast is required
 
boolean isExactlyEqual = (3 * 0.1 == 0.3); // false, due to floating-point representation

Q4. Which uses more memory: int or Integer? What is the size of an int on a 64-bit JVM?

Integer uses more: int is 4 bytes of raw data, whereas Integer is a full object with header overhead (class pointer, lock state), typically 16 bytes or more. An int is still 32 bits on a 64-bit JVM — primitive sizes are fixed by the language specification, not the platform's word size, in keeping with “write once, run anywhere.”

Q5. Why is String immutable, and can you use a String in a switch?

Immutability enables safe sharing of the same underlying object (as with the String pool) with no risk that one piece of code corrupts a String another relies on. It also makes String safe as a HashMap key (its hash code can't change after insertion) and inherently thread-safe. Strings can be used in switch since Java 7 as syntactic sugar over hashCode() and equals(). StringBuilder is mutable and not thread-safe (best for single-threaded manipulation); StringBuffer is mutable and synchronized (thread-safe, but with synchronization overhead).

Q6. What is a compile-time constant, and what is its risk?

A public static final field whose value is known at compile time (e.g. public static final int MAX_RETRIES = 5;) is inlined by the compiler directly into calling code. The risk: if the constant lives in a separate library that later changes its value, code compiled against the old version keeps using the old inlined value even after the new JAR is deployed, until that calling code is recompiled.

Q7. What is constructor chaining?

One constructor calls another of the same class via this(...) or of its superclass via super(...), so shared initialization lives in one place instead of being duplicated across overloads.

public class Rectangle {
    private final int width;
    private final int height;
 
    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }
 
    public Rectangle(int side) {
        this(side, side); // chains to the two-argument constructor above
    }
}

Object-oriented design

Q8. What are the four pillars of OOP? What is the difference between an abstract class and an interface, and between inheritance and composition?

The four pillars: Encapsulation (bundling data with methods and restricting access), Abstraction (hiding implementation behind interfaces), Inheritance (reusing/extending a parent's behavior), and Polymorphism (one interface, many implementations).

Abstract class vs. interface: a class extends only one class but implements any number of interfaces. An abstract class can hold state, constructors, and both abstract and concrete methods, and suits shared code for a closely related family; an interface (with default/static methods since Java 8, but no instance state) defines a contract/type that unrelated classes can implement. An interface's purpose is abstraction: client code written against List works with ArrayList or LinkedList unchanged.

Inheritance (“is-a”) is fixed at compile time and couples tightly to the parent's implementation; composition (“has-a”, holding a reference and delegating) can swap implementations at runtime, avoids fragile-base-class problems, and is easier to unit test — hence “favor composition over inheritance.”

Problem statement: Process different payment types polymorphically through a common base class.

abstract class PaymentProcessor {
    // each payment type supplies its own logic
    abstract void processPayment(double transactionAmount);
}
 
class CreditCardProcessor extends PaymentProcessor {
    @Override
    void processPayment(double transactionAmount) {
        System.out.println("Processing credit card payment: $" + transactionAmount);
    }
}
 
class PayPalProcessor extends PaymentProcessor {
    @Override
    void processPayment(double transactionAmount) {
        System.out.println("Processing PayPal payment: $" + transactionAmount);
    }
}
 
public class PaymentDemo {
    public static void main(String[] arguments) {
        List<PaymentProcessor> paymentProcessors = new ArrayList<>();
        paymentProcessors.add(new CreditCardProcessor());
        paymentProcessors.add(new PayPalProcessor());
 
        for (PaymentProcessor currentProcessor : paymentProcessors) {
            currentProcessor.processPayment(250.00); // correct override chosen at runtime
        }
    }
}

Q9. What is the difference between method overloading and overriding? Any overloading best practices?

Overloading (same name, different parameters, same class) is resolved at compile time from the signature at the call site — compile-time polymorphism. Overriding (a subclass redefining a superclass method with the same signature) is resolved at runtime from the object's actual type — runtime polymorphism, and it requires inheritance.

  • Avoid overloads that accept a primitive (int) in one variant and its wrapper (Integer) in another; auto-boxing makes it ambiguous which is called.
  • Avoid overloads that differ only in the order of same-typed parameters.
  • Beyond roughly 4–5 parameters, prefer varargs, a builder, or a parameter object over more overloads.

Q10. Explain the Liskov Substitution Principle, the Open/Closed Principle, and the Law of Demeter.

  • Liskov Substitution — subclass objects must be substitutable for superclass objects without breaking correctness: don't strengthen preconditions, weaken postconditions, or throw unexpected exceptions. Classic violation: a Square extending Rectangle and forcing width == height, breaking code that sets them independently.
  • Open/Closed — open for extension, closed for modification. The Strategy pattern is a textbook case (add a new strategy by writing a new implementation), and Collections.sort() is an everyday instance: a new sort order means a new Comparator, never a change to sort().
  • Law of Demeter (“only talk to your immediate friends”) — a method should call only methods on itself, its fields, its parameters, or objects it creates, not on objects those return; chains like a.getB().getC().doSomething() couple you to internal structure you don't own.

Q11. How do the Adapter, Decorator, and Proxy patterns differ?

All three wrap another object, but intent differs: Adapter converts one interface into another that a client expects; Decorator adds new behavior dynamically while keeping the same interface; Proxy adds a controlled layer of indirection (lazy initialization, access control, remote invocation, logging) while presenting the same interface as the wrapped object.

Q12. What are the Template Method, Visitor, Composite, Flyweight, Abstract Factory, and Prototype patterns used for?

  • Template Method — fixes the skeleton of an algorithm in a base class while subclasses override specific steps; e.g. Collections.sort() defines the algorithm and delegates comparison to your Comparable/Comparator.
  • Visitor — adds new operations to a stable class hierarchy without modifying it, using double dispatch (the overload invoked depends on both the element's and the visitor's runtime types).
  • Composite — arranges objects into tree part-whole hierarchies so clients treat a leaf and a group uniformly (filesystem of files/folders; the organizational chart in Part 2).
  • Flyweight — shares immutable objects to support many logical objects with few real ones; the String pool and the boxed Integer/Long cache (-128 to 127) are JDK examples.
  • Abstract Factory vs. Prototype — Abstract Factory creates families of related objects through factory methods that each return a new instance; Prototype creates objects by cloning a pre-configured instance, useful when construction is expensive.

Q13. What is the difference between Association, Aggregation, and Composition? Nested static class vs. top-level class?

  • Association — any relationship connecting two objects.
  • Aggregation (“has-a”, weak ownership) — the used object has an independent lifecycle: a University has Students, but a Student can exist without any particular University.
  • Composition (“owns-a”, strong ownership) — lifecycles are bound: a Car is composed of an Engine that has no meaningful existence apart from that Car.

A source file may contain only one top-level public class (matching the file name), but a top-level class can contain any number of nested static classes; Map.Entry (a nested static interface inside Map) is the JDK example.

Exceptions, XML, build tools & collections trivia

Q14. What is the difference between a DOM parser and a SAX parser? Maven vs. Ant?

DOM reads the entire XML document into an in-memory tree that can be freely navigated and modified: faster for repeated navigation of small-to-medium documents, but memory-hungry. SAX is event-based: it streams through once, firing callbacks (element start/end, text), holding only a small constant amount of memory regardless of document size — better for very large files, at the cost of a callback-driven style.

Ant is a general-purpose, imperative build tool: you script every step in XML, with no conventions or dependency management. Maven is convention-over-configuration: it imposes a standard project layout and resolves and downloads dependency JARs (and their transitive dependencies) from a central repository based on a declarative pom.xml.

Q15. What is the difference between poll() and remove() on a Queue? LinkedHashMap vs. PriorityQueue?

Both remove and return the head, but on an empty queue poll() returns null while remove() throws NoSuchElementException; the same pattern holds for peek() (null) vs. element() (throws). LinkedHashMap is a Map that iterates in insertion order (or access order if configured, handy for an LRU cache); PriorityQueue is a Queue that always keeps the lowest-priority-value (or highest, with a Comparator) element at its head — iterating it directly guarantees no order, only repeated poll() does.

Q16. Hashtable vs. HashMap? How does HashSet work? Default capacities? Is LinkedList singly or doubly linked?

  • Hashtable is a legacy JDK 1.0 class that synchronizes every operation and forbids null keys and values; HashMap (Java 1.2) is unsynchronized, allows one null key and any number of null values — use ConcurrentHashMap when you need both speed and thread safety.
  • HashSet is backed by a HashMap: each element is stored as a key paired with a shared dummy placeholder value, hence no duplicates and at most one null.
  • Default initial capacities: ArrayList 10, HashMap 16 (always a power of two, to support bit-masking of the hash).
  • LinkedList is doubly linked (each node references next and previous); TreeMap uses a red-black tree for guaranteed O(log n) operations.
// from ArrayList's source
private static final int DEFAULT_CAPACITY = 10;
// from HashMap's source
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4; // 16

Q17. Can two unequal objects share a hashCode()? Can two equal objects have different ones? Can hashCode() use random values?

  • Unequal objects with the same hashCode: yes — that's a hash collision, normal in any hash-based collection, and why equals() is still needed once keys land in the same bucket.
  • Equal objects with different hashCode: no — it violates the contract; an object could be inserted into a HashMap and then become unfindable because it computes a different bucket.
  • Random values inside hashCode(): no — it must be stable for as long as the object is unchanged; a fresh random value per call breaks the contract immediately.

Q18. What best practices apply to Collections, I/O, JDBC, and threads?

I/O:

  • Prefer buffered classes (BufferedReader, BufferedOutputStream) over byte-at-a-time I/O.
  • Prefer java.nio / NIO.2 for high-performance or non-blocking I/O; consider memory-mapped files (FileChannel.map()) for very large files.
  • Use try-with-resources rather than closing in finally; keep I/O off latency-critical hot paths (batch, buffer, or move it off the path).

JDBC:

  • Use batch statements (addBatch()/executeBatch()) for many rows instead of one round trip per row.
  • Always use PreparedStatement with bind parameters: it prevents SQL injection and lets the database cache the execution plan.
  • Use a connection pool; read ResultSet columns by name rather than index; never concatenate raw user input into SQL.

Threads (in addition to Part 1–2):

  • Always name your threads explicitly; it makes thread dumps dramatically easier to read.
  • Keep the task (Runnable/Callable) separate from the mechanism running it, and use a thread pool instead of ad-hoc thread creation.
  • Prefer volatile over synchronized when you only need visibility for a simple flag, and higher-level utilities (BlockingQueue, CountDownLatch, Semaphore, CompletableFuture) over hand-rolled wait()/notify().
  • Prefer concurrent collections over externally synchronized ones; use the non-synchronized ArrayList rather than legacy Vector unless synchronization is needed.

Section 12: Advanced Concurrency & Memory Model (Rapid-Fire)

Building on Part 1 (JMM, volatile, ConcurrentHashMap internals, locks, ThreadLocal, CompletableFuture) and Part 2 (CAS/ABA, virtual threads, BlockingQueue), the following questions add the remaining nuances.

Q1. Can volatile make a non-atomic operation atomic? What guarantees does volatile actually provide?

In one specific case, yes: reads and writes of long and double. These 64-bit primitives may, per the JVM specification, be split into two 32-bit operations when non-volatile, so a thread could observe a “torn” value (half old, half new). Declaring the field volatile guarantees each 64-bit read or write is a single atomic operation.

More broadly, volatile provides visibility and ordering. A write is immediately visible to every thread that subsequently reads the field (the happens-before relationship), and the compiler, JVM, and CPU may not reorder the volatile access relative to surrounding statements. The JMM effectively inserts a write barrier after a volatile write and a read barrier before a volatile read, so a reader also sees every write the writer made before the volatile write. Practical uses: atomic long/double access, simple shared flags such as a shutdown signal, and safe publication in double-checked locking.

Q2. Should wait() be called inside an if or a loop? Why?

Always a loop. Between being notified and actually reacquiring the lock, the condition may no longer hold because another thread got there first (and spurious wakeups can also occur). Re-testing the condition on every wake-up protects against this.

synchronized (sharedLockObject) {
    while (!conditionHolds()) {
        sharedLockObject.wait(); // releases the lock; reacquires it automatically on wakeup
    }
    // the condition is now guaranteed true -- safe to proceed
}

Q3. Is synchronization fundamentally harder for 10 threads than for 2?

Not in code mechanics — synchronized, wait(), and notify() work identically. What changes is the strategy: more threads means more lock contention, which can push you toward techniques such as lock striping (splitting one lock into several, each guarding a partition of the data).

Q4. What is false sharing, and how do you avoid it?

On multi-core CPUs, each core has its own cache. False sharing occurs when threads on different cores modify separate variables that happen to sit on the same cache line (typically 64 bytes). The coherency protocol treats the whole line as a unit, so one core's write invalidates the line for the other core, forcing costly reloads despite no real data dependency. It is notoriously hard to detect. Mitigate by padding or aligning heavily contended fields onto separate cache lines, or with the JDK-internal @Contended annotation.

Problem statement: Keep two threads' counters from invalidating each other's cache lines by padding each counter.

public class PaddedCounter {
    // 7 long padding fields isolate the counter on its own cache line
    private long padding1, padding2, padding3, padding4, padding5, padding6, padding7;
    private volatile long counterValue;
 
    public void incrementCounter() {
        counterValue++;
    }
 
    public long getCounterValue() {
        return counterValue;
    }
}
// Two threads updating separate PaddedCounter instances no longer invalidate
// each other's CPU cache lines, improving throughput.

Q5. What is busy-spinning, and when should you use it?

Busy-spinning waits for an event by looping on a condition without releasing the CPU or sleeping, avoiding the loss of CPU cache state that occurs when a paused thread resumes (possibly on another core). It only pays off for very short expected waits (microseconds to low milliseconds); otherwise the wasted cycles outweigh the benefit. Low-latency trading systems are the classic use — the LMAX Disruptor's BusySpinWaitStrategy is built on this idea.

Q6. Explain happens-before, memory fences, and why double-checked locking fails without volatile.

Happens-before is a partial ordering guaranteeing that writes before a point are visible after it; without it the JMM permits arbitrary reordering under the as-if-serial rule. Key sources: program order within a thread; a volatile write happens-before a subsequent volatile read of the same field; a monitor unlock happens-before the next lock of that monitor; Thread.start() happens-before the started thread's actions; and a thread's actions happen-before another thread's join() returns.

A memory fence prevents reordering across it. The four reordering types are LoadLoad, StoreStore, LoadStore, and StoreLoad (the most expensive to prevent). A volatile write inserts StoreStore and LoadStore barriers before it and a StoreLoad barrier after.

Double-checked locking fails without volatile because object construction is not atomic from the JVM's view: the JIT or CPU can publish the reference before the constructor finishes, so a second thread can read a non-null reference to a half-initialized object. volatile's barrier forces the object to be fully constructed before the reference becomes visible (see Part 1, Section 2, Q4).

Q7. Why is Thread.stop() deprecated, and how do you cancel a thread safely?

Thread.stop() kills a thread at an arbitrary point, releasing monitors mid-update and leaving shared objects in an inconsistent, corrupted state with no guarantee of cleanup. The safe alternative is cooperative cancellation: set a volatile boolean flag or call Thread.interrupt(); the task checks periodically (or is unblocked from a blocking call by an InterruptedException) and exits cleanly on its own terms.

Q8. What is a livelock, and how does it differ from a deadlock? What is reentrancy?

In a deadlock, threads are blocked and make no progress. In a livelock, threads stay active and keep changing state in response to each other (for example, both repeatedly backing off and retrying) but never make forward progress, burning CPU. Prevent it with randomized backoff or a strict resource-acquisition ordering/priority scheme that breaks the symmetric retry.

Java's intrinsic locks (synchronized) and ReentrantLock are reentrant: a thread already holding a lock can re-acquire it (e.g. calling another synchronized method on the same object) without blocking, tracked by a per-thread hold count decremented on each exit. A naive non-reentrant lock would deadlock a thread against itself in that scenario.

Q9. How does the fork/join framework achieve work stealing?

ForkJoinPool gives each worker thread its own double-ended work queue. A thread pushes and pops tasks from the head of its own queue (LIFO, cache-friendly), but when idle it steals from the tail of another thread's queue (FIFO, minimizing contention with the owner). This suits recursive divide-and-conquer workloads with uneven task sizes, since idle threads rebalance load automatically without a central coordinator.

Q10. How do CompletableFuture's handle(), exceptionally(), and whenComplete() differ? What production practices apply?

  • exceptionally() runs only on failure, supplies a recovery value, and is skipped entirely on success.
  • handle() always runs, receiving either the result or the exception (one is null), and can transform either path into a new result.
  • whenComplete() always runs but cannot alter the result; it only observes (useful for logging) and passes the original outcome through unless it itself throws.

Production practices: always supply a custom Executor (the default ForkJoinPool.commonPool() is shared JVM-wide and can starve under load); always set timeouts (orTimeout / completeOnTimeout) so pipelines can't hang indefinitely; and propagate correlation/trace IDs through the chain with structured logging, since async code is harder to debug.

CompletableFuture<UserProfile> userProfilePipeline =
        CompletableFuture.supplyAsync(() -> fetchUser(userId), customExecutor)
                // thenCompose chains a dependent async call, avoiding nested futures
                .thenCompose(user -> fetchOrdersAsync(user.getId())
                        .thenApply(orders -> enrich(user, orders)))
                .exceptionally(pipelineError -> {
                    log.error("Pipeline failed for user {}", userId, pipelineError);
                    return UserProfile.fallback(userId);
                })
                .orTimeout(2, TimeUnit.SECONDS); // never hang indefinitely
 
userProfilePipeline.thenAccept(profile -> render(profile));

Q11. How does biased locking work, and why was it removed?

Biased locking (pre-Java 15) optimistically assumes a monitor will be locked repeatedly by the same thread, storing that thread's ID in the object header so re-entry needs only a fast ID comparison rather than a CAS. It was disabled by default in Java 15+ because modern JIT lock elision (via escape analysis) and cheap hardware CAS instructions made the header-state complexity and expensive revocation (when the bias assumption is violated) no longer worthwhile.

Q12. Why can HashMap's resize cause an infinite loop or lost data in multithreaded code?

Pre-Java 8 HashMap rebuilt each bucket's linked list by re-inserting nodes during resize; concurrent structural modification could reverse a bucket's node order across two racing threads, creating a circular reference (an infinite loop on the next traversal) or silently dropping entries. Java 8 preserves relative order and splits buckets in place, reducing but not eliminating the risk: HashMap remains fundamentally not thread-safe, and ConcurrentHashMap must be used for concurrent access.
