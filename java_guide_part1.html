Section 1: Core Java Fundamentals

Q1. What is an immutable object? Can you write an immutable class?

An immutable object is an object whose state cannot be changed after construction. Any “modification” instead produces a brand-new object, leaving the original untouched. String is the most common example of an immutable class in Java.

Immutable classes are typically declared final, to stop a subclass from overriding methods in a way that could break immutability. You can achieve the same safety without the final keyword by making fields private and never modifying them after the constructor runs.

Rules for writing your own immutable class:

  • Declare the class as final so it cannot be subclassed.
  • Make all fields private and final.
  • Do not provide setter methods.
  • Initialize all fields via the constructor only.
  • If a field is a mutable object (e.g. a Date or a List), return a defensive copy from any getter, rather than the original reference.

Problem statement: Implement an immutable 2D point class that supports a “translate” operation without mutating the original instance.

public final class ImmutablePoint {
 
    private final int xCoordinate;
    private final int yCoordinate;
 
    public ImmutablePoint(int xCoordinate, int yCoordinate) {
        this.xCoordinate = xCoordinate;
        this.yCoordinate = yCoordinate;
    }
 
    public int getXCoordinate() {
        return xCoordinate;
    }
 
    public int getYCoordinate() {
        return yCoordinate;
    }
 
    // "Modifying" an immutable object returns a NEW instance instead
    // of mutating the fields of the current one.
    public ImmutablePoint translate(int deltaX, int deltaY) {
        return new ImmutablePoint(xCoordinate + deltaX, yCoordinate + deltaY);
    }
}

Q2. Do all properties of an immutable object need to be final?

Not strictly. You can achieve the same effect by making a field non-final but private, and simply never modifying it anywhere except inside the constructor. Marking fields final is still best practice because it lets the compiler enforce immutability for you and communicates intent clearly to other developers.

Q3. What is the difference between creating a String with new() and with a literal?

When you create a String using the new() operator, a new object is always allocated on the heap, and it is NOT automatically added to the String pool. When you create a String using a literal, Java automatically places it into the String pool (also called the intern pool), which lives on the heap.

Problem statement: Demonstrate the reference-identity difference between a heap-allocated String and a pooled String literal, and show how to manually intern a String.

String heapString = new String("Test");   // new object in heap, NOT in string pool
String pooledString = "Test";              // placed into the string pool automatically
 
// To manually add the heap-allocated string to the pool:
String internedString = heapString.intern();
 
System.out.println(pooledString == internedString); // true  - both refer to the pooled instance
System.out.println(pooledString == heapString);      // false - different objects

The String pool exists so that identical string literals can share a single object in memory, saving space, since Strings are immutable and safe to share.

Q4. How does substring() work internally in String?

substring() creates a new String object representing a portion of the original string, defined by the given start index (inclusive) and end index (exclusive). In older JDKs (before Java 7 update 6), substring() shared the original character array internally and only changed the offset and length fields — fast, but capable of causing a memory leak if a huge original string was kept alive by a tiny substring. Since that update, substring() copies the relevant characters into a new array, so the original string can be garbage collected independently.

String original = "Hello, World!";
String extracted = original.substring(7, 12); // "World"
// In modern Java, "extracted" holds its own independent char array,
// so "original" is free to be garbage collected even if "extracted" is still referenced.

Q5. Which two methods do you need to implement for a key object in a HashMap?

Any object used as a key in a HashMap must correctly implement equals() and hashCode(). These two methods work together: hashCode() determines which bucket the key is stored in, and equals() confirms an exact match once the correct bucket is found.

Q6. Where do equals() and hashCode() come into play during a get() operation?

When you call map.get(key), HashMap first calls hashCode() on the key to compute a bucket index. It then walks the entries in that bucket (there may be more than one, due to hash collisions) and calls equals() on each candidate key until it finds a match. If hashCode() is implemented poorly (e.g. it always returns the same value), every key lands in the same bucket, degrading lookups toward O(n).

Q7. When do you override hashCode() and equals(), and what happens if you don't?

Override both whenever you need to compare objects for logical equality (rather than reference equality), or whenever instances of the class will be used as keys in a hash-based collection (HashMap, HashSet, Hashtable) or stored as elements in one. The two methods must remain consistent: if two objects are equal according to equals(), they must return the same hashCode().

If a class does not override hashCode(), it inherits Object's default implementation, based on the object's memory address. Two logically-equal objects (even if equals() is overridden to compare their content) will then likely produce different hash codes, land in different buckets, and you will not be able to retrieve a value using a different-but-equal key instance than the one originally used to insert it.

Performance implication: a poorly-implemented hashCode() — or the default identity-based one when content-based equality was intended — causes more hash collisions. When many keys land in the same bucket, HashMap degrades from average O(1) lookup toward O(n) (or O(log n) in Java 8+, where large buckets convert to a red-black tree), because it must linearly scan (or tree-search) the colliding entries and call equals() on each one.

Q8. What's wrong with using HashMap in a multi-threaded environment? When can get() enter an infinite loop?

HashMap is not thread-safe. If multiple threads modify a HashMap concurrently — particularly during a resize operation (rehashing when the load-factor threshold is exceeded) — the internal linked structure of a bucket can become corrupted. In older Java versions (pre-Java 8), this could literally create a circular reference within a bucket's linked list, causing get() to loop forever while traversing that bucket. In Java 8+, the specific infinite-loop bug from bucket resizing was mitigated, but HashMap can still corrupt state under concurrent modification. Regardless of JDK version, HashMap should never be shared across threads without external synchronization — use ConcurrentHashMap instead.

Q9. Can you write code for iterating over a HashMap in both the old (pre-Java-5) style and the modern style?

Problem statement: Iterate over the key/value pairs of a HashMap using three progressively modern styles.

Map<String, Integer> inventoryCounts = new HashMap<>();
inventoryCounts.put("apples", 50);
inventoryCounts.put("bananas", 30);
 
// Old style (pre-Java 5): explicit Iterator over entrySet()
Iterator<Map.Entry<String, Integer>> entryIterator = inventoryCounts.entrySet().iterator();
while (entryIterator.hasNext()) {
    Map.Entry<String, Integer> currentEntry = entryIterator.next();
    System.out.println(currentEntry.getKey() + " = " + currentEntry.getValue());
}
 
// Modern style (Java 5+): enhanced for-loop over entrySet()
for (Map.Entry<String, Integer> currentEntry : inventoryCounts.entrySet()) {
    System.out.println(currentEntry.getKey() + " = " + currentEntry.getValue());
}
 
// Java 8+: forEach with a lambda
inventoryCounts.forEach((itemName, itemCount) ->
    System.out.println(itemName + " = " + itemCount));

Q10. How does HashMap's performance compare to TreeMap? Which would you choose and when?

HashMap offers average O(1) get/put, backed by an array of buckets with hashCode()-based dispatch, but gives no ordering guarantee over its keys. TreeMap offers guaranteed O(log n) get/put, backed by a red-black tree, and keeps keys in sorted order (natural ordering or a supplied Comparator), and additionally supports range queries such as firstKey(), lastKey(), headMap(), and tailMap(). Choose HashMap when you only need fast lookups and don't care about order; choose TreeMap when you need the keys sorted or need range-based navigation, and can accept the O(log n) cost.

Q11. How do you safely remove elements from an ArrayList while iterating over it?

Removing directly from a List with a for-each loop (or by index while iterating forward) throws ConcurrentModificationException or skips elements, because the List's internal modCount changes underneath the iterator. The safe approaches are to use the Iterator's own remove() method, or Java 8+'s removeIf().

List<String> shoppingCartItems = new ArrayList<>(List.of("milk", "eggs", "expired-cheese", "bread"));
 
// Safe: Iterator.remove() keeps the iterator's internal state consistent
Iterator<String> cartIterator = shoppingCartItems.iterator();
while (cartIterator.hasNext()) {
    String currentItem = cartIterator.next();
    if (currentItem.startsWith("expired")) {
        cartIterator.remove();
    }
}
 
// Safe and concise: Java 8+ removeIf()
shoppingCartItems.removeIf(itemName -> itemName.startsWith("expired"));

Q12. Can we create an immutable object that contains a mutable field, and still keep it truly immutable?

Yes, by never exposing the mutable field's original reference. The constructor must store a defensive copy of the mutable input, and every getter must return a defensive copy (or an unmodifiable view) rather than the field itself. Without this, a caller who obtains the reference could mutate the “immutable” object's internal state from outside.

public final class ImmutableSchedule {
    private final List<String> appointmentTimes;
 
    public ImmutableSchedule(List<String> appointmentTimes) {
        // defensive copy on the way in: caller's list can't mutate our state later
        this.appointmentTimes = new ArrayList<>(appointmentTimes);
    }
 
    public List<String> getAppointmentTimes() {
        // defensive copy on the way out: caller can't mutate our internal list
        return Collections.unmodifiableList(new ArrayList<>(appointmentTimes));
    }
}

Q13. Can you cast an int into a byte? What happens if the int is larger than a byte can hold?

Yes, via an explicit narrowing primitive cast: (byte) someInt. If the int's value doesn't fit in a byte's 8-bit signed range (-128 to 127), the higher-order bits are simply discarded (silent truncation, not an exception), which can produce a surprising, wrapped-around value. This is why narrowing casts of user-controlled values should be range-checked first.

int largeValue = 130;
byte truncatedValue = (byte) largeValue; // 130 doesn't fit in a byte -> wraps to -126
System.out.println(truncatedValue);       // prints -126, not 130

Q14. Can you make an array volatile in Java? What does that actually guarantee?

Yes, you can declare an array reference volatile, e.g. private volatile int[] counters. However, volatile only guarantees visibility and ordering for the reference itself — that is, for reassigning the array variable to point at a different array. It does NOT make the individual elements inside the array volatile: writes to counters[3] by one thread are not guaranteed to be visible to another thread without additional synchronization (e.g. using AtomicIntegerArray instead).

Q15. Can you write your own container class and use it in a for-each loop?

Yes — implement the Iterable interface (a single method, iterator(), returning an Iterator). Any class that implements Iterable can be used directly as the source of a for-each loop.

Problem statement: Write a simple bounded container that supports for-each iteration over its stored elements.

public class BoundedContainer<ElementType> implements Iterable<ElementType> {
    private final ElementType[] storedElements;
    private int elementCount = 0;
 
    @SuppressWarnings("unchecked")
    public BoundedContainer(int capacity) {
        storedElements = (ElementType[]) new Object[capacity];
    }
 
    public void add(ElementType element) {
        storedElements[elementCount++] = element;
    }
 
    @Override
    public Iterator<ElementType> iterator() {
        return new Iterator<ElementType>() {
            private int currentIndex = 0;
 
            @Override
            public boolean hasNext() {
                return currentIndex < elementCount;
            }
 
            @Override
            public ElementType next() {
                return storedElements[currentIndex++];
            }
        };
    }
}
 
// Usage:
BoundedContainer<String> fruitBasket = new BoundedContainer<>(3);
fruitBasket.add("apple");
fruitBasket.add("pear");
for (String fruitName : fruitBasket) {
    System.out.println(fruitName);
}

Q16. How can you determine what type a generic parameter is at runtime? (Type erasure)

You generally can't, directly — Java generics use type erasure: generic type information exists only at compile time for type-checking, and is erased to raw types (or their bounds) in the compiled bytecode. At runtime, a List<String> and a List<Integer> are both just List. Workarounds include passing a Class<T> token explicitly to the constructor/method, or using reflection on a field/method signature that still retains generic signature metadata (via getGenericSuperclass() on a concrete subclass).

Q17. Is recursion possible in Java? How does it relate to the call stack, and what happens if it goes too deep?

Yes, Java fully supports recursion — a method calling itself, directly or indirectly. Each call pushes a new stack frame (holding local variables and the return address) onto the current thread's call stack. If recursion doesn't terminate, or terminates only after more nested calls than the stack can hold, the JVM throws a StackOverflowError. Java does not perform tail-call optimization, so even a well-structured recursive algorithm can overflow the stack for large inputs; an iterative rewrite (or an explicit stack data structure) is the usual fix for deep recursion in production code.

Problem statement: Compute a factorial recursively, illustrating call-stack growth.

public static long computeFactorial(int inputNumber) {
    // base case: stops the recursion from growing the call stack forever
    if (inputNumber <= 1) {
        return 1;
    }
    // recursive case: each call adds one frame to the call stack
    return inputNumber * computeFactorial(inputNumber - 1);
}

Q18. Give the simplest way to find out how long a method takes to execute, without a profiling tool.

Read the system time immediately before invoking the method and immediately after it returns, then subtract. This gives a coarse wall-clock measurement without needing external tooling.

long startTimeMillis = System.currentTimeMillis();
methodUnderTest();
long endTimeMillis = System.currentTimeMillis();
System.out.println("Time taken for execution: " + (endTimeMillis - startTimeMillis) + " ms");
 
// For higher precision (nanoseconds, monotonic, unaffected by clock adjustments), prefer:
long startTimeNanos = System.nanoTime();
methodUnderTest();
long endTimeNanos = System.nanoTime();
System.out.println("Time taken (ns): " + (endTimeNanos - startTimeNanos));

Note: If the method executes too quickly, the measured time may round down to zero milliseconds. Test on a method that does a meaningful amount of work, or run it in a loop many times and divide the total by the iteration count.

Q19. What are some Java Collections best practices worth mentioning in an interview?

  • Program to interfaces (List, Map, Set), not concrete implementations (ArrayList, HashMap), so the implementation can change without touching calling code.
  • Prefer the enhanced for-loop or Streams over manual index-based loops where possible — clearer and less error-prone.
  • Use Collections.unmodifiableXxx() or the List.of()/Map.of() factory methods to expose read-only views and prevent accidental external mutation.
  • Choose the right implementation for the access pattern: ArrayList for random access, LinkedList for frequent insert/remove at the ends, TreeMap/TreeSet for sorted data, ConcurrentHashMap for concurrent access.
  • Specify an initial capacity for ArrayList/HashMap when the approximate size is known in advance, to avoid repeated internal resizing.

Q20. How do you handle error conditions while writing or calling a stored procedure from Java?

A stored procedure should be designed to return an explicit error code or status output parameter when a business-logic operation fails, so the calling Java code can inspect that value and react accordingly. If the stored procedure call itself fails at the JDBC level (e.g. connection lost, syntax error, constraint violation), Java throws a SQLException, which must be caught, logged, and handled — typically by rolling back the current transaction.

try (CallableStatement storedProcedureCall =
         databaseConnection.prepareCall("{call updateAccountBalance(?, ?)}")) {
    storedProcedureCall.setInt(1, accountId);
    storedProcedureCall.setBigDecimal(2, newBalance);
    storedProcedureCall.execute();
} catch (SQLException databaseException) {
    // handle connection/database-level failures explicitly
    logger.error("Stored procedure call failed", databaseException);
    transactionManager.rollback();
}

Q21. What is the difference between shallow copy and deep copy?

A shallow copy duplicates an object's top-level fields, but any reference-type fields still point to the same underlying objects as the original — mutating a shared nested object through the copy affects the original too. A deep copy recursively duplicates every referenced object as well, producing a fully independent object graph. Object.clone() performs a shallow copy by default; a true deep copy requires manual recursive cloning, a copy constructor that itself deep-copies nested fields, or serialization-based cloning.

Section 2: Design Patterns

Quick Reference

Observer Pattern

Defines a one-to-many dependency between objects: when one object (the Subject) changes state, all its dependents (Observers) are notified and updated automatically. Advantages: loose coupling between subject and observer; supports broadcast-style communication to many listeners at once. Disadvantages: debugging can be difficult because control flow is indirect; can introduce memory leaks if observers are not properly unregistered.

Factory Pattern

A creational pattern that centralizes object construction behind static factory methods rather than direct constructor calls. Benefits include the ability to cache and reuse immutable objects, and the ability to introduce new subclasses or implementations without changing calling code.

Singleton Pattern — trade-offs

  • Advantages: hides construction dependencies from client code; provides one well-known access point that's easy to maintain; supports both lazy and eager initialization; can be extended into a factory-style pattern.
  • Disadvantages: makes unit testing harder by introducing global shared state; reduces potential for parallelism, since concurrent access to the shared instance typically requires locking.

Q1. What are design patterns, and have you used one in your own code?

Design patterns are proven, reusable solutions to commonly occurring design problems, distilled from the collective experience of many software engineers over time. They are not finished code you copy-paste — they are templates describing how to structure a solution to a class of problem. Using them is a form of design reuse: instead of solving a well-known problem from scratch, you apply a battle-tested approach and gain a shared vocabulary with other engineers (saying “we used a Factory here” instantly communicates intent).

Q2. Can you name a few design patterns used in the standard JDK library?

  • Decorator — used throughout java.io, e.g. BufferedReader wraps a Reader to add buffering.
  • Singleton — used by java.lang.Runtime and java.util.Calendar's getInstance() methods.
  • Factory Method — used by wrapper classes such as Boolean.valueOf(...), Integer.valueOf(...).
  • Observer — used in java.util.Observer/Observable, and extensively in Swing's event-listener model.
  • Iterator — the entire java.util.Iterator/Iterable contract underlying the enhanced for-loop.
  • Proxy — used by java.lang.reflect.Proxy for dynamic proxies.

Q3. What is the Factory pattern, and how does it differ from Abstract Factory?

The Factory pattern provides a single method that creates objects of one product family, hiding the concrete class-selection logic from the caller. This gives increased encapsulation: when client code asks a factory for a product rather than calling new directly, you can later swap the concrete implementation without touching client code — useful when the exact type to create depends on runtime configuration, when construction is complex enough to warrant centralizing, or when you want to control/limit/cache instances (object pooling).

Abstract Factory adds one further level of abstraction: it defines an interface for creating families of related objects, and you can have multiple concrete factory implementations, each responsible for producing a whole related set of products. For example, an AbstractFactory interface might be extended by AutomobileFactory, UserFactory, and RoleFactory, each creating objects within its own family — whereas a plain Factory would just have one createProduct() method returning one kind of object.

Q4. What is the Singleton pattern? Compare three ways to write it thread-safely.

Singleton restricts a class to a single instance shared across the whole application, typically used for expensive-to-create, globally-needed objects like configuration managers or connection pools. java.lang.Runtime is the textbook example.

Approach 1 — enum singleton (simplest, recommended since Java 5):

Enum instances are inherently singleton and thread-safe by the JVM's class-loading guarantees, so no explicit synchronization is needed.

public enum ConfigurationManager {
    INSTANCE;
 
    private final Properties settings = new Properties();
 
    public String getSetting(String key) {
        return settings.getProperty(key);
    }
}
// Usage: ConfigurationManager.INSTANCE.getSetting("timeout");

Approach 2 — double-checked locking:

Synchronize only the critical section (the code that actually creates the instance), not the entire getInstance() method. Synchronizing the whole method forces every caller to acquire the lock even long after the instance already exists, needlessly serializing access and hurting performance under high concurrency.

Problem statement: Implement a thread-safe Singleton database connection manager using double-checked locking, ensuring the instance is only constructed once even under concurrent first access.

public class DatabaseConnectionManager {
    // volatile prevents instruction reordering that could expose a
    // partially-constructed instance to another thread
    private static volatile DatabaseConnectionManager singletonInstance;
 
    private DatabaseConnectionManager() {
        // expensive initialization, e.g. opening a connection pool
    }
 
    public static DatabaseConnectionManager getInstance() {
        if (singletonInstance == null) {               // first check (no locking, fast path)
            synchronized (DatabaseConnectionManager.class) { // critical section only
                if (singletonInstance == null) {        // second check (inside the lock)
                    singletonInstance = new DatabaseConnectionManager();
                }
            }
        }
        return singletonInstance;
    }
}

The volatile keyword is essential here: without it, another thread could see a reference to a DatabaseConnectionManager object whose constructor hasn't finished running yet, due to instruction reordering by the JIT compiler or CPU.

Approach 3 — Bill Pugh static holder idiom:

Relies on the JVM's own class-loading guarantees: the nested SingletonHolder class is not loaded until getInstance() is first called, so initialization is both lazy and inherently thread-safe, with no synchronization overhead at all on the read path.

public class ConfigurationManagerHolder {
    private ConfigurationManagerHolder() { } // private constructor
 
    private static class SingletonHolder {
        private static final ConfigurationManagerHolder INSTANCE = new ConfigurationManagerHolder();
    }
 
    public static ConfigurationManagerHolder getInstance() {
        return SingletonHolder.INSTANCE; // loaded lazily, thread-safe
    }
}

Q5. What is the Observer design pattern in Java?

Observer establishes a one-to-many relationship where a Subject notifies all registered Observer objects whenever its state changes, so each observer can react accordingly. A common real-world example is a weather station: the WeatherData object is the Subject, and multiple display panels (current conditions, forecast, statistics) are Observers that update automatically whenever new data arrives. Java's built-in java.util.Observer/Observable are deprecated; modern code typically defines a custom Listener interface with a List<Listener> and a notifyAll()-style method invoked on state change, or uses PropertyChangeListener.

Q6. Give an example of the Decorator design pattern. Does it operate at the object level or class level?

Decorator operates at the object level — it wraps an existing object instance at runtime to add new behavior or responsibilities, without altering the original class's source code or affecting other instances of the same class. Java's I/O library is the classic example: BufferedReader wraps any Reader to add buffered reading, and BufferedWriter wraps any Writer to add buffered writing, both improving performance transparently.

// The underlying reader has no buffering
FileReader rawFileReader = new FileReader("data.txt");
// Decorator wraps it, adding buffering capability without changing FileReader itself
BufferedReader bufferedFileReader = new BufferedReader(rawFileReader);
 
String currentLine;
while ((currentLine = bufferedFileReader.readLine()) != null) {
    System.out.println(currentLine);
}

Figure: Decorator pattern

Q7. What is the MVC design pattern? Give one example.

Model-View-Controller separates an application into three interconnected components, each with a distinct responsibility: the Model holds the application's data and business logic, independent of how it's displayed; the View renders the Model's data to the user (a UI screen, an HTML page, a report); the Controller receives user input, invokes the appropriate operations on the Model, and selects the View to render the result.

This separation means the same Model can be displayed through multiple different Views without duplicating business logic, and the UI can be redesigned without touching the underlying data logic. Spring MVC is the classic Java example: a @Controller class handles an incoming HTTP request, calls a service/Model layer to fetch or update data, and forwards the result to a JSP or Thymeleaf View template for rendering.

Figure: MVC pattern flow

Q8. What is the Front Controller design pattern? Give an example.

Front Controller centralizes all incoming requests to an application through a single handler, rather than letting each request go directly to its own separate handler/page. The front controller handles common cross-cutting logic — authentication, logging, routing to the correct downstream handler — before delegating actual business processing to a specific handler, avoiding duplicated security/logging code across dozens of individual servlets. The classic Java EE example is Spring MVC's DispatcherServlet, or the older single front-controller Servlet pattern in JSP/Servlet applications.

Figure: Front Controller pattern

Q9. What is the Chain of Responsibility design pattern?

Chain of Responsibility passes a request along a chain of potential handler objects, where each handler decides either to process the request or pass it to the next handler in the chain. The sender doesn't need to know which handler will ultimately process it, decoupling senders from receivers. A real-world Java example is the Servlet Filter chain: an incoming HTTP request passes through a series of Filter objects (authentication, logging, compression), each of which can process the request and either forward it via chain.doFilter() or short-circuit the chain entirely. Logging frameworks like java.util.logging use a chain of Handler/Logger objects in the same spirit.

Figure: Chain of Responsibility pattern

Q10. What is the Adapter design pattern? Give examples in Java.

Adapter converts the interface of one class into another interface a client expects, letting classes with incompatible interfaces work together without modifying their source. It acts as a bridge/wrapper between an existing class and the interface the caller actually needs.

  • java.util.Arrays.asList(...) adapts an array to the List interface.
  • java.io.InputStreamReader adapts a byte-oriented InputStream to a character-oriented Reader.
  • java.io.OutputStreamWriter adapts a byte-oriented OutputStream to a character-oriented Writer.
// InputStreamReader is a textbook Adapter: it adapts the byte-based InputStream
// interface to the character-based Reader interface that BufferedReader needs.
InputStream rawByteStream = new FileInputStream("data.txt");
Reader adaptedCharacterReader = new InputStreamReader(rawByteStream, StandardCharsets.UTF_8);
BufferedReader lineReader = new BufferedReader(adaptedCharacterReader);

Figure: Adapter pattern

Q11. What is the Builder pattern, and when should it be used?

Builder constructs complex objects step by step via chained method calls, avoiding telescoping constructors with many parameters. It's useful when an object has many optional fields: it improves readability (e.g. Person.builder().name("Alice").age(30).build()) and allows the resulting object to be immutable, since it's only constructed once all properties are set.

Q12. What is Dependency Injection, and how does Spring implement Inversion of Control?

Dependency Injection (DI) supplies an object's dependencies externally — via constructor, setter, or field — rather than having the object create them itself, promoting loose coupling and easier testing (dependencies can be mocked). Inversion of Control (IoC) is the broader principle DI implements: control over object creation and wiring is inverted from application code to a container/framework. Spring implements IoC via the ApplicationContext, which reads bean definitions (via annotations like @Autowired/@Inject or Java/XML configuration) and manages object lifecycles, injecting dependencies automatically and reducing tight coupling and boilerplate `new` calls throughout the codebase.

Section 3: Multithreading & Concurrency

The Executor Framework

Before java.util.concurrent existed, developers managed threads manually by creating new Thread objects directly — which does not scale well and makes it hard to control the number of concurrently running threads. The Executor framework decouples task submission from the mechanics of how each task actually runs: how threads are created, scheduled, reused, and shut down.

Executor

The simplest interface in the framework, in java.util.concurrent. It exposes a single method, execute(Runnable), whose entire purpose is to separate “submitting a task” from “deciding how and when that task actually runs.”

Executors

A factory class, also in java.util.concurrent, providing static factory methods that return various kinds of ExecutorService, ScheduledExecutorService, and ThreadFactory instances, so you rarely need to implement Executor yourself.

newFixedThreadPool()

One of the most commonly used factory methods on Executors. It creates a thread pool with a fixed number of reusable threads. If a thread dies unexpectedly before its task completes, a fresh thread from the pool automatically takes over remaining work, keeping the pool size constant.

Problem statement: Submit a recurring background task to a fixed-size thread pool without managing threads manually.

// RecurringCounterTask.java - prints an incrementing counter every second
package com.interviewguide.concurrency;
 
public class RecurringCounterTask implements Runnable {
    @Override
    public void run() {
        try {
            for (int counterValue = 0; ; counterValue++) {
                System.out.println(counterValue);
                Thread.sleep(1000);
            }
        } catch (InterruptedException interruptedException) {
            // restore the interrupt status so calling code can observe it
            Thread.currentThread().interrupt();
        }
    }
}
 
// TaskRunner.java - submits the task to a fixed-size thread pool
package com.interviewguide.concurrency;
 
import java.util.concurrent.Executor;
import java.util.concurrent.Executors;
 
public class TaskRunner {
    public static void main(String[] args) {
        Executor threadPoolExecutor = Executors.newFixedThreadPool(10);
        threadPoolExecutor.execute(new RecurringCounterTask());
    }
}

Executor vs. ExecutorService

Both are interfaces in java.util.concurrent. ExecutorService extends Executor and adds significant lifecycle and coordination control:

  • shutdown() / shutdownNow() — gracefully or forcibly stop accepting and running tasks.
  • awaitTermination(timeout, unit) — block until all tasks complete or the timeout elapses.
  • isShutdown() / isTerminated() — query the pool's lifecycle state.
  • invokeAny(...) / invokeAll(...) — submit a batch of Callable tasks and either get the first successful result, or wait for all of them.
  • submit(...) — unlike execute(), returns a Future so you can retrieve a result or exception.
ExecutorService threadPoolExecutor = Executors.newFixedThreadPool(10);
threadPoolExecutor.execute(new RecurringCounterTask());
// attempts to interrupt all running tasks and stop the pool immediately
threadPoolExecutor.shutdownNow();

Note: shutdownNow() attempts to stop all actively executing tasks by interrupting them. In the example above, the task is blocked inside Thread.sleep(), so the interrupt causes sleep() to throw an InterruptedException immediately, unwinding that task's run() method.

Thread Safety & Synchronization Fundamentals

Thread.sleep()

  • The static method Thread.sleep(long millis) forces the currently executing thread to pause for at least the given duration.
  • sleep() declares a checked exception, InterruptedException, so every call must either be wrapped in a try/catch or the enclosing method must declare it in its own throws clause.
  • Calling sleep() gives other threads a chance to run, but there is no guarantee about scheduling order afterward — sleep() is a simple (if crude) way to encourage fair thread switching, not a substitute for proper synchronization.
try {
    Thread.sleep(200); // pause this thread for ~200 milliseconds
} catch (InterruptedException interruptedException) {
    Thread.currentThread().interrupt(); // restore the interrupt flag
}

Why shared mutable state is dangerous

  • Serious problems arise when two or more threads have access to the same mutable object on the heap.
  • If one thread is interrupted mid-way through modifying an object's internal state, another thread could observe or modify that object while it's only half-updated, corrupting data.
  • To make a class thread-safe, you must decide which sequences of statements need to be treated as a single atomic operation — one that runs to completion, uninterrupted by any other thread, before another thread may touch the same object's state.

The synchronized keyword

  • Use synchronized on a method declaration to prevent more than one thread from entering that method (on the same object instance) at the same time.
  • Every object has a single intrinsic lock (monitor). It only becomes relevant once an object has one or more synchronized methods.
  • A thread attempting to enter a synchronized method must first acquire that object's lock; if another thread holds it, the requesting thread blocks until it becomes available.
  • Even with multiple synchronized methods on a class, there is still only one lock per object instance — once any thread enters one synchronized method on an object, no other thread can enter any other synchronized method on that same object concurrently. This is precisely what protects an object's internal data.
public class BankAccount {
    private double currentBalance;
 
    // synchronized: only one thread at a time can execute THIS method
    // on a given BankAccount instance
    public synchronized void withdrawFunds(double withdrawalAmount) {
        if (currentBalance >= withdrawalAmount) {
            currentBalance -= withdrawalAmount;
        }
    }
 
    // this method is ALSO locked out while withdrawFunds() is running,
    // because they share the same object-level lock
    public synchronized void depositFunds(double depositAmount) {
        currentBalance += depositAmount;
    }
}

Note: Synchronizing an entire method is the simplest approach, but locks out ALL synchronized methods on that instance for the duration, even unrelated ones. For finer-grained control, synchronize only the specific block of code that touches shared state, as shown in Q1 below.

Multithreading Interview Questions

Q1. What is the difference between a synchronized method and a synchronized block?

A synchronized method locks the entire method body using the intrinsic lock of the object it's called on (or the Class object, if the method is static). A synchronized block lets you lock on any explicit object you choose, and only for the specific statements inside the block. Synchronized blocks are generally preferred because they minimize the amount of code executed while holding the lock, reducing contention and improving throughput.

Problem statement: Reduce inventory stock safely under concurrent access, locking only the critical section rather than the entire method.

public class InventoryManager {
    private int stockCount;
    private final Object stockLock = new Object();
 
    public void reduceStock(int quantity) {
        // only this critical section is locked, not the whole method
        synchronized (stockLock) {
            if (stockCount >= quantity) {
                stockCount -= quantity;
            }
        }
        // any non-shared-state work can happen here, outside the lock
        logStockChange(quantity);
    }
 
    private void logStockChange(int quantity) {
        System.out.println("Reduced stock by " + quantity);
    }
}

Q2. What is a deadlock, and how can you avoid it?

A deadlock occurs when two or more threads are each waiting for a lock held by one of the others, so none of them can ever proceed. The classic example is Thread A holding Lock 1 and waiting for Lock 2, while Thread B holds Lock 2 and waits for Lock 1.

Common ways to avoid deadlock:

  • Always acquire multiple locks in a consistent, global order across all threads.
  • Use tryLock(timeout) from java.util.concurrent.locks.Lock instead of blocking indefinitely, so a thread can back off and retry if it cannot acquire a lock within a reasonable time.
  • Minimize the scope and duration for which locks are held.
  • Avoid calling out to unknown/overridable code while holding a lock.
// Deadlock-prone: threads may acquire lockA and lockB in different orders
synchronized (lockA) {
    synchronized (lockB) {
        // ...
    }
}
 
// Fix: always acquire locks in the same global order (e.g. by a consistent ID)
Object firstLock  = accountA.getId() < accountB.getId() ? lockA : lockB;
Object secondLock = accountA.getId() < accountB.getId() ? lockB : lockA;
synchronized (firstLock) {
    synchronized (secondLock) {
        // safe: every thread acquires locks in the same order
    }
}

Q3. What is the difference between wait()/notify() and sleep()?

wait() and notify() are methods on Object, used for inter-thread communication. A thread calling wait() must already hold the object's monitor lock; calling wait() releases that lock and suspends the thread until another thread calls notify() or notifyAll() on the same object. sleep(), by contrast, is a static Thread method that pauses the current thread for a fixed duration WITHOUT releasing any locks it holds.

Problem statement: Implement a simple producer/consumer handoff using wait()/notify() on a shared buffer.

class SharedBuffer {
    private final Object bufferLock = new Object();
    private boolean dataReady = false;
 
    void produce() {
        synchronized (bufferLock) {
            dataReady = true;
            bufferLock.notify(); // wake up a thread waiting on bufferLock
        }
    }
 
    void consume() throws InterruptedException {
        synchronized (bufferLock) {
            while (!dataReady) {
                bufferLock.wait(); // releases the lock and waits to be notified
            }
            // process the data
        }
    }
}

Q4. What is a race condition? Give an example.

A race condition occurs when the correctness of a program depends on the relative timing of multiple threads, and the outcome varies depending on which thread happens to execute first. A classic example is two threads incrementing a shared counter without synchronization: the increment (read, add one, write back) is not atomic, so both threads can read the same initial value before either writes back, and one increment is silently lost.

public class UnsafeCounter {
    private int count = 0;
 
    public void increment() {
        count++; // NOT atomic: read, add 1, write back - three separate steps
    }
}
// If two threads call increment() concurrently on the same instance without
// synchronization, one of the increments can be lost due to interleaving.
 
public class SafeCounter {
    private int count = 0;
 
    public synchronized void increment() {
        count++; // now atomic with respect to other synchronized calls
    }
}

Q5. What is the volatile keyword, and when should you use it?

volatile guarantees two things for a field: (1) every read of the field always sees the most recently written value from any thread (visibility), and (2) the compiler and CPU will not reorder instructions around accesses to that field. It does NOT make compound operations like count++ atomic. volatile is appropriate for simple flags or references that are written by one thread and read by others, such as a shutdown flag or the double-checked-locking Singleton pattern shown in Section 2.

public class Worker implements Runnable {
    private volatile boolean shutdownRequested = false;
 
    public void requestShutdown() {
        shutdownRequested = true; // visible to the worker thread immediately
    }
 
    @Override
    public void run() {
        while (!shutdownRequested) {
            // do work
        }
    }
}

Q6. What is the difference between Callable and Runnable?

Runnable's run() method returns void and cannot throw checked exceptions. Callable<V>'s call() method returns a value of type V and can throw a checked exception. Callable is designed to be used with ExecutorService.submit(), which returns a Future<V> that lets you retrieve the result once the task finishes.

Callable<Integer> computeSquareTask = () -> {
    int inputValue = 7;
    return inputValue * inputValue;
};
 
ExecutorService threadPoolExecutor = Executors.newSingleThreadExecutor();
Future<Integer> resultFuture = threadPoolExecutor.submit(computeSquareTask);
Integer squareResult = resultFuture.get(); // blocks until the result is ready
System.out.println(squareResult); // 49
threadPoolExecutor.shutdown();

Q7. What is the difference between Executor.submit() and Executor.execute()?

Both methods schedule a task for execution on a thread pool, but they differ in what they return and how they handle exceptions:

  • execute(Runnable) returns void. There is no way to retrieve a result or check whether the task completed successfully from the call itself.
  • submit(Callable) or submit(Runnable) returns a Future object, which lets you call get() to retrieve the task's result (blocking until it's done) or check isDone()/cancel().

The exception handling behavior also differs. If a task submitted with execute() throws an uncaught exception, it propagates to the thread's UncaughtExceptionHandler (by default this just prints a stack trace to System.err). If a task is submitted with submit(), any exception — checked or unchecked — is instead captured and stored inside the returned Future, surfacing only when you call future.get(), which re-throws it wrapped in an ExecutionException.

ExecutorService threadPool = Executors.newFixedThreadPool(4);
 
// execute(): fire-and-forget, exceptions go to the uncaught exception handler
threadPool.execute(() -> { throw new RuntimeException("boom"); });
 
// submit(): exception is captured inside the Future
Future<Integer> resultFuture = threadPool.submit(() -> {
    throw new RuntimeException("boom");
});
try {
    resultFuture.get(); // throws ExecutionException wrapping the RuntimeException
} catch (ExecutionException wrappedException) {
    System.out.println("Caught: " + wrappedException.getCause());
} catch (InterruptedException interruptedException) {
    Thread.currentThread().interrupt();
}

Q8. What is ConcurrentHashMap, and how is it different from a synchronized HashMap?

ConcurrentHashMap (java.util.concurrent) is a thread-safe map designed for high concurrency. Unlike Collections.synchronizedMap(new HashMap<>()), which uses a single lock for the entire map (so only one thread can access it at a time, even for unrelated keys), ConcurrentHashMap internally partitions its data so that multiple threads can read and write concurrently with minimal contention. In modern JDKs (Java 8+) it uses a combination of CAS (compare-and-swap) operations and fine-grained locking per bin, rather than locking the whole map.

  • Read operations in ConcurrentHashMap generally do not block at all.
  • Iterators returned by ConcurrentHashMap are weakly consistent: they never throw ConcurrentModificationException, and reflect the state of the map at some point at or after the iterator was created.
  • A synchronized HashMap's iterator, by contrast, throws ConcurrentModificationException if the map is structurally modified by another thread during iteration.

Internally (JDK 8+), ConcurrentHashMap achieves this without locking the entire map by using CAS-based updates for the common case of inserting into an empty bin, and synchronizing only on the head node of a single bin when a collision chain must be modified — so writes to different bins never contend with each other.

Q9. What is a ThreadLocal, and what memory-leak risk does it carry in application-server or thread-pool environments?

ThreadLocal<T> gives each thread its own independent copy of a variable, invisible to other threads — useful for per-thread context such as a database connection, a user session, or a SimpleDateFormat instance (which is not itself thread-safe). Internally, each Thread object holds a small map from ThreadLocal instance to value.

The memory-leak risk arises specifically in thread-pool environments (application servers, ExecutorService pools) because pooled threads are long-lived and reused across many logical tasks. If a task sets a ThreadLocal value and never calls remove() when it finishes, the value (and anything it references) stays attached to that pooled thread indefinitely, since the thread itself is never garbage collected. Over time and many task executions, this silently accumulates memory — and can also leak stale/incorrect context into a later, unrelated task reusing the same pooled thread. The fix is to always clear a ThreadLocal in a finally block once the task using it completes.

private static final ThreadLocal<SimpleDateFormat> DATE_FORMAT_HOLDER =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
 
public String formatOrderDate(Date orderDate) {
    try {
        return DATE_FORMAT_HOLDER.get().format(orderDate);
    } finally {
        // essential in a pooled-thread environment: prevents the value (and
        // anything it references) from leaking into the next task on this thread
        DATE_FORMAT_HOLDER.remove();
    }
}

Q10. Explain the Java Memory Model (JMM) and why volatile alone doesn't make compound operations atomic.

The Java Memory Model defines the rules for how and when writes made by one thread become visible to reads made by another thread, in the presence of compiler, JIT, and CPU-level instruction reordering. Without any synchronization, the JMM makes almost no visibility guarantees — one thread can run indefinitely without ever observing another thread's write to a shared, non-volatile field, because the reader may be working from a cached or reordered view of memory. Synchronization primitives (synchronized, volatile, java.util.concurrent locks) establish happens-before relationships, which are the JMM's formal guarantee that everything a thread did before a given point is visible to another thread after it reaches a corresponding point.

volatile establishes happens-before ordering for reads and writes of that single field, and prevents reordering around it — but a compound operation like count++ is actually three separate steps (read, increment, write). Even with count declared volatile, another thread can interleave between those steps: Thread A reads the current value, Thread B reads the same (still-old) value, both increment locally, and both write back, so one increment is lost. volatile guarantees visibility of the field, not atomicity of multi-step operations performed on it. True atomicity requires either synchronized around the whole read-modify-write sequence, or an atomic class from java.util.concurrent.atomic (e.g. AtomicInteger.incrementAndGet(), which performs the operation as a single CAS-based primitive).

Q11. ConcurrentHashMap internals — how does it achieve thread safety without locking the entire map?

Modern ConcurrentHashMap (Java 8+) is backed by the same array-of-buckets structure as HashMap, but synchronizes at the level of an individual bin (bucket) rather than the whole table. Inserting into an empty bin is done with a CAS (compare-and-swap) operation — lock-free. Only when a collision occurs and the bin's linked list (or, for large bins, its red-black tree) must be modified does the implementation synchronize, and it synchronizes only on that bin's head node, not on the map as a whole. This means writes targeting different bins never contend with each other, and reads are largely lock-free throughout, giving far higher throughput under concurrent access than a single coarse-grained lock over the entire map would.

Q12. What are the differences between synchronized, ReentrantLock, and StampedLock? When would you choose each?

synchronized is the built-in intrinsic lock: simplest to use, automatically released even if an exception is thrown, but strictly block-structured (you can't try to acquire it with a timeout, can't interrupt a thread waiting on it, and can't inspect whether it's currently held).

ReentrantLock (java.util.concurrent.locks) offers everything synchronized does, plus: tryLock() and tryLock(timeout, unit) for non-blocking or bounded-wait acquisition; lockInterruptibly() so a waiting thread can respond to interruption; fairness ordering (an optional constructor flag that grants the lock in the order threads requested it, avoiding thread starvation); and multiple associated Condition objects (in place of a single implicit wait/notify per object). The cost is that you must remember to unlock() in a finally block yourself — the JVM won't do it for you on an exception.

StampedLock (Java 8+) adds a third mode beyond simple read/write locking: an optimistic read, which doesn't block writers at all and instead returns a stamp that the reader later validates; if a write occurred in the meantime, the optimistic read is discarded and retried under a full read lock. This makes StampedLock significantly faster than ReentrantReadWriteLock for read-heavy workloads, at the cost of a more error-prone API (it is not reentrant, and forgetting to validate the optimistic stamp silently reads torn/stale data).

Choice: use synchronized for simple cases where its block-structured nature is sufficient; use ReentrantLock when you need tryLock/timeouts, interruptible waiting, fairness, or multiple wait conditions; use StampedLock for very read-heavy hot paths where the optimistic-read fast path's extra throughput is worth the added complexity and care.

Q13. Explain the difference between CompletableFuture and traditional Future. Design an async pipeline with error handling.

A plain Future only supports blocking retrieval of a result via get() (optionally with a timeout) — there is no way to register a callback, chain further work onto its completion, or combine it with another Future without a separate thread blocking on get(). CompletableFuture (java.util.concurrent, Java 8+) implements both Future and CompletionStage, adding a rich set of composition methods: thenApply() to transform a result, thenCompose() to chain a dependent async operation, thenCombine() to join two independent futures, and exceptionally()/handle() for error handling — all without blocking a thread to wait for the prior stage.

Problem statement: Build an asynchronous pipeline that fetches a customer's profile, then fetches their order history, combines both into a summary, and falls back to a default summary if any stage fails.

public CompletableFuture<CustomerSummary> buildCustomerSummaryAsync(String customerId) {
    CompletableFuture<CustomerProfile> profileFuture =
            CompletableFuture.supplyAsync(() -> customerService.fetchProfile(customerId));
 
    CompletableFuture<List<Order>> orderHistoryFuture =
            CompletableFuture.supplyAsync(() -> orderService.fetchOrderHistory(customerId));
 
    return profileFuture
            // thenCombine: merge two independent async results once both complete
            .thenCombine(orderHistoryFuture, CustomerSummary::new)
            // exceptionally: fall back to a safe default if any prior stage failed
            .exceptionally(pipelineError -> {
                logger.warn("Falling back to default summary for " + customerId, pipelineError);
                return CustomerSummary.defaultFor(customerId);
            });
}
