Section 1: Core Java Fundamentals

Q1. What is an immutable object? Can you write an immutable class?

An immutable object is an object whose state cannot be changed after construction. Any “modification” instead produces a brand-new object, leaving the original untouched. String is the most common example of an immutable class in Java.

Immutable classes are typically declared final, to stop a subclass from overriding methods in a way that could break immutability. You can achieve the same safety without the final keyword by making fields private and never modifying them after the constructor runs.

Rules for writing your own immutable class:

  • Declare the class as final so it cannot be subclassed.
  • Make all fields private and final.
  • Do not provide setter methods.
  • Initialize all fields via the constructor only.
  • If a field is a mutable object (e.g. a Date or a List), return a defensive copy from any getter, rather than the original reference.

Problem statement: Implement an immutable 2D point class that supports a “translate” operation without mutating the original instance.

public final class ImmutablePoint {
 
    private final int xCoordinate;
    private final int yCoordinate;
 
    public ImmutablePoint(int xCoordinate, int yCoordinate) {
        this.xCoordinate = xCoordinate;
        this.yCoordinate = yCoordinate;
    }
 
    public int getXCoordinate() {
        return xCoordinate;
    }
 
    public int getYCoordinate() {
        return yCoordinate;
    }
 
    // "Modifying" an immutable object returns a NEW instance instead
    // of mutating the fields of the current one.
    public ImmutablePoint translate(int deltaX, int deltaY) {
        return new ImmutablePoint(xCoordinate + deltaX, yCoordinate + deltaY);
    }
}

Q2. Do all properties of an immutable object need to be final?

Not strictly. You can achieve the same effect by making a field non-final but private, and simply never modifying it anywhere except inside the constructor. Marking fields final is still best practice because it lets the compiler enforce immutability for you and communicates intent clearly to other developers.

Q3. What is the difference between creating a String with new() and with a literal?

When you create a String using the new() operator, a new object is always allocated on the heap, and it is NOT automatically added to the String pool. When you create a String using a literal, Java automatically places it into the String pool (also called the intern pool), which lives on the heap.

Problem statement: Demonstrate the reference-identity difference between a heap-allocated String and a pooled String literal, and show how to manually intern a String.

String heapString = new String("Test");   // new object in heap, NOT in string pool
String pooledString = "Test";              // placed into the string pool automatically
 
// To manually add the heap-allocated string to the pool:
String internedString = heapString.intern();
 
System.out.println(pooledString == internedString); // true  - both refer to the pooled instance
System.out.println(pooledString == heapString);      // false - different objects

The String pool exists so that identical string literals can share a single object in memory, saving space, since Strings are immutable and safe to share.

Q4. How does substring() work internally in String?

substring() creates a new String object representing a portion of the original string, defined by the given start index (inclusive) and end index (exclusive). In older JDKs (before Java 7 update 6), substring() shared the original character array internally and only changed the offset and length fields — fast, but capable of causing a memory leak if a huge original string was kept alive by a tiny substring. Since that update, substring() copies the relevant characters into a new array, so the original string can be garbage collected independently.

String original = "Hello, World!";
String extracted = original.substring(7, 12); // "World"
// In modern Java, "extracted" holds its own independent char array,
// so "original" is free to be garbage collected even if "extracted" is still referenced.

Q5. Which two methods do you need to implement for a key object in a HashMap?

Any object used as a key in a HashMap must correctly implement equals() and hashCode(). These two methods work together: hashCode() determines which bucket the key is stored in, and equals() confirms an exact match once the correct bucket is found.

Q6. Where do equals() and hashCode() come into play during a get() operation?

When you call map.get(key), HashMap first calls hashCode() on the key to compute a bucket index. It then walks the entries in that bucket (there may be more than one, due to hash collisions) and calls equals() on each candidate key until it finds a match. If hashCode() is implemented poorly (e.g. it always returns the same value), every key lands in the same bucket, degrading lookups toward O(n).

Q7. When do you override hashCode() and equals(), and what happens if you don't?

Override both whenever you need to compare objects for logical equality (rather than reference equality), or whenever instances of the class will be used as keys in a hash-based collection (HashMap, HashSet, Hashtable) or stored as elements in one. The two methods must remain consistent: if two objects are equal according to equals(), they must return the same hashCode().

If a class does not override hashCode(), it inherits Object's default implementation, based on the object's memory address. Two logically-equal objects (even if equals() is overridden to compare their content) will then likely produce different hash codes, land in different buckets, and you will not be able to retrieve a value using a different-but-equal key instance than the one originally used to insert it.

Performance implication: a poorly-implemented hashCode() — or the default identity-based one when content-based equality was intended — causes more hash collisions. When many keys land in the same bucket, HashMap degrades from average O(1) lookup toward O(n) (or O(log n) in Java 8+, where large buckets convert to a red-black tree), because it must linearly scan (or tree-search) the colliding entries and call equals() on each one.

Q8. What's wrong with using HashMap in a multi-threaded environment? When can get() enter an infinite loop?

HashMap is not thread-safe. If multiple threads modify a HashMap concurrently — particularly during a resize operation (rehashing when the load-factor threshold is exceeded) — the internal linked structure of a bucket can become corrupted. In older Java versions (pre-Java 8), this could literally create a circular reference within a bucket's linked list, causing get() to loop forever while traversing that bucket. In Java 8+, the specific infinite-loop bug from bucket resizing was mitigated, but HashMap can still corrupt state under concurrent modification. Regardless of JDK version, HashMap should never be shared across threads without external synchronization — use ConcurrentHashMap instead.

Q9. Can you write code for iterating over a HashMap in both the old (pre-Java-5) style and the modern style?

Problem statement: Iterate over the key/value pairs of a HashMap using three progressively modern styles.

Map<String, Integer> inventoryCounts = new HashMap<>();
inventoryCounts.put("apples", 50);
inventoryCounts.put("bananas", 30);
 
// Old style (pre-Java 5): explicit Iterator over entrySet()
Iterator<Map.Entry<String, Integer>> entryIterator = inventoryCounts.entrySet().iterator();
while (entryIterator.hasNext()) {
    Map.Entry<String, Integer> currentEntry = entryIterator.next();
    System.out.println(currentEntry.getKey() + " = " + currentEntry.getValue());
}
 
// Modern style (Java 5+): enhanced for-loop over entrySet()
for (Map.Entry<String, Integer> currentEntry : inventoryCounts.entrySet()) {
    System.out.println(currentEntry.getKey() + " = " + currentEntry.getValue());
}
 
// Java 8+: forEach with a lambda
inventoryCounts.forEach((itemName, itemCount) ->
    System.out.println(itemName + " = " + itemCount));

Q10. How does HashMap's performance compare to TreeMap? Which would you choose and when?

HashMap offers average O(1) get/put, backed by an array of buckets with hashCode()-based dispatch, but gives no ordering guarantee over its keys. TreeMap offers guaranteed O(log n) get/put, backed by a red-black tree, and keeps keys in sorted order (natural ordering or a supplied Comparator), and additionally supports range queries such as firstKey(), lastKey(), headMap(), and tailMap(). Choose HashMap when you only need fast lookups and don't care about order; choose TreeMap when you need the keys sorted or need range-based navigation, and can accept the O(log n) cost.

Q11. How do you safely remove elements from an ArrayList while iterating over it?

Removing directly from a List with a for-each loop (or by index while iterating forward) throws ConcurrentModificationException or skips elements, because the List's internal modCount changes underneath the iterator. The safe approaches are to use the Iterator's own remove() method, or Java 8+'s removeIf().

List<String> shoppingCartItems = new ArrayList<>(List.of("milk", "eggs", "expired-cheese", "bread"));
 
// Safe: Iterator.remove() keeps the iterator's internal state consistent
Iterator<String> cartIterator = shoppingCartItems.iterator();
while (cartIterator.hasNext()) {
    String currentItem = cartIterator.next();
    if (currentItem.startsWith("expired")) {
        cartIterator.remove();
    }
}
 
// Safe and concise: Java 8+ removeIf()
shoppingCartItems.removeIf(itemName -> itemName.startsWith("expired"));

Q12. Can we create an immutable object that contains a mutable field, and still keep it truly immutable?

Yes, by never exposing the mutable field's original reference. The constructor must store a defensive copy of the mutable input, and every getter must return a defensive copy (or an unmodifiable view) rather than the field itself. Without this, a caller who obtains the reference could mutate the “immutable” object's internal state from outside.

public final class ImmutableSchedule {
    private final List<String> appointmentTimes;
 
    public ImmutableSchedule(List<String> appointmentTimes) {
        // defensive copy on the way in: caller's list can't mutate our state later
        this.appointmentTimes = new ArrayList<>(appointmentTimes);
    }
 
    public List<String> getAppointmentTimes() {
        // defensive copy on the way out: caller can't mutate our internal list
        return Collections.unmodifiableList(new ArrayList<>(appointmentTimes));
    }
}

Q13. Can you cast an int into a byte? What happens if the int is larger than a byte can hold?

Yes, via an explicit narrowing primitive cast: (byte) someInt. If the int's value doesn't fit in a byte's 8-bit signed range (-128 to 127), the higher-order bits are simply discarded (silent truncation, not an exception), which can produce a surprising, wrapped-around value. This is why narrowing casts of user-controlled values should be range-checked first.

int largeValue = 130;
byte truncatedValue = (byte) largeValue; // 130 doesn't fit in a byte -> wraps to -126
System.out.println(truncatedValue);       // prints -126, not 130

Q14. Can you make an array volatile in Java? What does that actually guarantee?

Yes, you can declare an array reference volatile, e.g. private volatile int[] counters. However, volatile only guarantees visibility and ordering for the reference itself — that is, for reassigning the array variable to point at a different array. It does NOT make the individual elements inside the array volatile: writes to counters[3] by one thread are not guaranteed to be visible to another thread without additional synchronization (e.g. using AtomicIntegerArray instead).

Q15. Can you write your own container class and use it in a for-each loop?

Yes — implement the Iterable interface (a single method, iterator(), returning an Iterator). Any class that implements Iterable can be used directly as the source of a for-each loop.

Problem statement: Write a simple bounded container that supports for-each iteration over its stored elements.

public class BoundedContainer<ElementType> implements Iterable<ElementType> {
    private final ElementType[] storedElements;
    private int elementCount = 0;
 
    @SuppressWarnings("unchecked")
    public BoundedContainer(int capacity) {
        storedElements = (ElementType[]) new Object[capacity];
    }
 
    public void add(ElementType element) {
        storedElements[elementCount++] = element;
    }
 
    @Override
    public Iterator<ElementType> iterator() {
        return new Iterator<ElementType>() {
            private int currentIndex = 0;
 
            @Override
            public boolean hasNext() {
                return currentIndex < elementCount;
            }
 
            @Override
            public ElementType next() {
                return storedElements[currentIndex++];
            }
        };
    }
}
 
// Usage:
BoundedContainer<String> fruitBasket = new BoundedContainer<>(3);
fruitBasket.add("apple");
fruitBasket.add("pear");
for (String fruitName : fruitBasket) {
    System.out.println(fruitName);
}

Q16. How can you determine what type a generic parameter is at runtime? (Type erasure)

You generally can't, directly — Java generics use type erasure: generic type information exists only at compile time for type-checking, and is erased to raw types (or their bounds) in the compiled bytecode. At runtime, a List<String> and a List<Integer> are both just List. Workarounds include passing a Class<T> token explicitly to the constructor/method, or using reflection on a field/method signature that still retains generic signature metadata (via getGenericSuperclass() on a concrete subclass).

Q17. Is recursion possible in Java? How does it relate to the call stack, and what happens if it goes too deep?

Yes, Java fully supports recursion — a method calling itself, directly or indirectly. Each call pushes a new stack frame (holding local variables and the return address) onto the current thread's call stack. If recursion doesn't terminate, or terminates only after more nested calls than the stack can hold, the JVM throws a StackOverflowError. Java does not perform tail-call optimization, so even a well-structured recursive algorithm can overflow the stack for large inputs; an iterative rewrite (or an explicit stack data structure) is the usual fix for deep recursion in production code.

Problem statement: Compute a factorial recursively, illustrating call-stack growth.

public static long computeFactorial(int inputNumber) {
    // base case: stops the recursion from growing the call stack forever
    if (inputNumber <= 1) {
        return 1;
    }
    // recursive case: each call adds one frame to the call stack
    return inputNumber * computeFactorial(inputNumber - 1);
}

Q18. Give the simplest way to find out how long a method takes to execute, without a profiling tool.

Read the system time immediately before invoking the method and immediately after it returns, then subtract. This gives a coarse wall-clock measurement without needing external tooling.

long startTimeMillis = System.currentTimeMillis();
methodUnderTest();
long endTimeMillis = System.currentTimeMillis();
System.out.println("Time taken for execution: " + (endTimeMillis - startTimeMillis) + " ms");
 
// For higher precision (nanoseconds, monotonic, unaffected by clock adjustments), prefer:
long startTimeNanos = System.nanoTime();
methodUnderTest();
long endTimeNanos = System.nanoTime();
System.out.println("Time taken (ns): " + (endTimeNanos - startTimeNanos));

Note: If the method executes too quickly, the measured time may round down to zero milliseconds. Test on a method that does a meaningful amount of work, or run it in a loop many times and divide the total by the iteration count.

Q19. What are some Java Collections best practices worth mentioning in an interview?

  • Program to interfaces (List, Map, Set), not concrete implementations (ArrayList, HashMap), so the implementation can change without touching calling code.
  • Prefer the enhanced for-loop or Streams over manual index-based loops where possible — clearer and less error-prone.
  • Use Collections.unmodifiableXxx() or the List.of()/Map.of() factory methods to expose read-only views and prevent accidental external mutation.
  • Choose the right implementation for the access pattern: ArrayList for random access, LinkedList for frequent insert/remove at the ends, TreeMap/TreeSet for sorted data, ConcurrentHashMap for concurrent access.
  • Specify an initial capacity for ArrayList/HashMap when the approximate size is known in advance, to avoid repeated internal resizing.

Q20. How do you handle error conditions while writing or calling a stored procedure from Java?

A stored procedure should be designed to return an explicit error code or status output parameter when a business-logic operation fails, so the calling Java code can inspect that value and react accordingly. If the stored procedure call itself fails at the JDBC level (e.g. connection lost, syntax error, constraint violation), Java throws a SQLException, which must be caught, logged, and handled — typically by rolling back the current transaction.

try (CallableStatement storedProcedureCall =
         databaseConnection.prepareCall("{call updateAccountBalance(?, ?)}")) {
    storedProcedureCall.setInt(1, accountId);
    storedProcedureCall.setBigDecimal(2, newBalance);
    storedProcedureCall.execute();
} catch (SQLException databaseException) {
    // handle connection/database-level failures explicitly
    logger.error("Stored procedure call failed", databaseException);
    transactionManager.rollback();
}

Q21. What is the difference between shallow copy and deep copy?

A shallow copy duplicates an object's top-level fields, but any reference-type fields still point to the same underlying objects as the original — mutating a shared nested object through the copy affects the original too. A deep copy recursively duplicates every referenced object as well, producing a fully independent object graph. Object.clone() performs a shallow copy by default; a true deep copy requires manual recursive cloning, a copy constructor that itself deep-copies nested fields, or serialization-based cloning.

Q22. What does the final keyword mean for a class, a method, and a field? How does a final class differ from an abstract class?

  • final class — cannot be subclassed (e.g., String, Integer).
  • final method — cannot be overridden, so subclasses cannot change its behaviour.
  • final field/variable — assigned exactly once; for references the reference is fixed, but the object's state can still change unless it is immutable.
  • Abstract class — meant to be extended; can contain abstract methods; cannot be instantiated.
  • final vs abstract — opposites: final forbids inheritance, abstract requires it, so a class can never be both.

Q23. What does the static keyword mean for a class, a method, and a field?

  • static field — one copy shared by all instances, stored with the class, initialised once at class loading.
  • static method — belongs to the class, called without an instance, cannot use this or access instance members directly; cannot be overridden (only hidden).
  • static block — runs once when the class is initialised.
  • static nested class — a nested class that does not hold a reference to an outer instance. Only nested classes can be static; a top-level class cannot.

Problem statement: Join a list of names into one comma-separated string efficiently.

public static String joinNames(List<String> customerNames) {
    // StringBuilder avoids creating a new String object on every append
    StringBuilder resultBuilder = new StringBuilder();
    for (String customerName : customerNames) {
        if (resultBuilder.length() > 0) {
            resultBuilder.append(", ");   // separator only between items
        }
        resultBuilder.append(customerName);
    }
    return resultBuilder.toString();
}

Q26. Is there a Tuple in Java? What is the difference between a Map and a Tuple?

  • A Map is a collection of key→value entries with unique keys and a variable size; lookup is by key.
  • A Tuple is a small, fixed-size, ordered group of values of possibly different types (e.g., a pair). Java has no built-in Tuple; use a record (Java 16+), Map.Entry/AbstractMap.SimpleEntry, or a library such as Apache Commons Pair.

Problem statement: Return a product name and its price from one method without creating a full class.

// A record is an immutable, typed tuple with named components
public record ProductPricePair(String productName, double unitPrice) { }

public static ProductPricePair findCheapestProduct(Map<String, Double> priceByProduct) {
    // Entry.comparingByValue picks the minimum price entry
    Map.Entry<String, Double> cheapestEntry = Collections.min(
            priceByProduct.entrySet(), Map.Entry.comparingByValue());
    return new ProductPricePair(cheapestEntry.getKey(), cheapestEntry.getValue());
}

Q27. What happens if you make a parameterised constructor private? Will the compiler give an error?

No compile error. A private constructor simply cannot be called from outside the class. Consequences:

  • If it is the only constructor, no other class can instantiate it with new or subclass it (the subclass constructor could not call super).
  • Used for Singletons, utility classes (all-static), and static factory methods / builders that control instance creation.
  • A private constructor is still callable from inside the class, including its static methods and nested classes.

Problem statement: Allow creating a Temperature object only through a validating static factory method.

public final class Temperature {
    private final double celsiusValue;

    // Private constructor: callers must use the factory method below
    private Temperature(double celsiusValue) {
        this.celsiusValue = celsiusValue;
    }

    public static Temperature ofCelsius(double celsiusValue) {
        if (celsiusValue < -273.15) {              // validate before creating the object
            throw new IllegalArgumentException("Below absolute zero");
        }
        return new Temperature(celsiusValue);
    }
}

Q28. What are the advantages of OOP? Give a real-time example.

  • Encapsulation — hide data behind methods (a BankAccount exposes deposit()/withdraw(), not the balance field).
  • Abstraction — expose what an object does, not how (PaymentProcessor interface).
  • Inheritance / reuse — share common behaviour (SavingsAccount and CurrentAccount extend Account).
  • Polymorphism — one call, different behaviour at runtime (processor.pay() works for card, UPI, or wallet).
  • Maintainability & testability — small, replaceable, mockable units.

Q29. What is the difference between BigDecimal and BigInteger? Why not use double for money?

  • BigInteger — arbitrary-precision whole numbers (beyond long's range, e.g., factorials, cryptography).
  • BigDecimal — arbitrary-precision decimal numbers with a scale; exact for money. Always create from a String (new BigDecimal("0.10")), not a double, and specify a RoundingMode when dividing.
  • double is binary floating point and cannot represent 0.1 exactly (0.1 + 0.2 != 0.3).
  • Both are immutable and slower than primitives.

Section 2: Java Object Fundamentals & Lifecycle

Q1. What is an object, and what three steps does a statement like Human person = new Human() perform?

An object is an instance of a class — a bundle of state (fields) and behavior (methods). Car, Bird, and Human are classes; a specific car with a given license plate is an object. The single statement performs three steps: Declaration (the name refers to an object of type Human), Instantiation (the new operator allocates memory), and Initialization (the constructor runs to set the initial state).

Q2. Describe the seven states in a Java object's lifecycle.

  • 1. Created — memory is allocated; if immediately assigned to a variable, the object moves straight to In Use.
  • 2. In Use — held by at least one strong reference (the default kind, as opposed to Weak/Soft/Phantom).
  • 3. Invisible — no strong reference is accessible from the currently executing program logic, even though one may technically still exist (e.g. a field that will never be read again).
  • 4. Unreachable — no strong reference exists from any GC root (local variables on a thread stack, active static fields, JNI references).
  • 5. Collected — the GC recognizes it as unreachable; if the class overrides finalize(), it is marked for that call.
  • 6. Finalized — still unreachable after finalize() ran, now awaiting deallocation.
  • 7. Deallocated — memory is reclaimed and made available for future allocations.

Note: Do not rely on finalize() to release important resources: there is no guarantee when (or if) it runs, and a finalizer can extend an object's lifetime and increase GC work. Prefer try-with-resources and AutoCloseable.

Section 3: Exception Handling

Q1. What is the difference between checked and unchecked exceptions, and between throw and throws?

Checked exceptions (subclasses of Exception that do not extend RuntimeException, e.g. IOException, SQLException) are verified at compile time: a method that might throw one must handle it or declare it, and they typically represent recoverable conditions. Unchecked exceptions (RuntimeException subclasses and Errors, e.g. NullPointerException, IllegalArgumentException) are not compiler-enforced and usually represent programming errors.

throw is a statement that raises a Throwable instance at a specific point (throw new IllegalArgumentException("size must be a multiple of 2")). throws is part of a method signature, listing the checked exceptions the method may propagate so the caller knows what to handle.

Q2. Can there be multiple catch blocks? What is multi-catch?

Yes: multiple catch blocks are evaluated top-down, most specific first. Since Java 7, multi-catch — catch (IOException | SQLException exception) — handles unrelated types in one block (no superclass/subclass pairs; the variable is implicitly final), reducing duplicated handling logic.

Q3. What is try-with-resources, and what happens if exceptions occur in both try and finally?

Introduced in Java 7, try-with-resources automatically closes resources implementing AutoCloseable/Closeable after the block, even on exceptions, eliminating manual finally cleanup. Resources close in reverse declaration order, and exceptions thrown by close() are attached to the primary exception as suppressed exceptions (retrievable via getSuppressed()).

With a plain try/finally, an exception thrown from the finally block replaces the one from try, and the original is lost unless captured — which is why finally blocks should avoid throwing exceptions or returning values.

Problem statement: Read a file line by line and guarantee the reader is closed without writing a finally block.

import java.io.*;
 
public class FileReadingDemo {
    public static void readFileContents(String filePath) {
        try (BufferedReader fileReader = new BufferedReader(new FileReader(filePath))) {
            String currentLine;
            while ((currentLine = fileReader.readLine()) != null) {
                System.out.println(currentLine);
            }
        } catch (IOException fileException) {
            System.out.println("Error reading file: " + fileException.getMessage());
        } // fileReader is auto-closed here, no finally needed
    }
}

Q4. What is exception chaining, and how do you write a custom checked exception?

Exception chaining wraps a lower-level exception inside a higher-level one via the cause constructor (new ServiceException("msg", originalException)) or initCause(), preserving the original stack trace/root cause while letting each layer throw domain-appropriate exceptions.

Problem statement: Reject a bank withdrawal that exceeds the balance by throwing a custom checked exception.

class InsufficientFundsException extends Exception {
    public InsufficientFundsException(String errorMessage) {
        super(errorMessage);
    }
}
 
class BankAccount {
    private double accountBalance;
 
    public BankAccount(double initialBalance) {
        this.accountBalance = initialBalance;
    }
 
    public void withdrawAmount(double requestedAmount) throws InsufficientFundsException {
        if (requestedAmount > accountBalance) {
            // explicitly throw a custom exception carrying context
            throw new InsufficientFundsException(
                    "Requested $" + requestedAmount + " exceeds balance $" + accountBalance);
        }
        accountBalance -= requestedAmount;
    }
}
 
public class BankDemo {
    public static void main(String[] arguments) {
        BankAccount savingsAccount = new BankAccount(500.0);
        try {
            savingsAccount.withdrawAmount(700.0); // triggers the custom exception
        } catch (InsufficientFundsException exceptionDetails) {
            System.out.println("Transaction failed: " + exceptionDetails.getMessage());
        }
    }
}

Section 4: Generics

Type erasure (why List<String> and List<Integer> share the same runtime class, and the Class<T> token / TypeToken workarounds) is covered in Section 1, Q16.

Q1. What is the difference between ? extends T and ? super T (PECS)?

? extends T (upper-bounded wildcard) allows reading T or its subtypes — use it for producers (Producer Extends). ? super T (lower-bounded) allows writing T or its subtypes into the structure — use it for consumers (Consumer Super). Comparator<? super T> accepting comparators for T or its supertypes is a canonical example.

Problem statement: Copy elements from a source list of a subtype into a destination list of a supertype.

import java.util.*;
 
public class BoundedWildcardDemo {
    // PECS: the source produces (extends), the destination consumes (super)
    public static <ElementType> void copyElements(
            List<? extends ElementType> sourceList,
            List<? super ElementType> destinationList) {
        for (ElementType currentElement : sourceList) {
            destinationList.add(currentElement);
        }
    }
 
    public static void main(String[] arguments) {
        List<Integer> integerSource = Arrays.asList(1, 2, 3);
        List<Number> numberDestination = new ArrayList<>();
        copyElements(integerSource, numberDestination);
        System.out.println(numberDestination); // [1, 2, 3]
    }
}

Q2. Why can't you create generic arrays like new T[10]?

Because of type erasure the JVM doesn't know T's runtime type, and arrays are covariant with runtime type checks (ArrayStoreException), so a raw T[] could let incompatible elements in. The workaround is an unchecked cast, @SuppressWarnings("unchecked") T[] array = (T[]) new Object[10], or, better, using ArrayList<T>.

Q3. What are bounded type parameters?

They restrict acceptable types using extends, with multiple bounds allowed: <T extends Comparable<T> & Serializable>. This lets the generic code call methods defined by the bound; for example <T extends Number> permits calling doubleValue() on T, which a plain <T> would not.

Section 5: Java 7–21 Features & Modern Java

Q1. Name key features introduced in Java 7 and Java 8.

Java 7:

  • try-with-resources for automatic resource closing.
  • The Fork/Join framework for divide-and-conquer parallel algorithms that balance work across cores.
  • Strings in switch statements (compiled to a hashCode()-based comparison plus an equals() check).
  • The diamond operator <> for generic type inference.
  • Multi-catch: catch (IOException | SQLException e).

Java 8:

  • Lambda expressions and method references.
  • The Stream API, with optional parallel execution.
  • The java.time package: an immutable, thread-safe replacement for Date/Calendar.
  • Default and static methods on interfaces.
  • Repeatable annotations, and Optional.

Q2. What is a lambda expression, and what are functional interfaces?

A lambda is a concise anonymous-function implementation of a functional interface — an interface with exactly one abstract method — e.g. (a, b) -> a + b. @FunctionalInterface is optional but recommended for compile-time checking. Built-in examples: Runnable, Comparator<T>, Function<T,R>, Predicate<T>, Supplier<T>, Consumer<T>; they underpin the lambda and Stream APIs.

Q3. What is the Stream API, and how do intermediate and terminal operations differ?

A Stream is a sequence of elements supporting declarative, functional-style pipelines (map, filter, reduce) that can run sequentially or in parallel. Unlike collections, streams don't store data and are consumed once. Intermediate operations (filter, map, sorted) are lazy and return a new Stream; nothing executes until a terminal operation (collect, forEach, reduce, count) triggers processing and closes the stream.

Problem statement: Given [1,2,3,4,5,6], filter the even numbers, square them, and sum the result in one pipeline (expected 4 + 16 + 36 = 56).

import java.util.*;
 
public class SumOfSquaresDemo {
    public static void main(String[] arguments) {
        List<Integer> numberCollection = Arrays.asList(1, 2, 3, 4, 5, 6);
 
        int sumOfEvenSquares = numberCollection.stream()
                .filter(currentValue -> currentValue % 2 == 0)  // intermediate: keep evens
                .map(currentValue -> currentValue * currentValue) // intermediate: square each
                .reduce(0, Integer::sum);                         // terminal: accumulate the sum
 
        System.out.println("Sum of squares of even numbers: " + sumOfEvenSquares); // 56
    }
}

Q4. What is the difference between map() and flatMap()?

map() transforms each element into exactly one other element (one-to-one), potentially yielding nested structures like Stream<List<T>>. flatMap() transforms each element into a stream and flattens all of them into a single-level Stream<T> — useful when each element maps to multiple elements, e.g. flattening List<List<Integer>> into List<Integer>.

Q5. What is Optional, and why was it introduced?

Optional<T> is a container that may or may not hold a non-null value, introduced to make absence explicit in method signatures and reduce NullPointerException risk. Use orElse(), orElseGet(), map(), and ifPresent() rather than manual null checks, and avoid calling get() without checking presence.

Q6. What are method references, and what are their four types?

Method references are shorthand lambdas that name an existing method: (1) static method — ClassName::staticMethod; (2) instance method of a particular object — object::instanceMethod; (3) instance method of an arbitrary object of a type — ClassName::instanceMethod; (4) constructor reference — ClassName::new.

Q7. What is the difference between Collectors.toList()/toSet() and groupingBy()?

toList()/toSet() collect elements into a plain collection. groupingBy() partitions elements into a Map<K, List<V>> by a classifier function, optionally with downstream collectors (counting, summing, mapping) — the Java equivalent of SQL GROUP BY.

Problem statement: Group employee names by department.

import java.util.*;
import java.util.stream.*;
 
public class EmployeeGroupingDemo {
    public static void main(String[] arguments) {
        List<String[]> employeeRecords = Arrays.asList(
                new String[]{"Alice", "Engineering"},
                new String[]{"Bob", "Sales"},
                new String[]{"Charlie", "Engineering"});
 
        Map<String, List<String>> employeesByDepartment = employeeRecords.stream()
                .collect(Collectors.groupingBy(
                        employeeRecord -> employeeRecord[1],   // classifier: department
                        Collectors.mapping(employeeRecord -> employeeRecord[0], // extract name
                                Collectors.toList())));
 
        System.out.println(employeesByDepartment);
        // {Engineering=[Alice, Charlie], Sales=[Bob]}
    }
}

Q8. What are default and static interface methods, and what problem do they solve? What is the diamond problem?

Before Java 8, adding a method to an interface broke every implementer. Default methods carry a body so existing implementers keep compiling — essential for evolving APIs such as adding Collection.stream() without breaking millions of implementations. Static methods belong to the interface itself, are called via InterfaceName.method(), and can't be overridden.

The diamond problem arises when a class inherits conflicting default implementations from two interfaces. Java forces the class to override the method explicitly, and it can call a specific version with InterfaceName.super.methodName(), avoiding the ambiguity multiple inheritance of state would cause.

Problem statement: Show an interface with an abstract, a default, and a static method, used by an implementing class.

interface PaymentProcessor {
    // abstract method: must be implemented
    void processPayment(double transactionAmount);
 
    // default method: shared behavior inherited for free
    default void logTransaction(double transactionAmount) {
        System.out.println("Logging transaction: " + transactionAmount);
    }
 
    // static method: utility bound to the interface itself
    static boolean isValidAmount(double transactionAmount) {
        return transactionAmount > 0;
    }
}
 
class CreditCardProcessor implements PaymentProcessor {
    @Override
    public void processPayment(double transactionAmount) {
        if (PaymentProcessor.isValidAmount(transactionAmount)) {
            logTransaction(transactionAmount);
            System.out.println("Processed: " + transactionAmount);
        }
    }
}

Q9. What is var (Java 10) and what are Text Blocks (Java 15)?

var lets the compiler infer a local variable's type from its initializer at compile time (it is not dynamic typing; the type is fixed). It reduces verbosity for complex generics but requires an initializer and can't be used for fields, parameters, or return types.

Text blocks (triple-quote """ delimiters) allow multi-line string literals without \n concatenation or escaping, preserving formatting for embedded SQL, JSON, or HTML. The compiler strips incidental leading whitespace based on the closing delimiter's indentation.

Q10. What are Records (Java 14+), Sealed classes (Java 17), and pattern matching for switch (Java 21)? Why do tech leads push for them?

Records are concise, immutable data carriers that auto-generate the constructor, equals(), hashCode(), toString(), and accessors, eliminating boilerplate and the bugs of hand-written equals/hashCode. Sealed types restrict which classes may extend or implement them via permits, giving a closed, compile-time-known hierarchy. Pattern matching for switch matches on types and deconstructs records directly; combined with sealed types the compiler enforces exhaustiveness, so no default branch is needed.

Problem statement: Model payment events as a sealed hierarchy of records and handle each case exhaustively.

public record Money(BigDecimal amount, Currency currency) {
    public Money {  // compact constructor: validation runs on every construction
        if (amount.signum() < 0) throw new IllegalArgumentException("Amount cannot be negative");
    }
}
 
public sealed interface PaymentEvent permits PaymentInitiated, PaymentSettled, PaymentFailed { }
public record PaymentInitiated(String transactionId) implements PaymentEvent { }
public record PaymentSettled(String transactionId, Instant settledAt) implements PaymentEvent { }
public record PaymentFailed(String transactionId, String reason) implements PaymentEvent { }
 
String eventDescription = switch (paymentEvent) {
    case PaymentInitiated initiated -> "Initiated: " + initiated.transactionId();
    case PaymentSettled settled     -> "Settled at " + settled.settledAt();
    case PaymentFailed failed       -> "Failed: " + failed.reason();
    // no default needed: the compiler knows every permitted type is covered
};

If a new event type is added later, this switch fails to compile until updated, turning a class of runtime bugs into compile-time errors — especially valuable in event-driven financial systems.

Note: Tech-lead takeaway: push for adoption of these features in new modules even inside legacy Java 8/11 codebases undergoing modernization; the reduction in boilerplate and “forgot to handle the new enum value” bugs pays for itself quickly. Virtual threads (Java 21) are covered in Part 2, Section 2.

Q11. How do Java Streams work, and what are parallel streams?

  • A stream is a pipeline: source → zero or more lazy intermediate operations (filter, map, sorted) → one terminal operation (collect, forEach, reduce). Nothing runs until the terminal operation is called, and elements flow through the whole pipeline one at a time.
  • Streams do not store data and cannot be reused once consumed.
  • Parallel stream (parallelStream() or .parallel()) splits the source and processes chunks on the common ForkJoinPool. It helps for large, CPU-bound, stateless work on splittable sources (ArrayList, arrays); it hurts for small data, I/O or blocking calls, LinkedList sources, or operations with shared mutable state.

Problem statement: Sum the squares of all even numbers in a large list, first sequentially and then in parallel.

public static long sumEvenSquares(List<Integer> numberList, boolean useParallel) {
    Stream<Integer> numberStream =
            useParallel ? numberList.parallelStream() : numberList.stream();
    return numberStream
            .filter(currentNumber -> currentNumber % 2 == 0)   // intermediate (lazy)
            .mapToLong(currentNumber -> (long) currentNumber * currentNumber)
            .sum();                                           // terminal: triggers execution
}

Language basics

Q1. What is the difference between a == b and a.equals(b)? And between final, finally, and finalize?

== compares references for objects (and values for primitives); equals() expresses logical equality and depends on the class overriding it — the inherited Object default is identical to ==, while String overrides it to compare characters.

  • final — a modifier: a final variable can't be reassigned, a final method can't be overridden, a final class can't be subclassed (supporting immutability, security, and design intent).
  • finally — a block paired with try/catch that always executes, whether or not an exception was thrown (short of System.exit() or a JVM crash).
  • finalize() — a method called by the GC just before reclaiming an object; deprecated since Java 9 and never guaranteed to run, so don't use it for critical cleanup.

Q2. What is the difference between a = a + b and a += b for narrower primitive types?

+= implicitly casts the result back to the left-hand type. For byte/short, a + b promotes both operands to int, so assigning it back without a cast is a compile error, whereas a += b compiles because the compiler inserts the narrowing cast.

byte firstValue = 127;
byte secondValue = 127;
secondValue = firstValue + secondValue; // COMPILE ERROR: int cannot be assigned to byte
secondValue += firstValue;              // OK: compiler implicitly casts back to byte

Q3. Can you store a double in a long without casting? Does 3 * 0.1 == 0.3?

No, an explicit cast is required: double has a different representation and range, and the narrowing cast truncates the fraction. And 3 * 0.1 == 0.3 is false: many decimal fractions can't be represented exactly in IEEE 754 binary floating point, so the result is extremely close to, but not bit-identical to, 0.3. Never compare floating-point values for exact equality; check that the difference is within an epsilon, or use BigDecimal when exact decimal arithmetic matters (such as money).

double sourceValue = 123.456;
long targetValue = (long) sourceValue; // 123 -- fraction truncated, cast is required
 
boolean isExactlyEqual = (3 * 0.1 == 0.3); // false, due to floating-point representation

Q4. Which uses more memory: int or Integer? What is the size of an int on a 64-bit JVM?

Integer uses more: int is 4 bytes of raw data, whereas Integer is a full object with header overhead (class pointer, lock state), typically 16 bytes or more. An int is still 32 bits on a 64-bit JVM — primitive sizes are fixed by the language specification, not the platform's word size, in keeping with “write once, run anywhere.”

Q5. Why is String immutable, and can you use a String in a switch?

Immutability enables safe sharing of the same underlying object (as with the String pool) with no risk that one piece of code corrupts a String another relies on. It also makes String safe as a HashMap key (its hash code can't change after insertion) and inherently thread-safe. Strings can be used in switch since Java 7 as syntactic sugar over hashCode() and equals(). StringBuilder is mutable and not thread-safe (best for single-threaded manipulation); StringBuffer is mutable and synchronized (thread-safe, but with synchronization overhead).

Q6. What is a compile-time constant, and what is its risk?

A public static final field whose value is known at compile time (e.g. public static final int MAX_RETRIES = 5;) is inlined by the compiler directly into calling code. The risk: if the constant lives in a separate library that later changes its value, code compiled against the old version keeps using the old inlined value even after the new JAR is deployed, until that calling code is recompiled.

Q7. What is constructor chaining?

One constructor calls another of the same class via this(...) or of its superclass via super(...), so shared initialization lives in one place instead of being duplicated across overloads.

public class Rectangle {
    private final int width;
    private final int height;
 
    public Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }
 
    public Rectangle(int side) {
        this(side, side); // chains to the two-argument constructor above
    }
}

Object-oriented design

Q8. What are the four pillars of OOP? What is the difference between an abstract class and an interface, and between inheritance and composition?

The four pillars: Encapsulation (bundling data with methods and restricting access), Abstraction (hiding implementation behind interfaces), Inheritance (reusing/extending a parent's behavior), and Polymorphism (one interface, many implementations).

Abstract class vs. interface: a class extends only one class but implements any number of interfaces. An abstract class can hold state, constructors, and both abstract and concrete methods, and suits shared code for a closely related family; an interface (with default/static methods since Java 8, but no instance state) defines a contract/type that unrelated classes can implement. An interface's purpose is abstraction: client code written against List works with ArrayList or LinkedList unchanged.

Inheritance (“is-a”) is fixed at compile time and couples tightly to the parent's implementation; composition (“has-a”, holding a reference and delegating) can swap implementations at runtime, avoids fragile-base-class problems, and is easier to unit test — hence “favor composition over inheritance.”

Problem statement: Process different payment types polymorphically through a common base class.

abstract class PaymentProcessor {
    // each payment type supplies its own logic
    abstract void processPayment(double transactionAmount);
}
 
class CreditCardProcessor extends PaymentProcessor {
    @Override
    void processPayment(double transactionAmount) {
        System.out.println("Processing credit card payment: $" + transactionAmount);
    }
}
 
class PayPalProcessor extends PaymentProcessor {
    @Override
    void processPayment(double transactionAmount) {
        System.out.println("Processing PayPal payment: $" + transactionAmount);
    }
}
 
public class PaymentDemo {
    public static void main(String[] arguments) {
        List<PaymentProcessor> paymentProcessors = new ArrayList<>();
        paymentProcessors.add(new CreditCardProcessor());
        paymentProcessors.add(new PayPalProcessor());
 
        for (PaymentProcessor currentProcessor : paymentProcessors) {
            currentProcessor.processPayment(250.00); // correct override chosen at runtime
        }
    }
}

Q9. What is the difference between method overloading and overriding? Any overloading best practices?

Overloading (same name, different parameters, same class) is resolved at compile time from the signature at the call site — compile-time polymorphism. Overriding (a subclass redefining a superclass method with the same signature) is resolved at runtime from the object's actual type — runtime polymorphism, and it requires inheritance.

  • Avoid overloads that accept a primitive (int) in one variant and its wrapper (Integer) in another; auto-boxing makes it ambiguous which is called.
  • Avoid overloads that differ only in the order of same-typed parameters.
  • Beyond roughly 4–5 parameters, prefer varargs, a builder, or a parameter object over more overloads.

Q10. Explain the Liskov Substitution Principle, the Open/Closed Principle, and the Law of Demeter.

  • Liskov Substitution — subclass objects must be substitutable for superclass objects without breaking correctness: don't strengthen preconditions, weaken postconditions, or throw unexpected exceptions. Classic violation: a Square extending Rectangle and forcing width == height, breaking code that sets them independently.
  • Open/Closed — open for extension, closed for modification. The Strategy pattern is a textbook case (add a new strategy by writing a new implementation), and Collections.sort() is an everyday instance: a new sort order means a new Comparator, never a change to sort().
  • Law of Demeter (“only talk to your immediate friends”) — a method should call only methods on itself, its fields, its parameters, or objects it creates, not on objects those return; chains like a.getB().getC().doSomething() couple you to internal structure you don't own.

Q11. How do the Adapter, Decorator, and Proxy patterns differ?

All three wrap another object, but intent differs: Adapter converts one interface into another that a client expects; Decorator adds new behavior dynamically while keeping the same interface; Proxy adds a controlled layer of indirection (lazy initialization, access control, remote invocation, logging) while presenting the same interface as the wrapped object.

Q12. What are the Template Method, Visitor, Composite, Flyweight, Abstract Factory, and Prototype patterns used for?

  • Template Method — fixes the skeleton of an algorithm in a base class while subclasses override specific steps; e.g. Collections.sort() defines the algorithm and delegates comparison to your Comparable/Comparator.
  • Visitor — adds new operations to a stable class hierarchy without modifying it, using double dispatch (the overload invoked depends on both the element's and the visitor's runtime types).
  • Composite — arranges objects into tree part-whole hierarchies so clients treat a leaf and a group uniformly (filesystem of files/folders; the organizational chart in Part 4, Section 7).
  • Flyweight — shares immutable objects to support many logical objects with few real ones; the String pool and the boxed Integer/Long cache (-128 to 127) are JDK examples.
  • Abstract Factory vs. Prototype — Abstract Factory creates families of related objects through factory methods that each return a new instance; Prototype creates objects by cloning a pre-configured instance, useful when construction is expensive.

Q13. What is the difference between Association, Aggregation, and Composition? Nested static class vs. top-level class?

  • Association — any relationship connecting two objects.
  • Aggregation (“has-a”, weak ownership) — the used object has an independent lifecycle: a University has Students, but a Student can exist without any particular University.
  • Composition (“owns-a”, strong ownership) — lifecycles are bound: a Car is composed of an Engine that has no meaningful existence apart from that Car.

A source file may contain only one top-level public class (matching the file name), but a top-level class can contain any number of nested static classes; Map.Entry (a nested static interface inside Map) is the JDK example.

Exceptions, XML, build tools & collections trivia

Q14. What is the difference between a DOM parser and a SAX parser? Maven vs. Ant?

DOM reads the entire XML document into an in-memory tree that can be freely navigated and modified: faster for repeated navigation of small-to-medium documents, but memory-hungry. SAX is event-based: it streams through once, firing callbacks (element start/end, text), holding only a small constant amount of memory regardless of document size — better for very large files, at the cost of a callback-driven style.

Ant is a general-purpose, imperative build tool: you script every step in XML, with no conventions or dependency management. Maven is convention-over-configuration: it imposes a standard project layout and resolves and downloads dependency JARs (and their transitive dependencies) from a central repository based on a declarative pom.xml.

Q15. What is the difference between poll() and remove() on a Queue? LinkedHashMap vs. PriorityQueue?

Both remove and return the head, but on an empty queue poll() returns null while remove() throws NoSuchElementException; the same pattern holds for peek() (null) vs. element() (throws). LinkedHashMap is a Map that iterates in insertion order (or access order if configured, handy for an LRU cache); PriorityQueue is a Queue that always keeps the lowest-priority-value (or highest, with a Comparator) element at its head — iterating it directly guarantees no order, only repeated poll() does.

Q16. Hashtable vs. HashMap? How does HashSet work? Default capacities? Is LinkedList singly or doubly linked?

  • Hashtable is a legacy JDK 1.0 class that synchronizes every operation and forbids null keys and values; HashMap (Java 1.2) is unsynchronized, allows one null key and any number of null values — use ConcurrentHashMap when you need both speed and thread safety.
  • HashSet is backed by a HashMap: each element is stored as a key paired with a shared dummy placeholder value, hence no duplicates and at most one null.
  • Default initial capacities: ArrayList 10, HashMap 16 (always a power of two, to support bit-masking of the hash).
  • LinkedList is doubly linked (each node references next and previous); TreeMap uses a red-black tree for guaranteed O(log n) operations.
// from ArrayList's source
private static final int DEFAULT_CAPACITY = 10;
// from HashMap's source
static final int DEFAULT_INITIAL_CAPACITY = 1 << 4; // 16

Q17. Can two unequal objects share a hashCode()? Can two equal objects have different ones? Can hashCode() use random values?

  • Unequal objects with the same hashCode: yes — that's a hash collision, normal in any hash-based collection, and why equals() is still needed once keys land in the same bucket.
  • Equal objects with different hashCode: no — it violates the contract; an object could be inserted into a HashMap and then become unfindable because it computes a different bucket.
  • Random values inside hashCode(): no — it must be stable for as long as the object is unchanged; a fresh random value per call breaks the contract immediately.

Q18. What best practices apply to Collections, I/O, JDBC, and threads?

I/O:

  • Prefer buffered classes (BufferedReader, BufferedOutputStream) over byte-at-a-time I/O.
  • Prefer java.nio / NIO.2 for high-performance or non-blocking I/O; consider memory-mapped files (FileChannel.map()) for very large files.
  • Use try-with-resources rather than closing in finally; keep I/O off latency-critical hot paths (batch, buffer, or move it off the path).

JDBC:

  • Use batch statements (addBatch()/executeBatch()) for many rows instead of one round trip per row.
  • Always use PreparedStatement with bind parameters: it prevents SQL injection and lets the database cache the execution plan.
  • Use a connection pool; read ResultSet columns by name rather than index; never concatenate raw user input into SQL.

Threads (in addition to Part 2, Sections 1–3):

  • Always name your threads explicitly; it makes thread dumps dramatically easier to read.
  • Keep the task (Runnable/Callable) separate from the mechanism running it, and use a thread pool instead of ad-hoc thread creation.
  • Prefer volatile over synchronized when you only need visibility for a simple flag, and higher-level utilities (BlockingQueue, CountDownLatch, Semaphore, CompletableFuture) over hand-rolled wait()/notify().
  • Prefer concurrent collections over externally synchronized ones; use the non-synchronized ArrayList rather than legacy Vector unless synchronization is needed.

Section 7: Java Serialization

Q1. How do you exclude fields from serialization, and which kinds of fields are typically transient?

Declare them transient. The default serialization mechanism skips them, and on deserialization they revert to their type's default (null / 0 / false). Typical transient fields are those that cannot be meaningfully serialized or should not be persisted for security reasons:

  • Logger references, file handles, and I/O streams (live runtime/OS resources).
  • Auditing or exception-handling helper instances (runtime-context specific).
  • Security-sensitive data such as passwords and raw cryptographic keys, to keep them out of a byte stream that might be logged, cached, or transmitted insecurely.
public class UserSession implements Serializable {
    private String username;                  // serialized normally
    private transient Connection dbConnection; // NOT serialized: live resource
}

Q2. Are static variables serialized?

No. Static variables belong to the class, not to any instance, and serialization only captures instance state. To preserve a static value you must do so explicitly by writing/reading it yourself inside custom writeObject()/readObject() methods.

Q3. How do you implement custom serialization, and how does Serializable differ from Externalizable?

Serializable is a marker interface that opts a class into Java's built-in, reflection-based default serialization — convenient, but relatively expensive, fragile, and offering limited control over the byte format. There are two ways to customize:

  • Implement Externalizable: you must write writeExternal(ObjectOutput) and readExternal(ObjectInput) yourself, giving complete control, generally better performance, and room for extra validation — nothing happens automatically.
  • Keep Serializable but add private writeObject(ObjectOutputStream) and readObject(ObjectInputStream) methods; the default mechanism calls them if present, while you can still delegate to defaultWriteObject()/defaultReadObject() for the fields you don't customize.

Problem statement: Serialize a record normally but rebuild a derived (transient) summary field on deserialization.

public class AuditableRecord implements Serializable {
    private String recordId;
    private transient String computedSummary; // recomputed on read, not stored
 
    private void writeObject(java.io.ObjectOutputStream outputStream) throws IOException {
        outputStream.defaultWriteObject(); // serializes all non-transient fields normally
    }
 
    private void readObject(java.io.ObjectInputStream inputStream)
            throws IOException, ClassNotFoundException {
        inputStream.defaultReadObject();            // restores non-transient fields
        this.computedSummary = recomputeSummary();  // rebuild the transient field
    }
 
    private String recomputeSummary() {
        return "Summary for " + recordId;
    }
}

Section 8: Date, Time & Calendar

Q1. Is SimpleDateFormat safe to use in a multithreaded program?

No. DateFormat and all its subclasses, including SimpleDateFormat, are NOT thread-safe. Sharing one instance across threads without external synchronization can produce silently wrong parse/format results (genuinely incorrect dates, not just exceptions), because its internal Calendar field is mutated during both parse() and format().

If you must use it in a multithreaded context, confine each instance to one thread, for example with a ThreadLocal (remember to call remove() in pooled-thread environments; see Part 2, Section 1).

private static final ThreadLocal<SimpleDateFormat> DATE_FORMATTER =
        ThreadLocal.withInitial(() -> new SimpleDateFormat("dd-MM-yyyy"));
 
String formattedDate = DATE_FORMATTER.get().format(new Date());

Note: The modern, strongly preferred fix is java.time (Java 8+): LocalDate, LocalDateTime, and DateTimeFormatter are immutable and inherently thread-safe, so a DateTimeFormatter can be shared freely across threads.

Q2. How do you format a date in Java (e.g. in ddMMyyyy format)?

Problem statement: Print today's date as ddMMyyyy using the modern API, and using the legacy API for older code.

// Modern (preferred): java.time
import java.time.LocalDate;
import java.time.format.DateTimeFormatter;
 
LocalDate today = LocalDate.now();
DateTimeFormatter formatter = DateTimeFormatter.ofPattern("ddMMyyyy");
String formattedDate = today.format(formatter); // e.g. "28092026"
 
// Legacy (only when maintaining older code): SimpleDateFormat
import java.text.SimpleDateFormat;
import java.util.Date;
 
SimpleDateFormat legacyFormatter = new SimpleDateFormat("ddMMyyyy");
String legacyFormattedDate = legacyFormatter.format(new Date());

Section 9: Design Patterns

Quick Reference

Observer Pattern

Defines a one-to-many dependency between objects: when one object (the Subject) changes state, all its dependents (Observers) are notified and updated automatically. Advantages: loose coupling between subject and observer; supports broadcast-style communication to many listeners at once. Disadvantages: debugging can be difficult because control flow is indirect; can introduce memory leaks if observers are not properly unregistered.

Factory Pattern

A creational pattern that centralizes object construction behind static factory methods rather than direct constructor calls. Benefits include the ability to cache and reuse immutable objects, and the ability to introduce new subclasses or implementations without changing calling code.

Singleton Pattern — trade-offs

  • Advantages: hides construction dependencies from client code; provides one well-known access point that's easy to maintain; supports both lazy and eager initialization; can be extended into a factory-style pattern.
  • Disadvantages: makes unit testing harder by introducing global shared state; reduces potential for parallelism, since concurrent access to the shared instance typically requires locking.

Design Pattern Interview Questions

Figure: Shallow copy vs deep copy

Q1. What are design patterns, and have you used one in your own code?

Design patterns are proven, reusable solutions to commonly occurring design problems, distilled from the collective experience of many software engineers over time. They are not finished code you copy-paste — they are templates describing how to structure a solution to a class of problem. Using them is a form of design reuse: instead of solving a well-known problem from scratch, you apply a battle-tested approach and gain a shared vocabulary with other engineers (saying “we used a Factory here” instantly communicates intent).

Q2. Can you name a few design patterns used in the standard JDK library?

  • Decorator — used throughout java.io, e.g. BufferedReader wraps a Reader to add buffering.
  • Singleton — used by java.lang.Runtime and java.util.Calendar's getInstance() methods.
  • Factory Method — used by wrapper classes such as Boolean.valueOf(...), Integer.valueOf(...).
  • Observer — used in java.util.Observer/Observable, and extensively in Swing's event-listener model.
  • Iterator — the entire java.util.Iterator/Iterable contract underlying the enhanced for-loop.
  • Proxy — used by java.lang.reflect.Proxy for dynamic proxies.

Q3. What is the Factory pattern, and how does it differ from Abstract Factory?

The Factory pattern provides a single method that creates objects of one product family, hiding the concrete class-selection logic from the caller. This gives increased encapsulation: when client code asks a factory for a product rather than calling new directly, you can later swap the concrete implementation without touching client code — useful when the exact type to create depends on runtime configuration, when construction is complex enough to warrant centralizing, or when you want to control/limit/cache instances (object pooling).

Abstract Factory adds one further level of abstraction: it defines an interface for creating families of related objects, and you can have multiple concrete factory implementations, each responsible for producing a whole related set of products. For example, an AbstractFactory interface might be extended by AutomobileFactory, UserFactory, and RoleFactory, each creating objects within its own family — whereas a plain Factory would just have one createProduct() method returning one kind of object.

Q4. What is the Singleton pattern? Compare three ways to write it thread-safely.

Singleton restricts a class to a single instance shared across the whole application, typically used for expensive-to-create, globally-needed objects like configuration managers or connection pools. java.lang.Runtime is the textbook example.

Approach 1 — enum singleton (simplest, recommended since Java 5):

Enum instances are inherently singleton and thread-safe by the JVM's class-loading guarantees, so no explicit synchronization is needed.

public enum ConfigurationManager {
    INSTANCE;
 
    private final Properties settings = new Properties();
 
    public String getSetting(String key) {
        return settings.getProperty(key);
    }
}
// Usage: ConfigurationManager.INSTANCE.getSetting("timeout");

Approach 2 — double-checked locking:

Synchronize only the critical section (the code that actually creates the instance), not the entire getInstance() method. Synchronizing the whole method forces every caller to acquire the lock even long after the instance already exists, needlessly serializing access and hurting performance under high concurrency.

Problem statement: Implement a thread-safe Singleton database connection manager using double-checked locking, ensuring the instance is only constructed once even under concurrent first access.

public class DatabaseConnectionManager {
    // volatile prevents instruction reordering that could expose a
    // partially-constructed instance to another thread
    private static volatile DatabaseConnectionManager singletonInstance;
 
    private DatabaseConnectionManager() {
        // expensive initialization, e.g. opening a connection pool
    }
 
    public static DatabaseConnectionManager getInstance() {
        if (singletonInstance == null) {               // first check (no locking, fast path)
            synchronized (DatabaseConnectionManager.class) { // critical section only
                if (singletonInstance == null) {        // second check (inside the lock)
                    singletonInstance = new DatabaseConnectionManager();
                }
            }
        }
        return singletonInstance;
    }
}

The volatile keyword is essential here: without it, another thread could see a reference to a DatabaseConnectionManager object whose constructor hasn't finished running yet, due to instruction reordering by the JIT compiler or CPU.

Approach 3 — Bill Pugh static holder idiom:

Relies on the JVM's own class-loading guarantees: the nested SingletonHolder class is not loaded until getInstance() is first called, so initialization is both lazy and inherently thread-safe, with no synchronization overhead at all on the read path.

public class ConfigurationManagerHolder {
    private ConfigurationManagerHolder() { } // private constructor
 
    private static class SingletonHolder {
        private static final ConfigurationManagerHolder INSTANCE = new ConfigurationManagerHolder();
    }
 
    public static ConfigurationManagerHolder getInstance() {
        return SingletonHolder.INSTANCE; // loaded lazily, thread-safe
    }
}

Q5. What is the Observer design pattern in Java?

Observer establishes a one-to-many relationship where a Subject notifies all registered Observer objects whenever its state changes, so each observer can react accordingly. A common real-world example is a weather station: the WeatherData object is the Subject, and multiple display panels (current conditions, forecast, statistics) are Observers that update automatically whenever new data arrives. Java's built-in java.util.Observer/Observable are deprecated; modern code typically defines a custom Listener interface with a List<Listener> and a notifyAll()-style method invoked on state change, or uses PropertyChangeListener.

Q6. Give an example of the Decorator design pattern. Does it operate at the object level or class level?

Decorator operates at the object level — it wraps an existing object instance at runtime to add new behavior or responsibilities, without altering the original class's source code or affecting other instances of the same class. Java's I/O library is the classic example: BufferedReader wraps any Reader to add buffered reading, and BufferedWriter wraps any Writer to add buffered writing, both improving performance transparently.

// The underlying reader has no buffering
FileReader rawFileReader = new FileReader("data.txt");
// Decorator wraps it, adding buffering capability without changing FileReader itself
BufferedReader bufferedFileReader = new BufferedReader(rawFileReader);
 
String currentLine;
while ((currentLine = bufferedFileReader.readLine()) != null) {
    System.out.println(currentLine);
}

Q7. What is the MVC design pattern? Give one example.

Model-View-Controller separates an application into three interconnected components, each with a distinct responsibility: the Model holds the application's data and business logic, independent of how it's displayed; the View renders the Model's data to the user (a UI screen, an HTML page, a report); the Controller receives user input, invokes the appropriate operations on the Model, and selects the View to render the result.

This separation means the same Model can be displayed through multiple different Views without duplicating business logic, and the UI can be redesigned without touching the underlying data logic. Spring MVC is the classic Java example: a @Controller class handles an incoming HTTP request, calls a service/Model layer to fetch or update data, and forwards the result to a JSP or Thymeleaf View template for rendering.

Q8. What is the Front Controller design pattern? Give an example.

Front Controller centralizes all incoming requests to an application through a single handler, rather than letting each request go directly to its own separate handler/page. The front controller handles common cross-cutting logic — authentication, logging, routing to the correct downstream handler — before delegating actual business processing to a specific handler, avoiding duplicated security/logging code across dozens of individual servlets. The classic Java EE example is Spring MVC's DispatcherServlet, or the older single front-controller Servlet pattern in JSP/Servlet applications.

Q9. What is the Chain of Responsibility design pattern?

Chain of Responsibility passes a request along a chain of potential handler objects, where each handler decides either to process the request or pass it to the next handler in the chain. The sender doesn't need to know which handler will ultimately process it, decoupling senders from receivers. A real-world Java example is the Servlet Filter chain: an incoming HTTP request passes through a series of Filter objects (authentication, logging, compression), each of which can process the request and either forward it via chain.doFilter() or short-circuit the chain entirely. Logging frameworks like java.util.logging use a chain of Handler/Logger objects in the same spirit.

Q10. What is the Adapter design pattern? Give examples in Java.

Adapter converts the interface of one class into another interface a client expects, letting classes with incompatible interfaces work together without modifying their source. It acts as a bridge/wrapper between an existing class and the interface the caller actually needs.

  • java.util.Arrays.asList(...) adapts an array to the List interface.
  • java.io.InputStreamReader adapts a byte-oriented InputStream to a character-oriented Reader.
  • java.io.OutputStreamWriter adapts a byte-oriented OutputStream to a character-oriented Writer.
// InputStreamReader is a textbook Adapter: it adapts the byte-based InputStream
// interface to the character-based Reader interface that BufferedReader needs.
InputStream rawByteStream = new FileInputStream("data.txt");
Reader adaptedCharacterReader = new InputStreamReader(rawByteStream, StandardCharsets.UTF_8);
BufferedReader lineReader = new BufferedReader(adaptedCharacterReader);

Figure: Adapter pattern

Q11. What is the Builder pattern, and when should it be used?

Builder constructs complex objects step by step via chained method calls, avoiding telescoping constructors with many parameters. It's useful when an object has many optional fields: it improves readability (e.g. Person.builder().name("Alice").age(30).build()) and allows the resulting object to be immutable, since it's only constructed once all properties are set.

Q12. What is Dependency Injection, and how does Spring implement Inversion of Control?

Dependency Injection (DI) supplies an object's dependencies externally — via constructor, setter, or field — rather than having the object create them itself, promoting loose coupling and easier testing (dependencies can be mocked). Inversion of Control (IoC) is the broader principle DI implements: control over object creation and wiring is inverted from application code to a container/framework. Spring implements IoC via the ApplicationContext, which reads bean definitions (via annotations like @Autowired/@Inject or Java/XML configuration) and manages object lifecycles, injecting dependencies automatically and reducing tight coupling and boilerplate `new` calls throughout the codebase.
