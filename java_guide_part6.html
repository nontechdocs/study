Section 1: Messaging Systems — JMS, IBM MQ, RabbitMQ

Q1. What is JMS, and when would you use it?

JMS (Java Message Service, part of Java/Jakarta EE) is a standard, vendor-neutral Java API for creating, sending, receiving, and reading messages asynchronously, decoupling sender and receiver in time and space. The sender places a message on a queue or topic and the broker (IBM MQ, ActiveMQ, or another JMS provider) reliably delivers it whenever the receiver is ready.

  • Point-to-Point (queues) — each message goes to exactly one consumer, even with several listening; it is removed once consumed. Suits work distribution across a pool of workers.
  • Publish/Subscribe (topics) — each message goes to every current subscriber (one-to-many broadcast). Suits event notification where several independent parts of a system react to the same event.

Common uses: decoupling microservices (Service A publishes OrderPlaced without knowing who reacts), absorbing traffic spikes by buffering work, and distributing long-running background jobs.

// Simplified JMS producer
ConnectionFactory connectionFactory = /* provided by the JMS provider, e.g. IBM MQ */;
try (JMSContext jmsContext = connectionFactory.createContext()) {
    Queue orderQueue = jmsContext.createQueue("ORDER_PROCESSING_QUEUE");
    jmsContext.createProducer().send(orderQueue, "New order: #12345");
}
 
// Simplified JMS consumer
try (JMSContext jmsContext = connectionFactory.createContext()) {
    Queue orderQueue = jmsContext.createQueue("ORDER_PROCESSING_QUEUE");
    String receivedMessage = jmsContext.createConsumer(orderQueue).receiveBody(String.class);
    System.out.println("Received: " + receivedMessage);
}

Q2. Have you used IBM MQ? What is it used for?

IBM MQ (formerly WebSphere MQ) is a mature, enterprise-grade message-oriented middleware: a commercial implementation of exactly the broker infrastructure the JMS API targets. It is common in large, established, especially financial, environments for its long track record and strong reliability guarantees (messages persisted to disk survive a broker restart) and mature support for guaranteed delivery across complex, cross-platform landscapes. Java apps typically use it through the standard JMS API with IBM's provider driver, so the code looks like the generic JMS code above, and the same application could be pointed at another JMS-compliant broker with minimal change.

Q3. How do you handle transactions and reliability in RabbitMQ?

RabbitMQ is an open-source broker implementing AMQP (distinct from, though similar in spirit to, JMS). It offers two producer-side mechanisms:

  • AMQP transactions (tx.select / tx.commit / tx.rollback) — group several publishes and commit or roll them back together like a database transaction, but with a significant throughput cost because each commit requires a synchronous broker round trip.
  • Publisher confirms — the lightweight, higher-throughput, generally recommended approach: the broker asynchronously acknowledges each published message once received (and, depending on configuration, persisted), and the producer tracks unconfirmed messages and retries as needed.

On the consumer side, RabbitMQ uses message acknowledgments: a consumer acks only after successfully finishing processing. If it disconnects or crashes before acking, RabbitMQ requeues the message for redelivery, which is what prevents silent message loss.

// Publisher confirms (RabbitMQ Java client)
channel.confirmSelect(); // enable publisher confirms on this channel
channel.basicPublish("", "orderQueue", null, messageBytes);
boolean isConfirmed = channel.waitForConfirms(5000); // broker's acknowledgment
if (!isConfirmed) {
    // handle the failure: retry, log, alert
}
 
// Consumer-side manual acknowledgment
channel.basicConsume("orderQueue", false, (consumerTag, delivery) -> {
    try {
        processMessage(delivery.getBody());
        channel.basicAck(delivery.getEnvelope().getDeliveryTag(), false);        // ack ONLY after success
    } catch (Exception processingException) {
        channel.basicNack(delivery.getEnvelope().getDeliveryTag(), false, true);  // requeue on failure
    }
}, consumerTag -> { });

Section 2: Apache Kafka & Event-Driven Architecture

Q1. What is Apache Kafka, and what problem does it solve?

Kafka is a distributed event-streaming platform for high-throughput, fault-tolerant, real-time data feeds. It replaces tightly coupled point-to-point integrations with a central, durable log: producers publish records to topics and consumers read them independently. Unlike a traditional queue, messages persist on disk for a configurable retention period and aren't removed when consumed, so many consumers can read the same data at different times without affecting each other. Common uses: log aggregation, event sourcing, real-time analytics pipelines, and decoupling microservices.

Q2. Explain partitions, consumer groups, and offsets.

  • Partitions — the unit of parallelism and scalability. A topic is split into partitions, each an ordered, immutable, append-only sequence spread across brokers. Ordering is guaranteed only within a partition, not across a topic. A producer key is hashed so the same key always lands in the same partition.
  • Consumer group — consumers sharing a topic's work; each partition is assigned to exactly one consumer in a group at a time, and multiple groups each receive a full copy of all messages (publish-subscribe across groups). Joining or leaving triggers a rebalance. Scaling consumers beyond the partition count adds no throughput (extras sit idle). If a consumer crashes, its partitions are reassigned.
  • Offset — a sequential, ever-increasing integer identifying a message's position within a partition. It is the consumer, not the broker, that tracks how far it has read, which lets a consumer resume where it left off, lets independent groups progress separately, and enables replay by seeking back to an earlier offset, something a consume-and-remove queue cannot do.
KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consumerProperties);
consumer.subscribe(List.of("order-events"));
while (true) {
    ConsumerRecords<String, String> polledRecords = consumer.poll(Duration.ofMillis(100));
    for (ConsumerRecord<String, String> currentRecord : polledRecords) {
        System.out.println("Offset " + currentRecord.offset() + ": " + currentRecord.value());
        processRecord(currentRecord);
    }
    consumer.commitSync(); // persist how far this consumer has read
}

Q3. How do you guarantee message ordering in Kafka while still scaling horizontally?

Key messages by the entity whose order matters (accountId, customerId) so Kafka's default partitioner routes every event for that entity to the same partition, preserving its order while different entities are processed in parallel across partitions and consumers. Set the partition count high enough up front: increasing it later changes the key-to-partition mapping and can break ordering for existing keys. On the consumer side, process each partition's records sequentially; introducing async processing within a partition without ordering safeguards defeats the guarantee.

For an extremely hot key (one customer generating disproportionate volume), consider sub-keying (customer ID plus a bounded sub-partition indicator, accepting slightly relaxed ordering across sub-partitions), and monitor consumer lag per partition to catch skew before it hurts SLAs.

@Service
public class AccountEventProducer {
    private final KafkaTemplate<String, AccountEvent> kafkaTemplate;
 
    public void publish(AccountEvent accountEvent) {
        // key = accountId: all events for this account go to the same partition, preserving order
        kafkaTemplate.send("account-events", accountEvent.getAccountId(), accountEvent);
    }
}

Note: A common production incident: “why were customer X's events processed out of order?” Trace it to a bad partition key (a random UUID instead of the entity ID) or an unnecessary re-key/repartition step in a stream job. Review partition-key decisions explicitly in design review; they're cheap to get right upfront and expensive to fix after data is produced.

Q4. How do you commit offsets safely, and what is a dead-letter topic?

Prefer enable.auto.commit=false with explicit offset commits after successful processing. Committing only after a whole batch succeeds means a mid-batch failure causes reprocessing (so consumers must be idempotent); committing too eagerly risks message loss. A dead-letter topic receives records that repeatedly fail (poison pills) so one bad message doesn't block a partition indefinitely.

@KafkaListener(topics = "account-events", groupId = "ledger-service")
public void consume(ConsumerRecord<String, AccountEvent> incomingRecord, Acknowledgment acknowledgment) {
    try {
        ledgerService.applyEvent(incomingRecord.value());
        acknowledgment.acknowledge();               // commit only after successful processing
    } catch (NonRetryableException nonRetryableFailure) {
        deadLetterProducer.send("account-events-dlq", incomingRecord.value());
        acknowledgment.acknowledge();               // don't block the partition on a poison message
    }
}

Q5. How does Kafka ensure durability and fault tolerance?

Through replication and configurable acknowledgments. Each partition is replicated across brokers: a leader handles all reads and writes while followers replicate as in-sync replicas (ISRs). If the leader fails, an in-sync follower is elected leader. The producer's acks setting trades latency for durability: acks=0 (no acknowledgment), acks=1 (leader only), acks=all (all in-sync replicas, strongest and slowest). Messages are also persisted to disk under configurable retention, so data survives broker restarts.

Q6. Compare at-most-once, at-least-once, and exactly-once semantics. How does Kafka achieve exactly-once?

  • At-most-once — messages may be lost but are never redelivered; happens when the offset is committed before processing, so a failure mid-processing skips the message.
  • At-least-once — no loss but possible duplicates; the common default, from committing the offset after processing (a crash between processing and commit causes reprocessing).
  • Exactly-once — each message processed one time even under failure, built from idempotent producers plus transactional APIs.

The idempotent producer gets a Producer ID (PID) and attaches a monotonically increasing sequence number per partition; the broker tracks the last sequence per PID/partition and drops duplicates from producer retries. Transactions extend this: a producer atomically writes to multiple partitions/topics and atomically commits both its output records and the consumer offsets (marking input as processed), using a transactional.id and a Transaction Coordinator that runs a two-phase-commit-like protocol, writing markers to the __transaction_state topic. Consumers with isolation.level=read_committed see only committed transactions.

The cost is extra broker round trips for coordination and marker writes, plus consumer buffering until a commit marker arrives, so latency rises and throughput falls versus at-least-once. Reserve exactly-once for cases where duplicates cause real business harm (financial ledgers); logging can tolerate at-least-once with deduplication.

Q7. Explain log compaction versus time-based retention.

Time/size-based retention deletes whole log segments once they exceed an age or size threshold, regardless of content — right for event streams (logs, clickstream, metrics) where history matters. Log compaction instead keeps only the latest value per message key, discarding older records with the same key; a background thread builds a map of the latest offset per key and rewrites segments. A record with a null value (a tombstone) signals deletion of a key and is retained for a configurable grace period so all consumers see the deletion before it is purged. Compaction suits changelog or state topics (Kafka Streams state stores, database CDC, configuration data), where consumers rebuild current state by replaying the compacted topic without reading the whole unbounded history.

Q8. A consumer group is rebalancing frequently in production. How do you diagnose and fix it?

Common root causes and fixes:

  • Processing exceeds max.poll.interval.ms — the broker assumes the consumer died and rebalances even though it's alive. Diagnose by comparing processing-time logs with the setting; fix by raising the interval, reducing max.poll.records for smaller faster batches, or offloading long work to a separate thread pool while the poll loop keeps heartbeating.
  • session.timeout.ms with a blocked heartbeat — in older single-threaded clients a busy main thread could get a consumer falsely marked dead; newer clients heartbeat from a background thread. Tune session.timeout.ms and heartbeat.interval.ms.
  • Genuine churn — unstable networks or frequent restarts (for example Kubernetes pod evictions without graceful shutdown) make consumers repeatedly leave and rejoin; correlate JoinGroup/LeaveGroup events with infrastructure events. Call consumer.close() in shutdown hooks to leave gracefully, and use static group membership (group.instance.id) to avoid rebalances during brief expected restarts such as rolling deployments.

Section 3: AWS, Cloud & Kubernetes

Q1. What are the essential Kubernetes concepts for a Java tech lead, and how does Spring Boot integrate with liveness/readiness probes?

  • Pod — the smallest deployable unit (one or more containers sharing network/storage); typically one Spring Boot JVM per pod.
  • Deployment — manages a ReplicaSet of pods and handles rolling updates and rollbacks declaratively.
  • Service — a stable network endpoint (ClusterIP, NodePort, LoadBalancer) load-balancing across pod replicas, since pod IPs are ephemeral.
  • ConfigMap / Secret — externalize configuration and credentials from the image, injected as env vars or mounted files, supporting the 12-factor principle.
  • HPA (Horizontal Pod Autoscaler) — scales replica count on CPU/memory or custom metrics (Kafka consumer lag, queue depth via KEDA).

Spring Boot Actuator (2.3+) exposes /actuator/health/liveness and /actuator/health/readiness as first-class Kubernetes probe groups.

# application.yml
management:
  endpoint:
    health:
      probes:
        enabled: true
  health:
    livenessstate:
      enabled: true
    readinessstate:
      enabled: true
 
# deployment.yaml
livenessProbe:
  httpGet:
    path: /actuator/health/liveness
    port: 8080
  initialDelaySeconds: 30
  periodSeconds: 10
readinessProbe:
  httpGet:
    path: /actuator/health/readiness
    port: 8080
  initialDelaySeconds: 20
  periodSeconds: 5

The critical distinction: a failing liveness probe makes Kubernetes restart the pod (use it only for unrecoverable states like a deadlocked JVM); a failing readiness probe removes the pod from the Service's load-balancing pool without restarting it (use it for “temporarily can't serve traffic,” such as warming caches at startup or a critical downstream dependency being unavailable). Conflating the two causes needless restart loops during transient outages.

Note: Own the health-check strategy explicitly rather than accepting defaults: a readiness check including a database ping correctly pulls a pod out of rotation during a DB blip, but using the same check for liveness would cause a pointless restart storm during that same blip.

Q2. What is the difference between EC2 and Lambda? Describe S3 storage classes.

EC2 provides resizable virtual servers with full control of the OS and runtime, billed by instance uptime regardless of utilization — suited to long-running, stateful, predictable workloads. Lambda is serverless compute that runs code in response to events with no server management: stateless, capped at 15 minutes per execution, billed per millisecond of compute — cost-effective for sporadic or event-driven work such as S3 uploads or API requests. The choice depends on traffic pattern, statefulness, and how much infrastructure management the team will accept.

S3 is highly scalable object storage (buckets of objects addressed by key) with 11 nines of durability. Storage classes trade cost for access pattern: Standard (frequent access), Intelligent-Tiering (auto-moves objects by usage), Standard-IA and One Zone-IA (infrequent access, cheaper), and Glacier / Glacier Deep Archive (long-term archival, retrieval from minutes to hours). Lifecycle policies automate transitions as data ages.

Q3. What is a VPC, and what are IAM best practices?

A VPC is a logically isolated network where you define IP ranges, subnets, route tables, and gateways. Traffic is controlled by security groups (stateful, instance-level) and network ACLs (stateless, subnet-level). Put load balancers in public subnets with an internet gateway, and databases and application servers in private subnets with no direct internet access; use VPC peering or Transit Gateway to connect VPCs and on-premises networks (via VPN or Direct Connect), and deploy multi-AZ for availability.

IAM controls authentication and authorization via users, groups, roles, and JSON policies. Best practices: least privilege; avoid the root account for daily work; enforce MFA; use roles rather than hardcoded credentials for EC2/Lambda; use temporary STS credentials instead of long-lived access keys; group users by function and attach policies to groups; and audit with IAM Access Analyzer to find unused or overly permissive policies.

Q4. What is the difference between horizontal and vertical scaling, and how does Auto Scaling work?

Vertical scaling (scale up) enlarges an existing instance (t3.medium to t3.xlarge): simpler, but bounded by hardware limits and usually needing downtime. Horizontal scaling (scale out) adds instances to spread load, managed on AWS by Auto Scaling Groups working with an Elastic Load Balancer. ASGs watch CloudWatch metrics (CPU, request count) and launch or terminate instances using target-tracking, step, or scheduled policies. Horizontal scaling is generally preferred in cloud-native design because it improves fault tolerance and removes single points of failure.

Q5. An Auto Scaling Group isn't scaling in despite low CPU. How do you troubleshoot?

  • Scaling policy and cooldown — a long scale-in cooldown (default 300 seconds, sometimes configured far higher) intentionally blocks rapid scale-in until it expires after the last activity.
  • Scale-in protection — individual instances may have protection enabled (intentionally for stateful, long-running jobs, or left on by accident), which stops the ASG terminating them regardless of metrics.
  • Conflicting policies or scheduled actions — a scheduled action holding minimum capacity, or step scaling conflicting with target tracking on the same ASG.
  • Minimum capacity — a minimum set higher than desired artificially prevents scale-in below that floor.
  • Multiple metrics — with combined metrics (ALB request count plus CPU), target tracking honors whichever needs more capacity, so another metric may block scale-in even though CPU looks low.

The fastest path to root cause is the Activity History tab in the EC2 console or the DescribeScalingActivities API, which logs why scaling decisions were made or blocked.

Q6. Design a multi-region disaster-recovery architecture on AWS with an RPO of 5 minutes and an RTO of 15 minutes.

A 5-minute RPO and 15-minute RTO call for warm standby or pilot light rather than backup-and-restore (whose RTO is measured in hours). Warm standby is safer for the RTO because pilot light must start compute from zero.

  • Database — Aurora Global Database (cross-region replication with typically sub-second lag, far inside the 5-minute RPO, plus fast regional failover), or DynamoDB Global Tables for active-active NoSQL.
  • Compute — keep a scaled-down but fully functional copy running in the secondary region (Auto Scaling Groups behind an Application Load Balancer), ready to scale up quickly on failover.
  • Traffic — Route 53 health checks with failover routing redirect DNS to the secondary region's load balancer on failure; keep DNS TTL low (around 60 seconds) to limit propagation delay.
  • Assets and config — S3 with Cross-Region Replication.
  • Automation — automate failover with Systems Manager runbooks or Lambda triggered by CloudWatch alarms, since manual steps add unpredictable delay that risks the RTO.
  • Validation — run regular DR drills with AWS Fault Injection Simulator to confirm the real failover time meets the target.

Q7. Design a secure, cost-optimized architecture for sensitive financial data using Lambda and S3.

  • Encryption at rest — use SSE-KMS rather than default SSE-S3: KMS gives CloudTrail audit trails of key use and fine-grained key policies over which IAM roles can decrypt, often a compliance requirement (PCI-DSS, SOC 2).
  • Encryption in transit and exposure — bucket policies deny non-HTTPS requests (aws:SecureTransport condition) and S3 Block Public Access is enabled at the account level.
  • Lambda hardening — encrypt sensitive environment variables with KMS and give the execution role least-privilege access scoped to specific S3 prefixes and KMS keys, with no wildcards.
  • Cold starts — provisioned concurrency keeps environments pre-warmed (at the cost of paying for reserved capacity continuously); for occasional cold-start pain, shrink the package, trim dependencies, and pick a faster-starting runtime. VPC-attached Lambdas once paid a big cold-start penalty for ENI creation, largely fixed by Hyperplane ENI sharing.
  • Auditing — enable AWS Config rules and CloudTrail account-wide for an immutable audit trail of API calls and configuration changes.

Q8. How would you migrate a 5TB PostgreSQL database to AWS with minimal downtime?

Use AWS Database Migration Service (DMS) with continuous replication rather than dump-and-restore, which would mean unacceptable downtime at this size.

  • 1. Provision the target (RDS or Aurora PostgreSQL), sized from the source's utilization.
  • 2. Run DMS's initial full load, using a large replication instance and parallel multi-threaded table loads to shorten the window.
  • 3. Enable Change Data Capture (via PostgreSQL logical replication / WAL) so ongoing source writes keep replicating during and after the full load; the app sees zero downtime in this phase.
  • 4. When CDC lag nears zero, validate consistency with DMS's built-in data validation (row counts and checksums).
  • 5. Cut over in a brief window: pause writes, drain remaining CDC changes, repoint connection strings/DNS to the new instance, and resume, typically a few minutes of downtime.
  • 6. For network transfer from on-premises, use Direct Connect or a Site-to-Site VPN; if transfer time is still prohibitive, seed the bulk data with AWS Snowball and let DMS CDC catch up the delta.

Section 4: Frontend Integration — Angular & React

AngularJS & Angular

Q1. What is scope in AngularJS, and what is two-way data binding?

In AngularJS 1.x (the legacy framework, distinct from the completely rewritten Angular 2+), $scope is the glue object connecting a controller's logic to its HTML template: anything attached to $scope is accessible from the template. Two-way data binding (via ng-model) keeps the view and model synchronized automatically: typing in an input updates the $scope property and programmatic model changes update the display, with no manual DOM manipulation. Under the hood AngularJS runs a digest cycle with dirty checking: on any event (user input, HTTP response, timeout) it compares the current and previous values of every watched expression, updates the DOM on differences, and re-runs until nothing changes or 10 iterations are reached.

// AngularJS 1.x controller
app.controller('EmployeeController', function($scope) {
    $scope.employeeName = "Alice"; // attached to $scope: visible in the template
    $scope.greetEmployee = function() {
        alert("Hello, " + $scope.employeeName);
    };
});
 
<!-- Corresponding template -->
<div ng-controller="EmployeeController">
    <input type="text" ng-model="employeeName">   <!-- two-way bound to $scope.employeeName -->
    <p>{{ employeeName }}</p>                        <!-- displays the current value live -->
    <button ng-click="greetEmployee()">Greet</button>
</div>

Note: $scope was entirely replaced in modern Angular (2+) by a TypeScript component architecture in which each component holds its own state as class fields, with unidirectional data flow and explicit change detection, one reason for the move away from AngularJS's watcher-heavy model.

Q2. Why does the digest cycle cause performance problems and infinite loops, and how do you fix them?

Dirty checking is synchronous and runs on every digest, so thousands of watchers cause visible UI lag, especially on older browsers and mobile. An infinite digest loop occurs when a watched expression's value changes as a side effect of the digest itself: typically a template-bound function (like {{ getFormattedValue() }}, or ng-repeat over a function returning a new array) that returns a new object reference on every call, which reference-equality checks read as a change, triggering yet another pass until the “10 $digest() iterations reached” error.

Debugging and fixes:

  • Find the offending watcher by logging inside $watch callbacks or using the Batarang extension (with debug info temporarily enabled).
  • Memoize the function so it returns a stable cached reference when inputs are unchanged, or precompute values in the controller and bind to scope properties updated explicitly.
  • Use one-time bindings ({{::item.name}}) for data that doesn't change after first render, which deregisters those watchers.
  • Use pagination or virtual scrolling (ui-grid) for large ng-repeat lists so only visible rows are watched, and track by (ng-repeat="item in items track by item.id") to avoid destroying and recreating DOM and watchers when the array reference changes.
  • Prefer ng-if over ng-show for large hidden sections, and use deep-watch ($watch's third argument) or a custom equality function judiciously.

Q3. What are directives (structural vs. attribute), and how do isolated-scope bindings '=', '&', and '@' differ?

A directive attaches custom behavior to, or creates, HTML elements and attributes. Kinds: component directives (a directive with its own template, e.g. <app-employee-card>); structural directives that change DOM structure by adding or removing elements (*ngIf, *ngFor); and attribute directives that change the appearance or behavior of an existing element (ngClass, ngStyle, or a custom highlighter).

<!-- Structural: conditionally includes/excludes this whole element -->
<div *ngIf="employee.isActive">{{ employee.name }} is currently active</div>
<!-- Structural: repeats this element once per item -->
<li *ngFor="let employee of employeeList">{{ employee.name }}</li>
<!-- Attribute: conditionally applies a CSS class -->
<div [ngClass]="{ 'highlighted': employee.isVip }">{{ employee.name }}</div>
 
// A custom ATTRIBUTE directive
@Directive({ selector: '[appHighlightOnHover]' })
export class HighlightOnHoverDirective {
    constructor(private elementRef: ElementRef) { }
 
    @HostListener('mouseenter') onMouseEnter() {
        this.elementRef.nativeElement.style.backgroundColor = 'yellow';
    }
    @HostListener('mouseleave') onMouseLeave() {
        this.elementRef.nativeElement.style.backgroundColor = '';
    }
}

For an AngularJS directive with an isolated scope, the three binding types are:

  • '@' — one-way string binding: passes the literal attribute value (or an interpolated {{ }} string) into the isolated scope; good for simple config like a title or label.
  • '=' — genuine two-way binding: a live link between a parent-scope property and an isolated-scope property (implemented with a $watch on each side), so changes propagate both ways.
  • '&' — passes behavior: wraps a parent expression or function so the directive can invoke it, often with locals (onSave({item: someItem})); the recommended way to trigger parent side effects with clean separation, versus $emit/$broadcast.

For bidirectional communication, combine '=' for shared reactive data (a selected item) with '&' for explicit action callbacks (onItemSelected), rather than leaking implementation detail through $rootScope.$broadcast.

Q4. What are decorators in Angular? What differs between ng-if and ng-show, factory and service, and dependency injection in AngularJS?

A decorator is a TypeScript feature that attaches metadata to a class, method, property, or parameter without changing its logic; Angular reads that metadata to wire things together.

  • @Component — marks a class as a component with its template, styles, and selector.
  • @Injectable — makes a class injectable via Angular's DI (parallel to Spring's DI on the backend).
  • @Input / @Output — data flowing in from a parent template / events (usually an EventEmitter) flowing out to the parent.
  • @NgModule — declares which components, directives, and modules belong together.
  • @HostListener — binds a method to a DOM event on the host element.
@Component({
    selector: 'app-employee-card',
    template: `<div>{{ employeeName }}</div>`
})
export class EmployeeCardComponent {
    @Input() employeeName: string;               // data flows IN from the parent
    @Output() cardClicked = new EventEmitter();  // events flow OUT to the parent
}
  • ng-if vs. ng-show/ng-hide — ng-show/ng-hide toggle the CSS display property, leaving the element (and its watchers and listeners) in the DOM: faster for frequent toggling of simple elements. ng-if adds or removes the element and creates or destroys its scope: better for complex or rarely shown content, with some overhead when toggled frequently.
  • factory vs. service — both produce singletons. A factory is a function whose returned object becomes the service, flexible and good for returning a function or an object with private state; a service is a constructor function instantiated with new, so you attach members to this.
  • Dependency injection in AngularJS — components declare dependencies (function($scope, $http, myService)) and the injector supplies them. Because minification renames parameters, use the array notation (['$scope', '$http', 'myService', function(...) {...}]). DI promotes loose coupling and easy mocking in tests (Jasmine/Karma).

Q5. How does AngularJS compare with Ext JS?

AngularJS (and Angular) is a comprehensive MVC/MVVM application framework focused on structuring logic and data flow (two-way binding, DI, routing, components) and deliberately ships few pre-styled visual widgets, so you pair it with a UI library (Angular Material, Bootstrap). Ext JS (Sencha) is primarily a rich UI component library of professionally styled, highly configurable widgets (sortable/filterable/groupable data grids, trees, complex forms, dashboards), historically strong for internal, data-heavy enterprise line-of-business apps and less common for public consumer sites.

React

Q6. What is the Virtual DOM, and how does React's Fiber reconciliation work?

The Virtual DOM is a lightweight in-memory JavaScript representation of the real DOM. On a state or props change React updates the Virtual DOM first, diffs the new tree against the previous one (reconciliation) to find the minimal set of changes, batches updates, and applies only those to the real DOM, avoiding costly reflow and repaint. It isn't always faster than hand-tuned direct manipulation, but it gives a predictable, declarative model that scales.

Fiber (React 16+) reimplements reconciliation to allow incremental, interruptible rendering. The old stack-based reconciler processed the whole tree synchronously and recursively, so a large tree could block the main thread and cause jank. Fiber breaks work into units represented as a tree of fiber nodes (each holding component type, props, state, and parent/child/sibling pointers), checks after each unit whether higher-priority work (a user interaction) should preempt, and yields to the browser using cooperative scheduling. It has two phases: render/reconciliation (interruptible, building a work-in-progress tree by comparing it against the current one) and commit (synchronous and uninterruptible, applying DOM mutations at once to avoid an inconsistent UI). This underpins Concurrent Mode, Suspense, and time-slicing.

Q7. What are the differences between functional and class components, and what do Hooks and keys do?

Class components extend React.Component, require render(), manage state with this.state/this.setState(), and use lifecycle methods (componentDidMount, componentDidUpdate). Since Hooks arrived in React 16.8, functional components can manage state and effects: useState replaces this.state, and useEffect consolidates componentDidMount/DidUpdate/WillUnmount into one dependency-array-based API. Hooks remove the pain of binding this and let you share stateful logic through custom hooks rather than higher-order components or render props, so functional components with Hooks are now the standard.

Keys are stable, unique attributes on list items that let React identify which items changed, were added, or removed during reconciliation. Use a stable data ID, not the array index: index keys on reorderable or filtered lists make React mismatch elements, causing state to persist on the wrong item, extra re-renders, or broken animations and focus.

Q8. How does useEffect work, and what is prop drilling?

useEffect runs side effects (data fetching, subscriptions, timers, manual DOM work) outside the render phase. The dependency array controls re-runs: omitted means after every render; empty ([]) means once after the initial render (like componentDidMount); listed values mean whenever any changes, compared with Object.is. The callback can return a cleanup function, which React calls before unmount or before the effect re-runs, essential for clearing subscriptions, timers, and listeners. An incomplete dependency array causes stale closures over outdated state or props; the ESLint exhaustive-deps rule catches this.

Prop drilling is passing data through many intermediate components that don't need it just to reach a deeply nested one, coupling components to the data's shape and cluttering them. The Context API (a Provider supplying a value, any descendant reading it with useContext) avoids it; for frequent updates, async logic, or global state across unrelated trees, use Redux, Zustand, or Recoil for predictable updates, middleware, and dev tools. Choose by application complexity and update frequency.

useEffect(() => {
    const abortController = new AbortController();
    const refreshIntervalId = setInterval(refreshOrders, 5000);
 
    fetch('/api/orders', { signal: abortController.signal })
        .then(response => response.json())
        .then(setOrders);
 
    // cleanup: runs on unmount (or before the effect re-runs)
    return () => {
        clearInterval(refreshIntervalId);   // stop the timer
        abortController.abort();            // cancel the in-flight request
    };
}, []); // empty dependency array: runs once after the initial render

Q9. How do you prevent unnecessary re-renders when a frequently changing context is used by only a few components?

Every useContext consumer re-renders whenever the context value changes (compared by reference), regardless of whether the slice it uses changed.

  • Split one large context into several granular ones so components subscribe only to the slice they need.
  • Memoize the context value with useMemo, so the Provider doesn't create a new object reference on every parent re-render when the data is unchanged.
  • Use a selector pattern (use-context-selector, or Zustand) so components re-render only when their selected derived value changes.
  • Wrap expensive descendants that don't consume the context in React.memo (with a custom comparison if needed) to create re-render boundaries.

Combining context splitting with strategic memoization usually gives the best balance without adopting a full external state library, unless complexity warrants one.

Q10. A React app leaks memory after many page navigations. How do you debug it?

Take heap snapshots in the browser DevTools Memory tab before and after repeated navigation cycles and use the comparison view to find object types whose instance counts grow with navigation but never return to baseline. Then trace retaining paths back to the root cause, commonly:

  • Missing cleanup in useEffect — subscriptions, listeners, timers (setInterval/setTimeout), or WebSockets not torn down on unmount keep component state alive through captured closures.
  • Async work resolving after unmount — fix with an AbortController to cancel in-flight requests, or a mounted-ref guard around state updates.
  • Third-party libraries (charts, maps, rich-text editors) that create DOM or listeners outside React's lifecycle and need explicit destroy()/dispose() in the cleanup function.
  • Global references — a module-level array or singleton event emitter accumulating listeners with no matching removeListener.

The React DevTools Profiler, combined with looking for components with unexpectedly high retainer counts in snapshots, usually turns a vague “React memory leak” into a concrete reference-retention bug.

Q11. What is the difference between == and === in JavaScript?

  • == loose equality: converts types first ("5" == 5 is true, null == undefined is true).
  • === strict equality: no conversion; types and values must both match ("5" === 5 is false).
  • Prefer === to avoid surprising coercion. (In Java, == compares primitives by value and references by identity; there is no ===.)

Q12. What does "use strict" do, at function level and at script level?

  • Enables strict mode: silent errors become thrown errors, undeclared variables are not allowed, duplicate parameter names and with are disallowed, and this is undefined in plain function calls.
  • Script level: put "use strict"; as the first statement of the file — applies to everything.
  • Function level: first statement inside one function — applies only to it.
  • Class bodies and ES modules are strict automatically.

Q13. What does CSS stand for?

Cascading Style Sheets — the language that describes the presentation (layout, colours, fonts) of HTML; the "cascade" is the rule order (specificity, source order, importance) that decides which style wins.

Section 5: Security — Application-Level & Secure Coding

Application-Level Security Questions

Q1. What is the difference between authentication and authorization?

Authentication verifies identity (“who are you”) via credentials, tokens, or certificates. Authorization determines permissions (“what are you allowed to do”) after identity is established, checking roles/scopes against protected resources. Spring Security handles both: the AuthenticationManager for authentication, and access-control rules / AccessDecisionManager for authorization.

Q2. What is a JWT, and what is its structure?

A JSON Web Token is a compact, self-contained token for transmitting claims between parties, made of three Base64Url-encoded parts separated by dots: Header (algorithm and type), Payload (claims such as user ID and expiry), and Signature (verifies integrity using a secret or private key). Being stateless, servers avoid session storage, which suits scalable, distributed REST authentication.

Figure: JWT structure

Q3. What are XSS and CSRF, and how does Spring Security help prevent them?

XSS injects malicious scripts into pages viewed by other users; mitigate with output encoding/escaping and Content-Security-Policy headers. CSRF tricks an authenticated user's browser into submitting unintended requests; mitigate with anti-CSRF tokens tied to the user session. Spring Security enables CSRF protection by default for state-changing requests and provides header utilities to reduce XSS exposure.

Secure Coding Guidelines (Condensed)

Adapted and condensed from Oracle's “Secure Coding Guidelines for Java SE”; captures the most interview-relevant points from each major topic area.

0. Fundamentals

  • Prefer code that is obviously correct over code that merely has “no obvious flaws.”
  • Design APIs with security in mind from the start; e.g. marking a class final prevents a malicious subclass from overriding methods or adding a finalizer.
  • Avoid duplicating code or data; a security fix applied to one copy is easily missed in another.
  • Follow least privilege: run code with the minimum permissions it needs, shrinking the blast radius of any flaw.
  • Establish clear trust boundaries and validate/sanitize any data crossing one.
  • Check permissions once and hand out a capability rather than re-checking throughout a call chain; encapsulate with private fields and a minimal public interface.

1. Denial of Service

Untrusted input must never trigger resource consumption wildly disproportionate to the request. Attack patterns to defend against:

  • Enormous requested image/vector-graphic sizes; integer overflow bypassing a size check.
  • A small payload expanding into a huge in-memory object graph; “zip bombs” (cap the decompressed size directly, never trust compressed size or metadata).
  • The “billion laughs” XML entity-expansion attack (enable XMLConstants.FEATURE_SECURE_PROCESSING).
  • Hash-flooding (many colliding keys degrading O(n) to O(n²)); catastrophic regex backtracking; unbounded XPath cost.
  • Unbounded resource use during deserialization of untrusted data; infinite loops on corner-case input (ensure each iteration makes forward progress).

Always release resources even when an exception occurs (try-with-resources), and watch for integer overflow in limit checks: rearrange arithmetic so no addition can overflow.

// Vulnerable: current + extra can overflow for large values and wrongly pass the check
if (current + extra > max) { throw new IllegalArgumentException(); }
 
// Safe: rearranged so no addition can overflow
private void checkGrowBy(long extra) {
    if (extra < 0 || current > max - extra) {
        throw new IllegalArgumentException();
    }
}

2. Confidential Information

  • Strip sensitive details from exception messages and stack traces before they reach an untrusted caller or lower-privilege log.
  • Never log passwords, session tokens, or full card numbers, even at debug level.
  • For very sensitive in-memory data, overwrite it when no longer needed; Strings are immutable and can't be cleared, which is why password APIs prefer char[].

3. Injection and Inclusion

  • Never build SQL, HTML, XML, or shell commands by concatenating untrusted input; use PreparedStatement bind parameters and proper templating/serialization libraries.
  • Never pass untrusted data onto a command line (Runtime.exec / ProcessBuilder) without careful validation.
  • Disable DTD processing / external entity resolution when parsing untrusted XML (XXE).
  • Treat evaluating untrusted expressions or scripts (scripting engines, EL) like executing arbitrary code.
// Vulnerable: string concatenation allows SQL injection
String unsafeQuery = "SELECT * FROM accounts WHERE username = '" + userInput + "'";
 
// Safe: PreparedStatement handles escaping correctly
PreparedStatement safeStatement =
        connection.prepareStatement("SELECT * FROM accounts WHERE username = ?");
safeStatement.setString(1, userInput);

4. Accessibility and Extensibility

  • Default to private and widen access only when genuinely needed; limit package accessibility and avoid unrelated classes sharing a package.
  • Limit exposure of ClassLoader instances, and mark security-sensitive classes final: a malicious subclass can override behavior, add a finalizer to resurrect a “destroyed” object, or violate invariants.
  • Be careful calling overridable methods from a superclass, especially constructors.

5. Input Validation

  • Validate all input crossing a trust boundary, including values returned by untrusted/overridable code.
  • Wrap native (JNI) methods in a Java-level wrapper that validates input before reaching native code, which lacks the JVM's memory-safety guarantees.

6. Mutability

  • Prefer immutable value types; return defensive copies of mutable fields and copy mutable inputs before storing them.
  • Don't rely on == identity for objects supplied by untrusted code; treat data passed into and returned from untrusted objects as output and unvalidated input respectively.
  • Make public static fields final and truly constant; never expose mutable static state publicly.

7. Object Construction

  • Prefer factory methods for sensitive classes so extra checks can be enforced; actively prevent unauthorized construction where it is a security problem.
  • Defend against partially initialized instances, never call overridable methods from a constructor, and guard non-final classes against malicious clone().

8. Serialization and Deserialization

  • Avoid making security-sensitive classes serializable; serialization is an alternate construction path that bypasses constructors.
  • Guard sensitive fields with transient or custom writeObject()/readObject().
  • Treat deserialization exactly like construction from attacker-controlled bytes: all validation and defensive-copying concerns apply to readObject().

Note: Deserializing untrusted data has caused numerous serious vulnerabilities, including remote code execution. If you must, use an object-input filter (ObjectInputFilter, standard since Java 9) to restrict which classes may be deserialized.

9. Access Control

  • Understand how SecurityManager checks walk the call stack to determine the effective caller.
  • Use AccessController.doPrivileged() carefully: it says “this trusted code knowingly exercises its own privilege on behalf of a possibly less-privileged caller.”
  • Don't cache the result of a privileged operation and hand it to a caller who couldn't have triggered it; know that security context does not automatically transfer to new threads; and be aware that reflection (Method.invoke) can obscure who the “real” caller is.

Note: SecurityManager and the sandbox-style permission model were deprecated for removal in Java 17 (JEP 411). This material remains useful for legacy code and the underlying concepts (trust boundaries, least privilege, privileged operations), but new applications should not be designed around SecurityManager.

Section 6: Security, Networking & API Performance

Q1. What is the difference between encryption and hashing?

They are frequently confused but are fundamentally different operations.

  • Encryption — a reversible transformation of plaintext into ciphertext using a key. Anyone with the correct key (the same key for symmetric encryption, the corresponding private key for asymmetric) can decrypt it back to the exact original. Use it when the original data must eventually be recovered. “Encrypted data” is simply the ciphertext output.
  • Hashing — a one-way, non-reversible transformation into a fixed-size digest. The same input always gives the same hash, but a good cryptographic hash makes it computationally infeasible to find any input producing a target hash. Use it to verify data (checking a password attempt against a stored hash without ever storing or recovering the plaintext) or to detect tampering.
// Encryption: REVERSIBLE, the original plaintext CAN be recovered with the right key
byte[] ciphertext = encryptCipher.doFinal(originalPlaintext.getBytes());
byte[] recoveredPlaintext = decryptCipher.doFinal(ciphertext); // gets the ORIGINAL back
 
// Hashing: NOT reversible, there is no "un-hash" operation
MessageDigest sha256Digest = MessageDigest.getInstance("SHA-256");
byte[] contentHash = sha256Digest.digest(inputData.getBytes());
// Verification re-hashes a LATER input and compares the two hashes

Note: For passwords, use a purpose-built, deliberately slow, tunable algorithm (bcrypt, scrypt, or Argon2), not a fast general-purpose hash like plain SHA-256. A fast hash makes brute-forcing a leaked hash database dramatically cheaper, exactly what password-hashing algorithms are engineered to counteract.

Q2. How are IP addresses communicated between servers?

  • 1. Name resolution (DNS) — the application usually starts with a hostname (api.example.com); a DNS server resolves it to the current IP address.
  • 2. Connection — the OS networking stack (typically TCP, for reliable ordered delivery) connects to that IP on a port (443 for HTTPS) through the three-way handshake (SYN, SYN-ACK, ACK).
  • 3. Routing — packets cross intermediate routers, each forwarding them one step closer based on the destination IP in the packet header.
  • 4. Data exchange — over the open TCP connection the servers exchange application data (an HTTP request and response).

From a Java application's viewpoint, java.net (or a higher-level HTTP client) handles all of this transparently; code supplies a URL or hostname and rarely touches raw IPs or packets.

Q3. What are HTTP handlers?

An HTTP handler is code that processes an incoming HTTP request and produces the response; the concept is universal even though naming varies by layer.

  • Servlet — the foundational Java EE handler (doGet()/doPost()).
  • Spring MVC @Controller methods — a higher-level abstraction on the Servlet API; each @RequestMapping-annotated method handles one URL and HTTP-method combination.
  • Filters — related but distinct: rather than completing a request, a Filter intercepts it (and the response) on the way through the pipeline for cross-cutting concerns (authentication, logging, compression) and passes it down the chain.
  • com.sun.net.httpserver.HttpHandler — the JDK's own minimal, built-in interface with one method, handle(HttpExchange), the barest expression of the concept.
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
 
public class SimpleHandler implements HttpHandler {
    @Override
    public void handle(HttpExchange httpExchange) throws IOException {
        String responseText = "Hello from a raw HTTP handler";
        httpExchange.sendResponseHeaders(200, responseText.length());
        try (OutputStream responseBody = httpExchange.getResponseBody()) {
            responseBody.write(responseText.getBytes());
        }
    }
}

Q4. How do you avoid SQL injection in a Java application?

Code examples of the vulnerable and safe forms are in Section 5 and Part 4, Section 4. The defenses, in priority order:

  • Always use PreparedStatement (or an ORM/query builder that parameterizes internally) with bind parameters for any user-originated value; never concatenate untrusted input into SQL.
  • If SQL structure must vary (an optional WHERE clause depending on selected filters), build the structure dynamically but still bind every value via parameters.
  • Apply least privilege to the application's database account (only the specific permissions it needs, never broad administrative rights), limiting the damage of a successful injection.
  • Add input validation (a numeric ID really is numeric) as defense in depth on top of parameterized queries, never as a replacement, since validation alone is easy to get wrong or bypass.

Q5. What steps would you take to improve the performance of an API?

  • 1. Measure first — profile, use distributed tracing (Zipkin, Jaeger, APM), and log per-step timings; optimizing a non-bottleneck wastes effort and adds complexity.
  • 2. Optimize database queries — often the single biggest lever: review slow queries, add indexes, and eliminate N+1 queries with JOIN FETCH, @EntityGraph, or batch fetching (Part 4, Section 5).
  • 3. Cache — in-memory (Caffeine) for small hot data, distributed (Redis) for data shared and consistent across instances, for data read often but changed rarely.
  • 4. Go async for non-critical work — hand off side effects (a confirmation email) to a message queue or async task instead of making the caller wait.
  • 5. Pool connections — both database connections and outgoing HTTP client connections, rather than paying setup cost per request.
  • 6. Shrink payloads — return only needed fields (projection parameters), compress large responses (gzip), and paginate unbounded lists.
  • 7. Scale horizontally — once a single instance is reasonably optimized, run several behind a load balancer.

Q6. On Amazon, applying search filters uses which design pattern?

The Strategy pattern (closely related to, and often combined with, the Specification pattern). Each filter (“Brand: Sony”, “Price: $20–$50”, “Rating: 4 stars & up”, “Prime eligible”) is modeled as its own predicate object behind a common interface with one method: does this product satisfy my criteria? The search engine combines the active filters (usually with logical AND) without knowing what any individual filter checks. This is the same design as the FilteredList exercise in Part 3, Section 6.

Problem statement: Combine any set of user-selected filters over a product list without the search engine knowing what each filter checks.

public interface ProductFilter {
    boolean matches(Product candidateProduct);
}
 
public class BrandFilter implements ProductFilter {
    private final String requiredBrand;
 
    public BrandFilter(String requiredBrand) {
        this.requiredBrand = requiredBrand;
    }
 
    @Override
    public boolean matches(Product candidateProduct) {
        return candidateProduct.getBrand().equalsIgnoreCase(requiredBrand);
    }
}
 
public class PriceRangeFilter implements ProductFilter {
    private final BigDecimal minimumPrice;
    private final BigDecimal maximumPrice;
 
    public PriceRangeFilter(BigDecimal minimumPrice, BigDecimal maximumPrice) {
        this.minimumPrice = minimumPrice;
        this.maximumPrice = maximumPrice;
    }
 
    @Override
    public boolean matches(Product candidateProduct) {
        return candidateProduct.getPrice().compareTo(minimumPrice) >= 0
                && candidateProduct.getPrice().compareTo(maximumPrice) <= 0;
    }
}
 
// The engine applies whichever filters are currently active (logical AND)
public List<Product> applyActiveFilters(List<Product> allProducts, List<ProductFilter> activeFilters) {
    return allProducts.stream()
            .filter(product -> activeFilters.stream().allMatch(filter -> filter.matches(product)))
            .collect(Collectors.toList());
}

Adding a new filter (“seller rating”) means writing one new class implementing ProductFilter, with zero changes to the engine: a textbook application of the Open/Closed Principle.

Section 7: Unix / Linux Command Line

Q1. How do you find a file recursively in Unix?

find searches recursively by default (unlike ls, which lists only a directory's immediate contents). To search inside file contents instead of by name, use grep -r.

# Find a file by exact name, searching recursively from the current directory downward
find . -name "application.properties"
 
# Case-insensitive name search
find . -iname "readme*"
 
# Only regular files (excluding directories) matching a pattern
find /var/log -type f -name "*.log"
 
# Combine criteria, e.g. files modified in the last 7 days
find . -name "*.tmp" -mtime -7
 
# Search WITHIN file contents, recursively
grep -r "TODO" /path/to/project

Q2. How do you see CPU and memory utilization in Unix?

  • top — the classic interactive, continuously refreshing view of processes (sorted by CPU by default) with a system-wide summary.
  • htop — a friendlier, colorized alternative with easier sorting, filtering, and a process tree (often must be installed separately).
  • free -h — a one-shot summary of total, used, and free RAM and swap in human-readable units.
  • vmstat — virtual-memory, CPU, and I/O statistics, useful for spotting system-level problems like heavy swapping.
  • ps aux — a one-shot snapshot of all processes with CPU and memory use, good for scripting and piping.
top                                # interactive, continuously refreshing view
free -h                            # quick memory summary in human-readable units
ps aux --sort=-%cpu | head -10     # top 10 processes by CPU usage, as a one-shot list

Q3. How can you run the last command without using the up arrow?

  • !! — repeats the immediately preceding command exactly; sudo !! re-runs it prefixed with sudo, handy after a permission failure.
  • !n — repeats a specific command by its number in the history list (shown by history).
  • !string — repeats the most recent command that started with the string (e.g. !git).
  • Ctrl+R — an interactive, incremental reverse search through history: type a few characters and jump to the matching past command.
ls -la /some/directory
!!        # re-runs "ls -la /some/directory" exactly
sudo !!   # re-runs the previous command again, prefixed with sudo

Q4. How does the Unix shell work at a high level?

A shell (bash, zsh, sh) is the command-line interpreter between the user and the kernel. When you press Enter it:

  • 1. Reads the input line.
  • 2. Parses it into tokens (command and arguments) and identifies shell syntax: pipes (|), redirection (>, >>, <), background execution (&), and command substitution ($(...)).
  • 3. Performs expansions: variables (like $HOME), wildcard/glob patterns (*.txt expanded to matching filenames), and tilde (~).
  • 4. Decides whether the command is a built-in (cd, echo, export, implemented by the shell itself with no new process) or an external program.
  • 5. For an external program, searches the directories in the PATH variable, in order, for a matching executable.
  • 6. Forks a child process and, in it, execs the program, replacing the child's memory image — the classic fork-then-exec mechanism.
  • 7. Waits for the process to finish, unless it was started in the background with a trailing &.
  • 8. Makes the exit status available (via $?), used by scripts for control flow such as an if statement.

Q5. What does grep do, and how does grep "word" filename execute?

grep (“Global Regular Expression Print”) searches input (files, or data piped from another command) for lines matching a literal string or regular expression and prints the matching lines.

  • grep "pattern" file.txt — print matching lines.
  • -i — case-insensitive; -r — search recursively through a directory tree; -v — invert (print lines that do NOT match); -c — print only a count; -n — prefix line numbers; -E — extended regex, enabling alternation (pattern1|pattern2).

For grep "word" filename: it reads the file line by line and checks whether the literal text “word” appears anywhere in each line. By default this is a substring match, so it also matches “password” and “wordsmith”. Matching lines are printed in file order and non-matching lines are skipped. If nothing matches, grep prints nothing and its exit status is 1 (0 means at least one match), which is what lets it drive shell if conditions.

# Match "word" as a whole, separate word (not a substring of "password"):
grep -w "word" filename
 
# Using grep's exit status directly in a shell script's control flow:
if grep -q "ERROR" application.log; then
    echo "Errors were found in the log file"
fi

Q6. What are nohup and & used for, and how do you run a process in the background?

They solve two different, complementary problems. A trailing & runs the command in the background so the shell returns control immediately. nohup (“no hang up”) makes the command immune to SIGHUP, the signal sent to a session's processes when its controlling terminal closes (for example, closing an SSH connection); without it the process is normally killed with the terminal. Used together, they launch a long-running job that neither ties up your terminal nor dies when you log out.

nohup ./long_running_script.sh &
# Runs in the background AND survives closing this SSH session.
# By default nohup writes the output to nohup.out in the current directory:
cat nohup.out
 
./my_script.sh &   # runs immediately in the background
jobs               # lists background jobs in THIS shell session
fg %1              # brings background job 1 back to the foreground
bg %1              # resumes a STOPPED job (e.g. paused with Ctrl+Z) in the background
 
# Move an already-running foreground process to the background:
# press Ctrl+Z to pause it, then run: bg

Note: Better options for genuinely long-running work: tmux or screen (terminal multiplexers that let you detach and later re-attach to view live output), or for a real production service a process supervisor/init system such as systemd or supervisord rather than nohup.

Q7. How do you see the first and last 10 lines of a file, and how do you delete files recursively?

head -10 filename.txt   # first 10 lines (10 is also the default)
tail -10 filename.txt   # last 10 lines (10 is also the default)
tail -f application.log # follow a growing log file live, printing new lines as they are appended
 
rm -r some_directory    # recursively remove a directory and everything in it
rm -rf some_directory   # same, but FORCE: no confirmation, ignore missing files/errors
 
# Delete only files matching a pattern, recursively:
find . -name "*.tmp" -type f -delete

Note: rm -rf is genuinely dangerous: it deletes recursively and silently with no confirmation and no recycle bin. A typo, an unexpectedly expanded wildcard, or (worst) running it as root against / or a variable that evaluated to empty has caused countless data-loss incidents. Double- and triple-check the exact target, especially in automated scripts.
